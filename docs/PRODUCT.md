# Product

Сводка уровня продукта; полные требования (FR-1…14, NFR-1…8, сцены приёмки, матрица
трассировки) — [prd.md](prd.md) (принято v1.4).

## What & Why

Агент-аналитик данных (ДЗ-1, OTUS «AI Agents», кейс 2). Бизнес ждёт часы на
вопрос, который сводится к одному SELECT с парой JOIN: аналитик пишет каждый
запрос руками, и ручной SQL не контролирует доступ (кто умеет писать запросы —
тот видит всё). Агент принимает вопрос на естественном языке, сам строит SQL
по графу связей, безопасно выполняет его под правами пользователя и объясняет
результат — минуты вместо часов, права как настройка, цифры бизнес-корректные.

Ценность по prd §1: скорость (V1), доступ как настройка (V2), бизнес-корректность
(V3), предсказуемость — каждый ответ с SQL, допущениями и стоимостью (V4),
проверяемость — валидация до выполнения + трейс (V5).

## Users

По prd §2:

- **Аналитик** (основной) — вопросы на естественном языке в рамках своих прав;
  при неоднозначности — один уточняющий вопрос.
- **Аналитик с правами нескольких доменов** — кросс-доменные джойны (логистика + HR).
- **Владелец данных** — вносит бизнес-рёбра и меняет права как настройки
  (`agent_relationships`, `agent_permissions`), без разработчика.
- **Администратор платформы** — трейсы, метрики, стоимость, аудит отказов.

## Scope

- Демо-схема из 7 таблиц (`customers`, `orders`, `order_items`, `products`,
  `campaigns`, `employees`, `bonuses`); только `SELECT`; одиночный «вопрос →
  ответ» без истории диалога.
- Цели v1: работающий контур «вопрос → SQL → безопасное выполнение → объяснение»,
  RBAC как настройки, семантика связей владельцев, декомпозиция тяжёлых запросов,
  каскад моделей с экономикой ≤ 0,7 ₽/запрос, трейс каждого прогона.
- Точки входа — CLI и Streamlit-демо (живой выбор пользователя для RBAC; c4-l2).
- Расширения владельца: live-наблюдаемость (ADR-010, ДЗ-06), внешний источник SAP
  (ADR-011, после ДЗ-06) — точки роста, не базовый скоуп.
- Детальный план фич — [feature_list.json](../feature_list.json).

## Non-Goals

Продукт сознательно НЕ делает (prd §3, model-card §2, c4-l2):

- **История диалога / мульти-turn** — одиночный «вопрос → ответ» (v1).
- **DDL/DML** — только `SELECT`; read-only роль — единственный канал исполнения.
- **Реальный SSO** — MVP `DevTokenAuth`; OIDC — production-конфигурация порта AuthProvider (ADR-005).
- **Per-user гранты в PostgreSQL** — права как данные + AST-валидатор (ADR-005); одна сервисная read-only роль.
- **HTTP API с контрактом** — интерфейсы CLI/Streamlit; openapi не ведётся (D-005).
- **Вероятностный роутер моделей** — статический Intent-Based роутинг (ADR-007); динамический — после появления eval-сета.
- **Собственное обучение моделей** — только pre-trained за шлюзом (model-card).
- **Единственный источник решений** — каждый ответ несёт SQL и допущения, проверяемо человеком.
- **Оценка/ранжирование людей, юридические заключения** — аналитика по процессам, не кадровые решения.
