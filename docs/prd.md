## 1. Проблема и ценность

Доступ к данным идёт через ручные SQL-запросы: аналитик пишет каждый запрос руками,
бизнес ждёт часы на вопрос, который сводится к одному SELECT с парой JOIN. Помимо
скорости есть вторая проблема — доступ: разные пользователи имеют право видеть разные
данные, и ручной SQL никак это не контролирует (кто умеет писать запросы — тот видит всё).

Агент принимает вопрос на естественном языке, строит SQL по графу связей схемы,
безопасно выполняет его под правами пользователя и объясняет результат на языке бизнеса.

| Поток | Ценность |
|---|---|
| V1 Скорость | Типовой вопрос — минуты вместо часов; не нужен SQL-навык |
| V2 Доступ как настройка | Права меняются `UPDATE`-ом строки (без деплоя и DDL) и действуют со следующего запроса |
| V3 Бизнес-корректность | Джойны и атрибуция — по семантике рёбер, внесённой владельцем данных; цифры не «какие-то», а правильные |
| V4 Предсказуемость | Каждый ответ снабжён SQL, допущениями и стоимостью; отказ по правам честный и формулируется бизнес-понятиями |
| V5 Проверяемость | Валидация до выполнения; трейс каждого прогона; оценка стоимости запроса в рублях |

## 2. Пользователи

| Роль | Главный сценарий | Что получает |
|---|---|---|
| Аналитик (основной пользователь) | «Сколько новых клиентов из Германии пришло из рекламных кампаний в октябре, и их средняя выручка?» | Ответ: текст + SQL + допущения + стоимость; при неоднозначности — один уточняющий вопрос |
| Аналитик с правами нескольких доменов | «Кто из менеджеров выполнил план по отгрузкам и не был премирован?» | Кросс-доменный джойн в рамках своих прав (отгрузки → сотрудники → премии) |
| Владелец данных | Ведёт связи и права своего домена | `agent_relationships` и `agent_permissions` как настройки: вносит бизнес-рёбра и меняет права без разработчика |
| Администратор платформы | Контроль качества и бюджета | Трейс прогонов, метрики (observability.md), стоимость запросов, аудит отказов по правам |

## 3. Цели и не-цели

**Цели (v1, учебный проект):** работающий контур «вопрос → SQL → безопасное выполнение →
объяснение» на демо-схеме из 7 таблиц (`customers`, `orders`, `order_items`, `products`,
`campaigns`, `employees`, `bonuses`); RBAC как настройки в БД; семантика связей владельцев
данных; декомпозиция тяжёлых запросов; каскад моделей с экономикой ≤ 0,7 ₽ на запрос;
трейс каждого прогона.

**Не-цели:**

- аутентификация внутри агента (SSO/IdP — задача фронта; агент — resource server за портом `AuthProvider`);
- запись в БД (только `SELECT`; read-only роль — единственный канал исполнения);
- row-level security как первичная граница прав и федерация второй БД (следующая ступень; RLS как составная часть рубежа БД уже заложена — ADR-005 v1.2);
- история диалога / мультиходовость («одиночный вопрос → ответ»);
- собственное обучение моделей и редактирование прав агентом;
- мини-UI владельцев данных для прав и связей (v1 — SQL-настройки).

## 4. Функциональные требования

Приоритеты: **P0** — ядро контура, без него сценарий не работает; **P1** — реализуется
в рамках проекта (T1-декомпозиция — основной путь на боевом масштабе; на демо-стенде
`plan_query` — заглушка «не декомпозировать», прозрачная для архитектуры — ADR-004).

| ID | Требование | Приоритет |
|---|---|---|
| FR-1 | Принимать бизнес-вопрос на естественном языке; возвращать ответ: текст + SQL + список допущений + стоимость | P0 |
| FR-2 | Строить SQL только по плану: код строит k взвешенных путей по активным рёбрам реестра (`find_join_paths`, снапшот с `graph_version`), модель ранжирует топ-5, при равных кандидатах — уточнение; соединить таблицы по несуществующей связи физически не может НИ В ОДНОМ контуре: FSM — SQL не пишется без JoinPlan (порядок узлов), тул-контур — пара операндов каждого JOIN сверяется с активным снимком реестра (`join_edges`, S31/D-033 п.5) | P0 |
| FR-3 | Неоднозначные формулировки: **один** уточняющий вопрос и остановка (`interrupt()` + checkpointer), или явная фиксация допущений; бизнес-глоссарий («выручка» = `SUM(orders.total)`) в векторной памяти | P0 |
| FR-4 | Валидация **до** выполнения в ОБОИХ контурах исполнения (FSM-ребро и тул-контур CLI — единый рубеж, S31): AST-обход (sqlglot, диалект postgres; одна инструкция; запрет `SET/COPY/CALL/DO` и функций deny-list; обход CTE/UNION/подзапросов/LATERAL; `LIMIT` к внешнему запросу) + ACL (вкл. колонки соединения) + deny-list схем (`pg_catalog`, `information_schema`, служебные схемы графа, `agent_*`) + инвариант реестра; FSM-вход дополнительно: джойны ⊆ `edge_id` плана + скелет не изменён (`skeleton_hash`, `mandatory_predicates` на месте); identity — проверенный токен для любого SQL-контура; текст от LLM — не доверенный; DDL/DML отказываются на уровне Rules + AST-whitelist + read-only роли | P0 |
| FR-5 | Различение исходов валидации: таблица не существует → галлюцинация → `diagnose_error` (retry); существует, но вне прав → `degrade` (без retry, сигнал безопасности) | P0 |
| FR-6 | RBAC: права как настройки (`agent_permissions`: роль → таблица → колонки; `agent_user_roles`); аутентификация за портом `AuthProvider` (MVP — `DevTokenAuth`); рубежи: фильтрация мира → AST-валидатор → deny-list схем → ACL колонок соединения → БД (RLS + `SET LOCAL app.user_id`, read-only, timeout); деградация вместо отказа с формулировкой через бизнес-понятия, без подтверждения существования чужих данных | P0 |
| FR-7 | Семантика связей: реестр `agent_relationships` — **единственный источник истины** (`edge_id`, жизненный цикл `draft → CI → active` с CI по факту, `cardinality`/`fanout_guard`, `mandatory_predicates`, `meaning`, `intent_tags`, `usage_notes`); FK — генератор кандидатов в очередь владельцу, не ребро; заявки `agent_edge_proposals`; `graph_version` снапшота пинится на прогон (state, кэш, аудит); `join_type` берётся из плана, модель не решает сама; допущения из `usage_notes` раскрываются в ответе | P0 |
| FR-8 | Каскад моделей: Intent-Based Routing «узел → навык → модель» (cheap/mid/strong за одним OpenAI-совместимым шлюзом); политика ретраев M1 (D-016): попытка 1 — базовая модель узла, попытка 2 — та же модель + текст ошибки, попытка 3 — уровень вверх при достатке бюджета; счётчики ≤ 3 на узел + глобальные капы ≤ 8 LLM-вызовов / ≤ 90 s / ≤ 2 ₽; reasoning-режим адресно | P0 |
| FR-9 | Принудительные форматы: `JoinPlan` / `QueryPlan` / `ResultCompact` — pydantic-модели, ответ валидируется схемой (temperature 0); constrained decoding где доступно, тул-based enforcement где нет | P0 |
| FR-10 | Самокоррекция: `diagnose_error → generate_sql`; невалидный JoinPlan → retry по политике M1 (валидация плана — код при парсинге); исчерпание — отказ с уточняющим вопросом; лимиты задаёт код: per-node счётчики + `recursion_limit` на весь граф (dead loop исключён) | P0 |
| FR-11 | Наблюдаемость: трейс каждого прогона — вопрос, допущения, план, SQL (шагов), `edge_id`, `graph_version`, retry_count, latency, TTFT, стоимость (итог + по узлам), cache hit; структурные логи с trace_id; live-метрики и спаны — Prometheus/Grafana через OTel (ADR-010), аналитические отчёты — из query_trace (observability.md); аудит append-only (S8) — отдельно от трейсов; основа eval-сета | P0 |
| FR-12 | Декомпозиция тяжёлых запросов (key-set exchange): T1 структурный (≥ 4 таблиц / ≥ 3 хопов → декомпозиция; основной путь на боевом масштабе) и T2 по EXPLAIN-cost (тяжёлый одиночный план → async / matview / approximate / отказ с рекомендацией — **не** декомпозиция); `plan_query` строит QueryPlan DAG (≤ 4 шагов, ≤ 3 таблиц), bind-параметры `= ANY(:keys)`, чанки 1000, промежуточный key-set без `LIMIT` — кап кардинальности 50 000 ключей (превышение → async / отказ / флаг `approximate`), `REPEATABLE READ`, short-circuit пустого key-set, `merge_results` — детерминированный код; лимиты прогона: `deadline 90 s / statement_timeout 30 s / max_sql_executions 4` | P1 (на стенде `plan_query` — заглушка «не декомпозировать») |
| FR-13 | Кэш вопросов (Valkey): точное совпадение нормализованного вопроса → готовый SQL; **кэш не обходит гейт (S7):** ключ `rights_hash + graph_version + assumptions`, кэшируется SQL, не результат; на hit SQL проходит `validate_sql` + ACL против текущих прав + `EXPLAIN`; namespace'ы few-shot/глоссария по ролям; кэш справочных шагов декомпозиции с TTL; семантическая близость исключена (ADR-009 v1.2) | P1 |
| FR-14 | Бюджет: кап 2 ₽ на запрос с резервом 0,6 ₽ под `interpret_result`; проверка остатка перед каждой эскалацией; при исчерпании — остановка с частичным ответом (incomplete-флаг, валидный исход) | P0 |

## 5. Нефункциональные требования

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-1 | Латентность | p95 < 20s; TTFT ≤ 3s (контроль «инфраструктурного налога» на дешёвых узлах) |
| NFR-2 | Стоимость | средний запрос ≤ 0,7 ₽ (зафиксированный расчёт — ADR-007 §4.3); кап 2 ₽ с резервом 0,6 ₽ (NFR связан с FR-14) |
| NFR-3 | Безопасность исполнения | только `SELECT`; read-only роль `agent_ro` — единственный канал пользовательских SQL (timeout 30s, `LIMIT 1000`, `EXPLAIN ANALYZE` запрещён); RLS + `SET LOCAL app.user_id`, раздельные коннекты планировщик/исполнитель; запись трейса — отдельный INSERT-only канал `agent_trace` (append-only: без SELECT/UPDATE/DELETE); one-time hardening сервисной роли (запрет `dblink`/`pg_read_file`) |
| NFR-4 | Граница прав | недоступная таблица не существует в версии реальности агента (подграф, RAG, DDL); **ACL-leak = 0** (hard gate §6); 0 утечек через кэш (ключ с правами и `graph_version`) |
| NFR-5 | Скорость изменения прав | `UPDATE` строки → действует со следующего запроса, без деплоя и DDL |
| NFR-6 | Качество | success rate ≥ 80%; точность пути джойна ≥ 85%; join-correctness по `edge_id` ≥ 85% (eval-сет атрибуции) |
| NFR-7 | Воспроизводимость | смена модели/провайдера — конфиг (OpenAI-совместимый шлюз), не код; все прогоны трассируются с `graph_version` |
| NFR-8 | Отказы | dead loop исключён двумя уровнями код-лимитов (per-node счётчики + `recursion_limit`); HTTP 429 → backoff 1→2→4с; circuit breaker: 5 сбоев → пауза 60с, завершается деградацией (валидный SQL без объяснения / отложенная задача) |

## 6. Критерии приёмки

**Сцены (функциональная приёмка):**

1. **Кейс закрыт полностью:** вопрос → SQL → выполнение → объяснение; ответ несёт SQL, допущения, стоимость, флаги усечения/`approximate`.
2. **Сцена RBAC №1 (допуск):** Boris (logistics + hr) получает кросс-доменный ответ «кто выполнил план и не был премирован» с `LEFT JOIN ... IS NULL` из семантики ребра.
3. **Сцена RBAC №2 (deny):** Anna (только logistics) спрашивает про премии → деградация: «Данные о премиях доступны только роли HR. Могу показать…» — без раскрытия чужой схемы и без подтверждения существования данных.
4. **Сцена качества:** вопрос с неоднозначной атрибуцией («пришли из рекламы») → допущение first-touch из `usage_notes` зафиксировано и раскрыто в ответе.
5. **Сцена надёжности:** невалидный SQL → `diagnose_error` → retry по политике M1 (≤ 3 попыток на узел); DDL/DML-инъекция → отказ на валидаторе, выполнение не состоялось.
6. **Сцена декомпозиции:** джойн 5 таблиц → T1 → QueryPlan из 3 шагов → key-set exchange с bind-параметрами → `merge_results` кодом; пустой промежуточный key-set → честное «данных нет» без выполнения зависимых шагов.
7. **Экономика:** типовой запрос ≤ 0,7 ₽ (зафиксированный расчёт ADR-007), трейс содержит стоимость и `graph_version`.

**Eval-критерии (N4; CI-гейт: не мержить при ACL-leak > 0 или падении accuracy на −3 п.п.):**

| Метрика | Порог/цель |
|---|---|
| **ACL-leak (попытка доступа вне прав)** | **= 0 — hard gate** |
| Execution accuracy | ≥ 80% (рост с базлайна) |
| Join-correctness (правильное ребро по `edge_id`) | ≥ 85% |
| Fan-out-агрегаты (двойной счёт) | 0 случаев на eval-сете агрегатов |
| Честные отказы (права/нет пути/бюджет) | формулировка бизнес-понятиями, без раскрытия схемы; отказы не хуже 100% корректных формулировок |
| Точность уточнений (`clarify`) | ответ на уточнение снимает неоднозначность в ≥ 90% |
| p95 latency / TTFT | < 20s / ≤ 3s |
| ₽/запрос | ≤ 0,7 ₽ средний, кап 2 ₽ |
| Доля эскалаций | план-узлы < 10% |
| Покрытие реестра | доля вопросов с активным путём; time-to-edge — рост от старта |
| Red-team: injection в вопросе/данных/RAG/`usage_notes` | 0 исполнений; блокировка + аудит |

## 8. Допущения и зависимости

- **Аутентификация вне агента:** MVP — `DevTokenAuth` (токен/выбор пользователя в Streamlit); production — OIDC-адаптер. Голый `user_id` параметром — не identity.
- **Модели — каталог routerai.ru, снимок 18.11.2026** (618 моделей, имена проверены); тарифы плавают — расчёт зафиксирован по снимку с датой (D-017, Q7 default `TODO(confirm)`); методика расчёта важнее цифр; смена модели — параметр вызова.
- **Контексты 1М у всех трёх моделей**; тариф qwen двухуровневый, запросы агента ≤ 6,6К токенов — всегда дешёвый уровень.
- **Целевой масштаб (Q1 `TODO(confirm)`):** сотни таблиц, тысячи связей, несколько доменов; демо-схема 7 таблиц — отладочный стенд.
- **SAP в скоупе (Q2 `TODO(confirm)`):** да, как один из ландшафтов → реестр — SoT, FK — только bootstrap-кандидаты, пример ребра с `MANDT`.
- **Отказ не раскрывает существование данных (Q3 `TODO(confirm)`):** формулировка бизнес-понятиями без имён таблиц + доступная альтернатива.
- **Кап 2 ₽ (Q4 `TODO(confirm)`):** оставлен, с резервом 0,6 ₽ под `interpret_result`.
- **Политика ретраев M1 (Q6):** принята — D-016 (экономика сходится именно на дешёвом retry). **Стек (Q5):** вопрос снят — чистый Python (D-017).
- **Пороги T1/T2 и кап кардинальности (50 000 ключей)** — начальные: единицы EXPLAIN-cost зависят от железа и статистики БД, калибруются на eval-сете (открытый вопрос №3).
- **Граф — Neo4j** (D-013, ADR-003 v2.0): PG — хранилище истины, граф — производный снапшот реестра с `graph_version`; хранилище — заменяемая деталь за `find_join_paths()` (D-015); синк по `settings_version` + reconciliation-тест — ADR-006 §4.3.
- **Eval-сет «вопрос → эталонный SQL / путь / ребро»** — общий фундамент калибровки (open #2), до него метрики качества — целевые, не измеренные.
- **Прод-сцена — внешний источник SAP** (OAuth-вход пользователя; в HTTPS-ручку уходит формализованная спека запроса — QuerySpec, ручка на ABAP строит Open SQL и проверяет права): архитектура обязана допускать подключение с минимальными усилиями — внешний datasource за портами `AuthProvider`/`SQLExecutor`, права арбитрит SAP (ADR-011); реализация — после v1 (hw-plan §7).
