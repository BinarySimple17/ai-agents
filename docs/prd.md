## 1. Проблема и ценность

Доступ к данным идёт через ручные SQL-запросы: аналитик пишет каждый запрос руками,
бизнес ждёт часы на вопрос, который сводится к одному SELECT с парой JOIN. Помимо
скорости есть вторая проблема — доступ: разные пользователи имеют право видеть разные
данные, и ручной SQL никак это не контролирует (кто умеет писать запросы — тот видит всё).

Агент принимает вопрос на естественном языке, строит SQL по графу связей схемы,
безопасно выполняет его под правами пользователя и объясняет результат на языке бизнеса.

| Поток | Ценность |
|---|---|
| V1 Скорость | Типовой вопрос — минуты вместо часов; не нужен SQL-навык |
| V2 Доступ как настройка | Права меняются `UPDATE`-ом строки (без деплоя и DDL) и действуют со следующего запроса |
| V3 Бизнес-корректность | Джойны и атрибуция — по семантике рёбер, внесённой владельцем данных; цифры не «какие-то», а правильные |
| V4 Предсказуемость | Каждый ответ снабжён SQL, допущениями и стоимостью; отказ по правам честный и формулируется бизнес-понятиями |
| V5 Проверяемость | Валидация до выполнения; трейс каждого прогона; оценка стоимости запроса в рублях |

## 2. Пользователи

| Роль | Главный сценарий | Что получает |
|---|---|---|
| Аналитик (основной пользователь) | «Сколько новых клиентов из Германии пришло из рекламных кампаний в октябре, и их средняя выручка?» | Ответ: текст + SQL + допущения + стоимость; при неоднозначности — один уточняющий вопрос |
| Аналитик с правами нескольких доменов | «Кто из менеджеров выполнил план по отгрузкам и не был премирован?» | Кросс-доменный джойн в рамках своих прав (отгрузки → сотрудники → премии) |
| Владелец данных | Ведёт связи и права своего домена | `agent_relationships` и `agent_permissions` как настройки: вносит бизнес-рёбра и меняет права без разработчика |
| Администратор платформы | Контроль качества и бюджета | Трейс прогонов, метрики (§8 README), стоимость запросов, аудит отказов по правам |

## 3. Цели и не-цели

**Цели (v1, учебный проект):** работающий контур «вопрос → SQL → безопасное выполнение →
объяснение» на демо-схеме из 7 таблиц (`customers`, `orders`, `order_items`, `products`,
`campaigns`, `employees`, `bonuses`); RBAC как настройки в БД; семантика связей владельцев
данных; декомпозиция тяжёлых запросов; каскад моделей с экономикой ≤ 0,7 ₽ на запрос;
трейс каждого прогона.

**Не-цели:**

- аутентификация внутри агента (SSO/IdP — задача фронта; агент — resource server за портом `AuthProvider`);
- запись в БД (только `SELECT`; read-only роль — единственный канал исполнения);
- row-level security и федерация второй БД (следующая ступень, §8 README — архитектура готова, не сейчас);
- история диалога / мультиходовость («одиночный вопрос → ответ»);
- собственное обучение моделей и редактирование прав агентом;
- мини-UI владельцев данных для прав и связей (открытый вопрос §8 README, v1 — SQL-настройки).

## 4. Функциональные требования

Приоритеты: **P0** — ядро контура, без него сценарий не работает; **P1** — реализуется
в рамках проекта (есть план Б: заглушка, прозрачная для архитектуры).

| ID | Требование | Приоритет |
|---|---|---|
| FR-1 | Принимать бизнес-вопрос на естественном языке; возвращать ответ: текст + SQL + список допущений + стоимость | P0 |
| FR-2 | Строить SQL только по плану: `plan_joins` находит путь джойна по графу связей (`shortestPath`), модель ходит только по реальным рёбрам — соединить таблицы по несуществующей связи физически не может; SQL не пишется без JoinPlan | P0 |
| FR-3 | Неоднозначные формулировки: **один** уточняющий вопрос и остановка, или явная фиксация допущений; бизнес-глоссарий («выручка» = `SUM(orders.total)`) в векторной памяти | P0 |
| FR-4 | Валидация **до** выполнения: AST-обход (sqlglot) + проверка джойнов по графу + ACL; текст от LLM — не доверенный; DDL/DML отказываются на уровне Rules + AST-whitelist + read-only роли | P0 |
| FR-5 | Различение исходов валидации: таблица не существует → галлюцинация → `diagnose_error` (retry); существует, но вне прав → `degrade` (без retry, сигнал безопасности) | P0 |
| FR-6 | RBAC: права как настройки (`agent_permissions`: роль → таблица → колонки; `agent_user_roles`); аутентификация за портом `AuthProvider` (MVP — `DevTokenAuth`); три рубежа (фильтрация мира → AST-валидатор → coarse БД); деградация вместо отказа с формулировкой через бизнес-понятия | P0 |
| FR-7 | Семантика связей: `agent_relationships` (`kind` fk\|business, `meaning`, `join_type`, `usage_notes`); FK-рёбра вычитываются из каталога автоматически, бизнес-рёбра вносит владелец данных; `join_type` берётся из плана, модель не решает сама; допущения из `usage_notes` раскрываются в ответе | P0 |
| FR-8 | Каскад моделей: Intent-Based Routing «узел → навык → модель» (cheap/mid/strong за одним OpenAI-совместимым шлюзом); эскалация на уровень вверх при провале генерирующих узлов (plan_joins, generate_sql, plan_query, шаги декомпозиции) — назначает код по факту провала валидации, retry-бюджет общий ≤ 3; reasoning-режим адресно | P0 |
| FR-9 | Принудительные форматы: все структурированные выходы (`Clarification`, `JoinPlan`, `QueryPlan`, диагностика) — валидный JSON по схеме; constrained decoding где доступно, тул-based enforcement где нет | P0 |
| FR-10 | Самокоррекция: `diagnose_error → generate_sql`; невалидный JoinPlan → retry `plan_joins` с эскалацией (валидация плана — код при парсинге); retry-бюджет ≤ 3 общий, задаётся кодом (dead loop исключён) | P0 |
| FR-11 | Наблюдаемость: трейс каждого прогона — вопрос, допущения, план, SQL (шагов), retry_count, latency, TTFT, стоимость (итог + по узлам), cache hit; структурные логи с trace_id; live-метрики и спаны — Prometheus/Grafana через OTel (ADR-010), аналитические отчёты — из query_trace (observability.md); основа eval-сета | P0 |
| FR-12 | Декомпозиция тяжёлых запросов (аналог FOR ALL ENTRIES): триггеры T1 (структурный, ≥ 4 таблиц / ≥ 3 хопов) и T2 (EXPLAIN-cost), `plan_query` строит QueryPlan DAG (≤ 4 шагов, ≤ 3 таблиц), bind-параметры `= ANY(:keys)`, чанки 1000, кап key-set 5000, `REPEATABLE READ`, short-circuit пустого key-set, merge — детерминированный код | P1 (заглушка `plan_query` — план Б) |
| FR-13 | Кэш вопросов (Valkey): точное совпадение нормализованного вопроса → готовый SQL, ключ (scope, вопрос), namespace'ы few-shot/глоссария по ролям; кэш справочных шагов декомпозиции с TTL; семантическая близость исключена (решение владельца, ADR-009 v1.2) | P1 |
| FR-14 | Бюджет: жёсткий кап 2 ₽ на запрос пользователя; при исчерпании — остановка с частичным ответом | P0 |

## 5. Нефункциональные требования

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-1 | Латентность | p95 < 20s; TTFT ≤ 3s (контроль «инфраструктурного налога» на дешёвых узлах) |
| NFR-2 | Стоимость | средний запрос ≤ 0,7 ₽; жёсткий кап 2 ₽ (NFR связан с FR-14) |
| NFR-3 | Безопасность исполнения | только `SELECT`; read-only роль `agent_ro` — единственный канал пользовательских SQL (timeout 30s, `LIMIT 1000`, `EXPLAIN ANALYZE` запрещён); запись трейса — отдельный INSERT-only канал `agent_trace` (append-only: без SELECT/UPDATE/DELETE); one-time hardening сервисной роли (запрет `dblink`/`pg_read_file`) |
| NFR-4 | Граница прав | недоступная таблица не существует в версии реальности агента (подграф, RAG, DDL); 0 утечек через кэш (ключ со scope) |
| NFR-5 | Скорость изменения прав | `UPDATE` строки → действует со следующего запроса, без деплоя и DDL |
| NFR-6 | Качество | success rate ≥ 80%; точность пути джойна ≥ 85%; join semantics accuracy ≥ 85% (eval-сет атрибуции) |
| NFR-7 | Воспроизводимость | смена модели/провайдера — конфиг (OpenAI-совместимый шлюз), не код; все прогоны трассируются |
| NFR-8 | Отказы | dead loop исключён код-лимитами; HTTP 429 → backoff 1→2→4с; circuit breaker: 5 сбоев → пауза 60с |

## 6. Критерии приёмки

1. **Кейс закрыт полностью:** вопрос → SQL → выполнение → объяснение; ответ несёт SQL, допущения, стоимость.
2. **Сцена RBAC №1 (допуск):** Boris (logistics + hr) получает кросс-доменный ответ «кто выполнил план и не был премирован» с `LEFT JOIN ... IS NULL` из семантики ребра.
3. **Сцена RBAC №2 (deny):** Anna (только logistics) спрашивает про премии → деградация: «Данные о премиях доступны только роли HR. Могу показать…» — без раскрытия чужой схемы.
4. **Сцена качества:** вопрос с неоднозначной атрибуцией («пришли из рекламы») → допущение first-touch из `usage_notes` зафиксировано и раскрыто в ответе.
5. **Сцена надёжности:** невалидный SQL → `diagnose_error` → retry ≤ 3; DDL/DML-инъекция → отказ на валидаторе, выполнение не состоялось.
6. **Сцена декомпозиции:** джойн 5 таблиц → T1 → QueryPlan из 3 шагов → key-set exchange с bind-параметрами → merge кодом; пустой промежуточный key-set → честное «данных нет» без выполнения зависимых шагов.
7. **Экономика:** типовой запрос ≤ 0,7 ₽ (расчёт в ADR-007), трейс содержит стоимость.

## 8. Допущения и зависимости

- **Аутентификация вне агента:** MVP — `DevTokenAuth` (токен/выбор пользователя в Streamlit); production — OIDC-адаптер. Голый `user_id` параметром — не identity.
- **Модели — каталог routerai.ru** на момент расчёта (608 моделей, цены в ₽/1М); цены плавают — методика расчёта важнее цифр; смена модели — параметр вызова.
- **Контексты 1М у всех трёх моделей**; тариф qwen двухуровневый, агент всегда в дешёвом уровне (~3К токенов).
- **Пороги T1/T2 и `max_keys`** — начальные: единицы EXPLAIN-cost зависят от железа и статистики БД, калибруются на eval-сете (открытый вопрос №3).
- **Граф — Neo4j** (решение владельца после аудита, ADR-003 v2.0): PG — хранилище
  истины, топология графа — производная (синк по `settings_version` +
  reconciliation-тест — ADR-006 §4); официальный образ pgvector вместо кастомной
  сборки AGE+pgvector.
- **Eval-сет «вопрос → эталонный SQL / путь / ребро»** — общий фундамент калибровки (open #2), до него метрики качества — целевые, не измеренные.
- **Прод-сцена — внешний источник SAP** (OAuth-вход пользователя; в HTTPS-ручку уходит формализованная спека запроса — QuerySpec, ручка на ABAP строит Open SQL и проверяет права): архитектура обязана допускать подключение с минимальными усилиями — внешний datasource за портами `AuthProvider`/`SQLExecutor`, права арбитрит SAP (ADR-011); реализация — после v1 (hw-plan §7).
