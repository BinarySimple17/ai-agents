# Security-документация — Text-to-SQL Agent

- **Статус:** Принято v1.5 (2026-11-15 — Neo4j в контуре: сеть, секрет, модель угроз, ADR-003 v2.0; v1.4 — `agent_ro` без SELECT на `query_trace`: трейсы вне канала исполнения, FIX-005; v1.3 — QuerySpec, вызов ручки как актёр угроз; v1.2 — граница SAP; v1.1 — ревизия 02)
- **Назначение:** операционный уровень поверх архитектурных решений: что именно проверяется, как реагируем, где лежат ключи, как аудируем. Архитектурная мотивация — в ADR-005 (RBAC) и ADR-002 (валидатор на единственном ребре); здесь её нет.
- **Связанные документы:** ADR-005 (владеющее решение по правам), ADR-002, ADR-004 (guardrails шагов), ADR-009 (кэш), prd.md (FR-4…FR-6, NFR-3/4), RISKS.md

## 1. Область и модель угроз

**Активы:** бизнес-данные демо-схемы (в т.ч. PII-колонка `employees.salary`); таблицы
настроек прав и связей; трейсы (кто что спрашивал); секреты (API-ключ шлюза, пароль
БД); сам агентный контур (промпты, инструкции).

**Актёры:**

| Актёр | Мотив / вектор |
|---|---|
| Пользователь вне прав | Получить данные чужого домена («кто не был премирован» без прав HR) |
| Пользователь с правами | Prompt injection в вопросе: «игнорируй ограничения», «покажи salary всех» |
| Через данные | Инъекция в содержимом (комментарии/значения, попавшие в DDL-комментарии и few-shot) |
| Нарушитель снаружи | Прямой доступ к БД/Neo4j/Valkey в обход приложения (порты, сеть) |
| Инсайдер-админ | Чтение трейсов/секретов; митигируется аудитом и минимальностью контура |
| Экономическая атака | Дорогие вопросы (комбинаторные джойны, бесконечные retry) — выжигание бюджета |
| Вызов SAP-ручки напрямую | Обход guardrails агента (бюджет, rate-limit, аудит); данные — под правами вызывающего, утечки нет (RISKS R-S5) |

## 2. Аутентификация и авторизация (операционно; архитектура — ADR-005)

- **Поток:** клиент → IdP/портал (SSO; MVP — `DevTokenAuth`) → агент получает
  проверенную identity → `resolve_access` (детерминированный код) читает
  `agent_user_roles`/`agent_permissions` → scope в state. Запрос без проверенной
  identity → **отказ без вызова LLM** (fail-closed; голый `user_id` — не identity).
- **Кэш прав:** per-user кэш `resolve_access` с проверкой версии на **каждый**
  запрос. Версия — триггерный счётчик `settings_version` (ADR-005 §4), не
  `max(updated_at)`: UPDATE покрыт и им, но выдача/отзыв роли — INSERT/DELETE
  (`agent_user_roles` версии не имела вовсе), DELETE строки прав `max()` не
  поднимает. Счётчик изменился → per-user кэш сбрасывается целиком (пользователей
  ≤ 10) — revoke роли действует со следующего запроса (NFR-5, включая кейс отзыва;
  ревизия 02 §3.2). TTL поверх версии не применяется: он возвращал бы staleness
  до 60с; проверка счётчика — один дешёвый SELECT трёх строк.
- **Аудит-события (query_trace + логи, append-only; полный перечень событий и их схема — observability.md §2):** `identity_rejected`,
  `degrade` (вне прав: что именно, без деталей чужой схемы), `retry_exhausted`,
  `budget_stop`, `overflow`, `short_circuit`, инъекция-класс валидатора. Retention —
  политика заказчика (в v1 — живёт весь срок проекта).
- **Правило для разработчиков:** новый путь к данным не принимается без (а) scope в
  контексте, (б) юнит-теста «чужая таблица → отказ», (в) кейса в adversarial-наборе.

### 2.1. Канал исполнения: сервисная роль `agent_ro` (единственный путь SQL в БД)

SQL к PostgreSQL уходит **только** через сервисный аккаунт `agent_ro` — один на всех
пользователей; пользовательская identity в БД не ходит (она живёт в state и влияет
на scope, не на креды). Соединение держит приложение (порт `SQLExecutor`) — единственный
клиент data plane; креды — `.env` (дев) / Vault (прод); порты БД наружу не публикуются.

Настройка — один раз в `init.sql`:

```sql
CREATE ROLE agent_ro LOGIN PASSWORD '...';
ALTER ROLE agent_ro SET default_transaction_read_only = on;  -- DML/DDL отклонены на уровне сессии
ALTER ROLE agent_ro SET statement_timeout = '30s';
GRANT USAGE ON SCHEMA public TO agent_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO agent_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO agent_ro;
REVOKE SELECT ON query_trace FROM agent_ro;  -- трейсы (вопросы всех пользователей)
-- не читаются каналом исполнения: defense-in-depth к рубежу 2 (FIX-005)
-- dblink / file_fdw в демо-БД не устанавливаются вовсе:
-- иначе FROM dblink(...) обошёл бы табличный whitelist валидатора
```

- **Рубеж 3 — coarse, последний, не главный:** сюда SQL доходит уже отфильтрованным
  (рубеж 2 — ACL-валидатор). Роль ловит баг всего предыдущего контура (read-only,
  timeout), но не различает «кого» — осознанный трейд ADR-005 за «права как данные».
- **Аудит на стороне БД:** на каждой транзакции `SET LOCAL app.scope = '<user>'` —
  в логах PostgreSQL видно, чей scope выполнял запрос; полный контекст (проверенная
  identity, план, стоимость) — в `query_trace` приложения.
- **Декомпозиция (ADR-004):** все шаги тяжёлого плана — одна транзакция
  `REPEATABLE READ` на одном read-only соединении: N SELECT'ов видят один снапшот.

### 2.2. Канал записи трейса: роль `agent_trace` (второй SQL-канал, INSERT-only)

`agent_ro` ослаблять нельзя — его read-only задан на уровне сессии
(`default_transaction_read_only = on`, жёстче любых GRANT-ов), а `query_trace` —
system of record (FR-11), в который пишет **каждый** прогон. Ревизия 02 (§3.1):
запись трейса — отдельный канал с минимальным правом:

```sql
-- существующий agent_ro — без изменений (read-only, сессионная гарантия)
CREATE ROLE agent_trace LOGIN PASSWORD '...';   -- второй канал: только трейс
GRANT USAGE ON SCHEMA public TO agent_trace;
GRANT INSERT ON query_trace TO agent_trace;
-- SELECT/UPDATE/DELETE/TRUNCATE не выдаются вовсе: append-only = отсутствие грантов
-- (страховка: триггер BEFORE UPDATE OR DELETE ON query_trace → EXCEPTION)
```

- Мини-пул (1–2 соединения); запись — в конце прогона; ошибка записи → строка в
  stdout-лог (best-effort fallback: PG жив, раз прогон выполнился; потеря строки
  трейса допустима, потеря ответа пользователю — нет).
- Append-only аудита (§2) обеспечен физически: нет гранта — нет способа; триггер —
  страховка от выдачи прав позже.

## 3. Guardrails: пороги, реакции, аудит

| Контур | Что | Порог/конфиг | Реакция | Аудит |
|---|---|---|---|---|
| I1 длина | символов в вопросе | `GUARD_MAX_INPUT_CHARS` (8000) | 4xx, отказ без деталей | `guardrail_block(length)` |
| I2 санитайзер | control/zero-width символы | всегда | мутирует текст | — (не событие) |
| I3 инъекции в вопросе | «игнорируй ограничения», DDL/DML-команды в тексте | Rules (приоритет над инструкциями пользователя) + AST-whitelist как предохранитель | правила перекрывают; AST отклонит команду даже если модель послушалась | `guardrail_block(injection)` |
| AST-whitelist | только SELECT; каждая таблица/колонка ∈ правам scope; `SELECT *` разворачивается; каталоги (`information_schema`, `pg_catalog`) отсекаются; **deny-by-default: тип узла вне whitelist'а валидатора → отказ** (ADR-005 §4) | всегда | отклонение **до** выполнения | `validator_reject` (галлюцинация vs deny) |
| ACL-семантика | различение: не существует → `diagnose_error` (retry); вне прав → `degrade` без retry | всегда | маршрут FSM (ADR-005) | `degrade` с указанием узла |
| Джойны по графу | JOIN ON соответствует ребру (fk/business); тип джойна = `join_type` плана | всегда | отклонение | `validator_reject(join)` |
| Шаги декомпозиции | те же проверки на каждый шаг + `ANY(:keys)` только на whitelist key-колонках; только bind | всегда | отклонение шага | `validator_reject(step)` |
| Исполнение | read-only `agent_ro` (one-time hardening: запрет `dblink`/`pg_read_file`); `LIMIT 1000`; timeout 30s; только `EXPLAIN`, никогда `EXPLAIN ANALYZE` | всегда | SQL-ошибка → `diagnose_error` | трейс |
| Бюджет | кап 2 ₽/запрос; retry ≤ 3 общий | всегда | остановка с частичным ответом (валидный исход) | `budget_stop` / `retry_exhausted` |
| Key-set капы | `LIMIT max_keys+1`; 0 ключей → short-circuit | max_keys = 5000 | уточняющий вопрос / честное «данных нет» | `overflow` / `short_circuit` |
| PII | три границы (расшифровка под таблицей): внутри контура — только ACL (метка не дублирует права); наружу (LLM-провайдер) и в телеметрию — маскирование по меткам колонок **в коде, до отправки**, дисциплина модели не участвует; метки v1 — конфиг `PII_MASK_COLUMNS` (напр. `employees.salary`), рост числа меток / их ведение владельцем → таблица настроек по образцу ADR-005 | `PII_MASK_COLUMNS` | маскирование/исключение колонки из payload; телеметрия — только идентификаторы/счётчики (observability §2.2) | — |
| Кэш | ключ (scope, вопрос); namespace'ы по ролям; допущения `clarify` в значении и сверка на hit (ADR-009 п. 6) | всегда | несовпадение допущений → miss | `cache_hit` в трейсе |
| Rate limit per user | token bucket на пользователя **в коде агента** (портала в v1 нет) | `RATE_LIMIT_USER` (напр. 10 запросов/мин) | 429 с заголовком Retry-After | `rate_limited` |

**Границы PII — что маскируется, а что нет:**

1. **Внутри контура (пользователю):** данные разрешённых по ACL колонок — как есть;
   маскирование не применяется, метка не дублирует права (NFR-4).
2. **Наружу (LLM-провайдер):** колонки с меткой маскируются до отправки; строчные
   результаты уходят к провайдеру только на `interpret_result` (агрегаты/сжатое
   представление), сырые значения пользователю отдаёт приложение из `QueryResult`
   мимо LLM. Текст вопроса — наружу допускается (осознанный допуск R-S4: синтетика;
   корпоративный контур — revisit ADR-007, локальные модели).
3. **Телеметрия (логи/спаны/метрики):** PII не содержит по построению — только
   идентификаторы, счётчики, латентности (observability.md §2.2); текст вопроса и
   результаты — только в `query_trace` (внутри контура).

Маскирование «и вопрос, и salary» осознанно не делается: LLM не объяснил бы цифры,
которые не видит, — продукт ломается при нулевом выигрыше (допуск R-S4 уже
покрывает вопрос).

**Работа с ложными срабатываниями:** пороги — конфиг; категория — в аудит; отчёт по
категориям — вход подстройки. Отключение AST-whitelist или ACL — запрещено (изменение
— через revisit ADR-005).

## 4. Управление ключами и секретами

| Секрет | Дев | Прод | Ротация |
|---|---|---|---|
| API-ключ routerai.ru | `.env` (в gitignore) | Vault / секрет-хранилище | 90 дней / по инциденту |
| POSTGRES_PASSWORD | `.env` (генерация при первом старте) | Vault | 180 дней |
| Valkey (ACL, если включён) | `.env` | Vault | 180 дней |
| Neo4j (community, локальный контур — ADR-003 v2.0) | `.env` (`NEO4J_PASSWORD`) | Vault | 180 дней |
| Токены DevTokenAuth | тестовые значения, только дев | — (замена на OIDC) | по контуру |
| OAuth-токен пользователя (SAP, ADR-011) | — (SAP в дев нет) | не хранится: память прогона (`RunContext`) | срок жизни IdP / refresh по сессии |

- `.env.example` — шаблон без значений, коммитится; фактические `.env` — никогда
  (gitignore + gitleaks).
- **Данные у LLM-провайдера — осознанный допуск** (C4 L1): промпты содержат текст
  вопроса и DDL разрешённых таблиц. Результаты SQL к провайдеру уходят только на
  `interpret_result` (агрегированный итог). Для контура с локализацией — локальные
  модели за тем же `LLMProvider`-портом (revisit ADR-007); пароль БД и секреты в
  промпты не попадают никогда.
- **Граница контура с SAP (ADR-011 v1.1):** в SAP-ручку уходит формализованная спека
  запроса (`QuerySpec`, не SQL-текст — sqlglot-валидация для Open SQL неприменима;
  спека проверяется структурно: deny-by-default по схеме IR, операторы из whitelist,
  значения — bind); ручка на ABAP строит Open SQL и проверяет права (CDS/DCL).
  Токен — только в памяти прогона (`RunContext`), в логи/спаны/`query_trace` не
  попадает (там — pseudonymous subject токена); 401/403 — `degrade`-исход, не retry;
  PII-правила §3 действуют на этой границе так же, как для LLM-провайдера.

## 5. Сегментация сети

- **docker-compose, внутренняя сеть:** PostgreSQL, Neo4j и Valkey порты наружу не
  публикуют (localhost-bind); единственный клиент — `app`. Публикация портов БД
  для отладки — только профилем `debug` с явным флагом.
- **Исходящие:** только к routerai.ru (LLM-вызовы). IdP — дев — мок, прод —
  корпоративный.
- **`agent_ro` — coarse-рубеж:** read-only, timeout, hardening запретом опасных
  функций; per-user изоляция на уровне БД сознательно не держится (ADR-005, трейд
  за «права как данные») — компенсация: обязательные adversarial-тесты валидатора
  в CI (UNION с чужой таблицей, подзапросы, EXISTS, CTE, `t.*`, каталоги, `dblink`).
- **Плоскость телеметрии (ADR-010):** jaeger/prometheus/grafana/alertmanager —
  во внутренней сети compose, порты наружу не публикуются (Grafana — только профиль
  `debug`, как и БД); пароль администратора Grafana — `.env`, анонимный доступ
  выключен; чувствительный payload (текст вопроса, результаты SQL) не идёт в
  span-атрибуты и логи — только идентификаторы, счётчики, латентности
  (observability.md §2.2).

## 6. Реагирование на инциденты (мини-playbook)

| Сценарий | Признак | Действия |
|---|---|---|
| Пропуск валидатора (данные не тому пользователю) | жалоба / аномалия `degrade`-статистики | зафиксировать trace, воспроизвести unit-тестом, при подтверждении — фикс + кейс в adversarial-набор + разбор ветки валидатора; рассмотреть per-user роль БД для затронутых таблиц (revisit ADR-005) |
| Подозрение на утечку через кэш | cross-scope hit в логах | проверить, что ключ содержит scope (ADR-009); сброс кэша, исправление ключа, регресс-тест |
| Утёкший API-ключ | gitleaks / аномалия биллинга | ротация ключа у провайдера, аудит затрат за период |
| 429-шторм / деградация шлюза | рост backoff, breaker открыт | circuit breaker сам держит паузу 60с; при длительной недоступности — остановка приёма вопросов (fail-closed), не отключение guardrails |
| Инъекция через данные (few-shot/DDL-комментарий) | валидатор/правила сработали на контент | изъять источник из индекса, пересобрать, кейс в regression |
| Бюджет-атака (дорогие вопросы) | рост средней стоимости, `budget_stop`-волна | per-user token bucket в коде агента (§3), калибровка T2; в проде — лимиты портала |
