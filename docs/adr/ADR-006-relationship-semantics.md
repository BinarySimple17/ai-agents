# ADR-006: семантика связей — FK ≠ бизнес, владелец данных вносит рёбра

- **Статус:** Принято (v1.2 — 2026-11-15: граф — Neo4j вместо AGE (ADR-003 v2.0), протокол синка не меняется; v1.1 — синк по счётчику settings_version, ревизия 02)
- **Дата:** 2026-11-14
- **Контекст принятия:** запрос владельца: связи по FK верны с т.з. БД, но не всегда с т.з. бизнеса; владелец данных должен сам вносить связи между сущностями
- **Связанные документы:** prd.md (§4 FR-2, FR-7, NFR-6), ADR-002 (Reason на узле `plan_joins`), ADR-003 (FK из каталога той же БД), ADR-005 (симметрия: связи — тоже настройки)

---

## 1. Контекст

Связи по внешним ключам корректны с точки зрения БД, но вопрос пользователя — всегда
бизнес-семантика. Между «как связаны физически» и «как правильно считать» — три типа
разрыва, все присутствуют на демо-схеме:

| Разрыв | Пример | Что происходит без семантики |
|---|---|---|
| FK есть, смысл другой | «Клиенты, пришедшие из рекламы» | агент считает any-touch (клиент с хотя бы одним заказом из кампании); бизнес ждёт first-touch — первый заказ. Цифры различаются в разы, уверенно и молча |
| Нужен другой тип джойна | «Кто выполнил план и не был премирован» | `INNER JOIN bonuses` тихо теряет непремированных; нужен `LEFT JOIN ... WHERE ... IS NULL` |
| Бизнес-связи без FK | «Выручка в EUR по курсу на дату заказа»; «те же люди» customers ↔ leads по email | валидатор честно отвечает «путь не найден», хотя бизнес-связь существует |

Ни один из разрывов не исправляется «лучшей моделью»: направление, тип джойна и
условия применения связи — знания домена, которых нет ни в DDL, ни в весах LLM.
Кто обладает этим знанием — владелец данных. Вопрос: куда положить это знание и кто
его вносит.

## 2. Сравнение по осям

| Ось | A: только FK-граф | B: LLM угадывает связи | C: реестр связей — настройки, владелец вносит |
|---|---|---|---|
| Бизнес-рёбра без FK (курс на дату, по email) | недоступны | угадываются ненадёжно | **вносятся владельцем** |
| Тип джойна (inner vs left) | модель решает сама — источник «тихой» потери строк | модель решает сама | **бизнес-дефолт в ребре, модель не решает** |
| Ловушки атрибуции (first-touch vs any-touch) | негде хранить | всплывают только в ответах (unreliable) | **`usage_notes` в ребре → допущение в ответе** |
| Воспроизводимость цифр | одинаковый SQL — разные бизнес-смыслы | не гарантирована между прогонами | **ребро + допущение фиксируются в трейсе** |
| Кто отвечает за корректность | разработчик схемы | модель | **владелец данных** |
| Стоимость наполнения | нулевая | нулевая | ручной труд владельцев (удешевляется автообнаружением) |
| Инвариант «модель не придумывает связи» | да | **нет** — модель может соединить по домыслу | да — ходит только по рёбрам графа |

## 3. Рассмотренные варианты

### Вариант A — только FK-граф
Отвергнут: закрывает физическую соединимость, не закрывает ни один из трёх разрывов.
«Кто не был премирован» вернёт неверные цифры или «путь не найден» — оба исхода
подрывают доверие к агенту.

### Вариант B — LLM угадывает связи из данных/схемы
Отвергнут: ровно тот класс ошибок, от которого строится весь guardrails-контур
(модель не придумывает связи). Угадывание переносит ошибку с этапа настройки на этап
каждого запроса, где её никто не ревьюит.

### Вариант D — автогенерация семантики по логам без подтверждения
Отвергнут в чистом виде: связи из логов попадают в граф автоматически — это та же
«модель решает», только с накоплением. Принята как **режим удешевления наполнения**
внутри C: строгий процесс «предложить → человек подтвердил → ребро в настройках».

### Вариант C — реестр связей как настройки ✅ **ПРИНЯТО**

## 4. Решение

**Семантика ребра живёт в графе; связи — настройки в БД; вносит владелец данных.**
FK-рёбра вычитываются из системного каталога PostgreSQL автоматически (ADR-003 —
та же БД); бизнес-рёбра (по дате, по email, иерархии) — из таблицы настроек,
без разработчика и без деплоя. Симметрия с правами (ADR-005): и права, и связи —
данные, редактируемые владельцами, не разработчиками.

```sql
CREATE TABLE agent_relationships (
    rel_id       serial PRIMARY KEY,
    left_table   text NOT NULL,
    left_column  text NOT NULL,
    right_table  text NOT NULL,
    right_column text NOT NULL,
    kind         text NOT NULL DEFAULT 'business',  -- 'fk' | 'business'
    meaning      text NOT NULL,                     -- «заказ атрибутирован кампании»
    join_type    text NOT NULL DEFAULT 'inner',     -- бизнес-дефолт: inner | left
    usage_notes  text,                              -- ловушки и обязательные допущения
    created_by   text,
    created_at   timestamptz NOT NULL DEFAULT now(),
    UNIQUE (left_table, left_column, right_table, right_column)
);
```

**Протокол синхронизации настроек ↔ графом Neo4j (контракт, не данность).** Граф —
производная структура; после ADR-003 v2.0 дрейф «истина в PG vs производные рёбра»
стал межсистемным — контракт тем более обязательный. Контракт:

- **Neo4j хранит только топологию** (пары узлов + `rel_id`); **семантика ребра
  (`meaning`, `join_type`, `usage_notes`, `kind`) читается из PG-строк по `rel_id`
  на этапе планирования** — истина всегда в настройках, AGE не дублирует её.
- **Синк по версии:** как у прав (ADR-005 §4) — `plan_joins` читает счётчик
  `settings_version.name = 'relationships'` (триггер инкрементирует его на
  INSERT/UPDATE/DELETE строк связей) на каждый запрос; версия выросла →
  перестройка топологии рёбер Neo4j из каталога PG + настроек до выдачи пути. DELETE
  ребра поднимает счётчик — фантом в графе живёт не дольше одного запроса
  (раньше: `max(rel_id)`/`max(updated_at)` DELETE не покрывали, а в DDL
  `agent_relationships` есть только `created_at` — ловил только
  reconciliation-тест в CI; ревизия 02 §3.2).
- **Reconciliation-тест в CI:** «строки настроек (+ FK каталога) = рёбра графа» —
  расхождение в любую сторону красное. Без него дрейф = несуществующий путь
  («путь не найден» при живом ребре) или ребро без семантики → неверный `join_type`.

Пример ребра «пришли из рекламы»:

| Поле ребра | Значение |
|---|---|
| связь | `orders.campaign_id → campaigns.campaign_id`, kind = fk |
| meaning | «заказ атрибутирован кампании» |
| join_type | inner |
| usage_notes | «'пришли из рекламы' = first-touch: первый заказ клиента из ads-кампании; any-touch завышает цифру; campaign_id надёжен с 2026-03» |

**Изменения по узлам:** `plan_joins` — shortestPath возвращает топологию + `rel_id`,
семантика (`meaning`, `join_type`, `usage_notes`) читается из PG-строк (протокол §4);
несколько рёбер между таблицами → Reason «какое соответствует вопросу», неоднозначная
атрибуция → уточнение через `clarify`. `generate_sql` — `join_type` берётся из плана,
модель не решает сама; `usage_notes` входят в контекст как обязательные допущения.
`validate_sql` — JOIN ON соответствует ребру любого типа; тип джойна в SQL совпадает
с `join_type` плана (INNER там, где план сказал LEFT — нарушение до выполнения).
`interpret_result` — раскрывает допущение из `usage_notes`: «посчитано по любому
заказу из кампании; при first-touch цифра другая».

Главный инвариант сохраняется: **модель по-прежнему не может придумать связь — она
ходит только по рёбрам графа.** Меняется то, что рёбер больше, чем FK, и каждое
несёт смысл.

## 5. Последствия

**Положительные:**
- Три разрыва закрыты явно: атрибуция — в `usage_notes`, тип джойна — бизнес-дефолт
  в ребре, бизнес-связи без FK — вносятся владельцем.
- Ответы бизнес-корректны и воспроизводимы: ребро + допущение фиксируются в трейсе;
  качество меряется (join semantics accuracy ≥ 85% на eval-сете атрибуции).
- Знание домена живёт у владельца данных и меняется без разработчика.

**Отрицательные / риски:**
- **Семантический слой — ручной труд**: сложность переносится из разработки в
  domain-настройку — осознанная цена; удешевляется автообнаружением кандидатов из
  успешных SQL (строгий режим «предложить → подтвердил»).
- **Граф — производная структура (с ADR-003 v2.0 — в отдельной СУБД):** дрейф
  настроек ↔ рёбра возможен. Закрыто протоколом §4: истина в PG-строках (Neo4j —
  только топология), синк по версии, reconciliation-тест в CI.
- Конфликт ребра с грязными данными (campaign_id надёжен только с 2026-03)
  фиксируется в `usage_notes`, а не правкой данных — ловушка остаётся видимой.
- Пропуск владельцем нужного ребра → «путь не найден» + уточняющий вопрос: честный
  отказ предпочтительнее домысла.

**Критерии пересмотра решения (revisit triggers):**
- Наполнение связей становится бутылочным горлом (много доменов, мало владельцев) →
  усилить автообнаружение: ранжирование кандидатов по частоте использования в
  успешных прогонах, батч-подтверждение владельцем.
- Появляется требование «время-зависимых» связей (курс на дату заказа с таблицей
  курсов) → расширение `join_type` условным джойном (temporal join) — правка
  ребра/планировщика, не принципа.
- Eval-сет покажет систематические ошибки выбора ребра → пересмотреть подсказку
  `meaning` в промпте `plan_joins` (подсказку — да, свободу — нет).
