# ADR-006: семантика связей — реестр — единственный источник истины, владелец данных вносит рёбра

- **Статус:** Принято (v1.6 — 2026-11-25, re-review S31 fix-волна 4: критерий произведения функциональный — равенство обязано связывать присоединяемый источник с уже присоединёнными и стоять в конъюнктивном скелете ON (равенство «чужих» источников, OR TRUE/OR-ветки/CASE связь не утверждают); v1.5 — 2026-11-25, re-review fix-волны 2–3: честная граница инварианта — сверка пар JOIN + корреляций + fail-closed несверяемых форм; semi-join/скалярный подзапрос без корреляции вне сверки BY DESIGN (BL-045); v1.4 — 2026-11-25, S31: инвариант реестра — обоих контуров (тул-контур сверяет пары JOIN с `join_edges`); v1.3 — 2026-11-18, отработка ревью-03 R1–R7: реестр — единственный SoT, FK — только генератор кандидатов в очередь владельцу; полный контракт ребра + жизненный цикл `draft → CI → active`; `graph_version` пинится на прогон; заявки `agent_edge_proposals`; bootstrap и cold start. v1.2 — граф — Neo4j вместо AGE (ADR-003 v2.0), протокол синка не меняется; v1.1 — синк по счётчику settings_version, ревизия 02)
- **Дата:** 2026-11-14
- **Контекст принятия:** запрос владельца: связи по FK верны с т.з. БД, но не всегда с т.з. бизнеса; владелец данных должен сам вносить связи между сущностями. Ревизия v1.3 — ревью-03 (принцип 1 и R1–R7) подняло ставку: FK перестаёт быть вторым источником рёбер
- **Связанные документы:** prd.md (§4 FR-2, FR-7, NFR-6), ADR-002 (Reason на узле `plan_joins`), ADR-003 (граф — производный снапшот реестра), ADR-004 (fanout_guard и предагрегация — вместе), ADR-005 (симметрия: связи — тоже настройки)

## 1. Контекст

Связи по внешним ключам корректны с точки зрения БД, но вопрос пользователя — всегда
бизнес-семантика. Между «как связаны физически» и «как правильно считать» — три типа
разрыва, все присутствуют на демо-схеме:

| Разрыв | Пример | Что происходит без семантики |
|---|---|---|
| FK есть, смысл другой | «Клиенты, пришедшие из рекламы» | агент считает any-touch (клиент с хотя бы одним заказом из кампании); бизнес ждёт first-touch — первый заказ. Цифры различаются в разы, уверенно и молча |
| Нужен другой тип джойна | «Кто выполнил план и не был премирован» | `INNER JOIN bonuses` тихо теряет непремированных; нужен `LEFT JOIN ... WHERE ... IS NULL` |
| Бизнес-связи без FK | «Выручка в EUR по курсу на дату заказа»; «те же люди» customers ↔ leads по email | валидатор честно отвечает «путь не найден», хотя бизнес-связь существует |

Ни один из разрывов не исправляется «лучшей моделью»: направление, тип джойна и
условия применения связи — знания домена, которых нет ни в DDL, ни в весах LLM.
Кто обладает этим знанием — владелец данных. Вопрос: куда положить это знание и кто
его вносит.

## 2. Сравнение по осям

| Ось | A: только FK-граф | B: LLM угадывает связи | C: реестр связей — настройки, владелец вносит |
|---|---|---|---|
| Бизнес-рёбра без FK (курс на дату, по email) | недоступны | угадываются ненадёжно | **вносятся владельцем** |
| Тип джойна (inner vs left) | модель решает сама — источник «тихой» потери строк | модель решает сама | **бизнес-дефолт в ребре, модель не решает** |
| Ловушки атрибуции (first-touch vs any-touch) | негде хранить | всплывают только в ответах (unreliable) | **`usage_notes` в ребре → допущение в ответе** |
| Воспроизводимость цифр | одинаковый SQL — разные бизнес-смыслы | не гарантирована между прогонами | **ребро + допущение фиксируются в трейсе** |
| Кто отвечает за корректность | разработчик схемы | модель | **владелец данных** |
| Стоимость наполнения | нулевая | нулевая | ручной труд владельцев (удешевляется bootstrap: FK + майнинг как кандидаты) |
| Инвариант «модель не придумывает связи» | да | **нет** — модель может соединить по домыслу | да — ходит только по рёбрам графа |

## 3. Рассмотренные варианты

### Вариант A — только FK-граф
Отвергнут: закрывает физическую соединимость, не закрывает ни один из трёх разрывов.
«Кто не был премирован» вернёт неверные цифры или «путь не найден» — оба исхода
подрывают доверие к агенту.

### Вариант B — LLM угадывает связи из данных/схемы
Отвергнут: ровно тот класс ошибок, от которого строится весь guardrails-контур
(модель не придумывает связи). Угадывание переносит ошибку с этапа настройки на этап
каждого запроса, где её никто не ревьюит.

### Вариант D — автогенерация семантики по логам без подтверждения
Отвергнут в чистом виде: связи из логов попадают в граф автоматически — это та же
«модель решает», только с накоплением. Принята как **режим удешевления наполнения**
внутри C: строгий процесс «предложить → человек подтвердил → ребро в настройках».

### Вариант C — реестр связей как настройки ✅ **ПРИНЯТО**

## 4. Решение

**Единственный источник истины по связям — реестр `agent_relationships`, который
ведёт владелец данных. FK — не ребро, а генератор кандидатов в очередь владельцу:
технически корректный джойн не обязан быть бизнес-верным.** Симметрия с правами
(ADR-005): и права, и связи — данные, редактируемые владельцами, не разработчиками.

**Мультиграф, не дерево.** Между парой таблиц может быть несколько активных рёбер
с разной семантикой, поэтому кратчайший путь не годится как решающее правило
планировщика: код строит k взвешенных путей с фильтрацией по свойствам рёбер
(`intent_tags`, `temporal`), модель ранжирует топ-5, при равных кандидатах —
уточнение через `clarify` (ADR-003). `shortestPath` — имя функции хранилища, не
решающее правило.

### 4.1 Контракт ребра (единственный DDL-источник для диаграмм и миграций)

```sql
CREATE TABLE agent_relationships (
    edge_id       text PRIMARY KEY,               -- адресация в плане, валидаторе и аудите
    version       integer NOT NULL DEFAULT 1,     -- ревизия ребра (правка = +1, не DELETE)
    status        text NOT NULL DEFAULT 'draft',  -- draft | active | deprecated
    replaced_by   text REFERENCES agent_relationships(edge_id),  -- устаревание вместо удаления
    left_table    text NOT NULL,
    left_columns  text[] NOT NULL,                -- составные ключи
    right_table   text NOT NULL,
    right_columns text[] NOT NULL,
    join_operator text NOT NULL DEFAULT '=',
    join_type     text NOT NULL DEFAULT 'inner',  -- inner | left; бизнес-дефолт, модель не решает
    cardinality   text NOT NULL,                  -- 1:1 | 1:n | n:1 | n:m
    fanout_guard  boolean NOT NULL DEFAULT false, -- агрегация поверх ребра требует предагрегации (ADR-004)
    mandatory_predicates jsonb NOT NULL DEFAULT '{}',  -- MANDT, языковой ключ, deleted=false, tenant
    temporal      jsonb,                          -- «на дату заказа» vs «на сегодня»
    meaning       text NOT NULL,                  -- что связь значит бизнесу
    intent_tags   text[] NOT NULL DEFAULT '{}',   -- выбор между параллельными рёбрами
    usage_notes   text,                           -- ловушки; входят в ответ как допущения
    weight        numeric NOT NULL DEFAULT 1.0,   -- ранжирование путей
    domain        text NOT NULL,                  -- доменная нарезка
    owner         text NOT NULL,                  -- ответственность
    reviewed_at   timestamptz,                    -- дата последнего ревью владельцем
    ci_report     jsonb,                          -- протокол последнего CI-прогона ребра
    created_at    timestamptz NOT NULL DEFAULT now()
);
```

### 4.2 Жизненный цикл: `draft → CI → active`

Агент читает только `active` — через вьюху (`CREATE VIEW agent_relationships_active
AS SELECT ... WHERE status = 'active'`); `draft` для агента не существует.
CI-гейт активации проверяет **по факту**, а не по заявлению владельца: колонки
существуют, типы совместимы, ключ реально уникален (или измерена доля сирот),
**измеренный fan-out против заявленной `cardinality`** — расхождение в любую
сторону → ребро не активируется (CI заодно ловит дрейф схемы). Устаревшее ребро —
`status = deprecated` + `replaced_by`, история и аудит сохраняются; DELETE не
используется.

**Запись — только владелец через ревью; агент строго read-only** (иначе агент
«подарит» себе ребро в запрещённую таблицу). Все изменения реестра — в аудит.

### 4.3 `graph_version`: снапшот пинится на прогон

Граф (Neo4j, ADR-003) — **производный снапшот реестра**: детерминированный ETL
«строки реестра `active` → рёбра графа». Ревизия снапшота — `graph_version`;
`resolve_access` пинит её на прогон в state, ключ кэша и запись аудита включают
`graph_version` — иначе кэш отдаст SQL, построенный по переопределённому ребру.
Триггер перестройки — счётчик `settings_version.name = 'relationships'` (ADR-005 §4,
INSERT/UPDATE/DELETE покрыты); `graph_version` — производная ревизии реестра, а не
дубль `settings_version`: первый пинит снапшот на прогон, второй будит синк.
Reconciliation-тест в CI сохраняется: «активные строки реестра = рёбра графа» —
расхождение в любую сторону красное (дрейф = «путь не найден» при живом ребре или
ребро без семантики → неверный `join_type`).

### 4.4 Заявки на рёбра: `agent_edge_proposals`

«Нет активного пути» — не только отказ, но и заявка владельцу:

```sql
CREATE TABLE agent_edge_proposals (
    proposal_id    serial PRIMARY KEY,
    left_table     text NOT NULL,
    right_table    text NOT NULL,
    question_sample text NOT NULL,   -- пример вопроса без активного пути
    hits           integer NOT NULL DEFAULT 1,  -- частота (ранжирует очередь владельцу)
    status         text NOT NULL DEFAULT 'open', -- open | accepted | rejected
    created_at     timestamptz NOT NULL DEFAULT now()
);
```

Подтвердит владелец — следующий такой вопрос уже отвечается; агент по-прежнему не
пишет в реестр, только в очередь заявок.

### 4.5 Bootstrap и cold start

Кандидаты рёбер — из двух источников, оба только **в очередь владельцу**: FK
(каталог — генератор кандидатов) и майнинг SQL аналитиков и BI-вьюх (там зашиты
верные джойны). Для кросс-доменных рёбер арбитр — data steward, иначе самые ценные
связи никто не подтверждает. **Cold start — честно:** пока реестр пуст, агент
бесполезен; метрика №1 старта — доля вопросов с активным путём и time-to-edge
(SLA владельца). Владелец — организационное узкое место: сломанное ребро →
`degrade` + заявка, не retry с перегенерацией.

### 4.6 Fan-out и защита агрегатов (вместе с ADR-004)

`orders JOIN order_items` + `SUM(orders.total)` удваивает выручку — самый частый
класс тихих ошибок Text-to-SQL. `cardinality` + `fanout_guard` в ребре дают
планировщику формальное основание: агрегация поверх fan-out ребра без предагрегации
в CTE не пропускается (инвариант `plan_joins`/`validate_sql`, декомпозиция — ADR-004).

### 4.7 SAP-оговорка (TODO(confirm))

Если ландшафт включает SAP, FK на уровне БД практически нет — связи живут в
DDIC/check-таблицах и CDS; реестр выражает то, чего каталог не умеет, и bootstrap
по FK там не срабатывает. Пример ребра `orders → deliveries`:
`mandatory_predicates = {"mandt": "100", "deleted": false}`.

Пример ребра «пришли из рекламы»:

| Поле ребра | Значение |
|---|---|
| связь | `orders.campaign_id → campaigns.campaign_id` (join_type = inner, cardinality = n:1) |
| meaning | «заказ атрибутирован кампании» |
| intent_tags | `['атрибуция', 'маркетинг']` |
| usage_notes | «'пришли из рекламы' = first-touch: первый заказ клиента из ads-кампании; any-touch завышает цифру; campaign_id надёжен с 2026-03» |

**Изменения по узлам:** `plan_joins` — код строит k взвешенных путей по снапшоту
с `graph_version` (§4.3), модель ранжирует топ-5; несколько рёбер между таблицами →
Reason «какое соответствует вопросу», неоднозначная атрибуция → `clarify`.
`build_skeleton` — джойны пишет код из рёбер плана (ключи, тип,
`mandatory_predicates`), модель наполняет только `SELECT / WHERE / GROUP BY /
ORDER BY`. `validate_sql` — джойны ⊆ `edge_id` плана, скелет не изменён,
`join_type` совпадает с планом, `mandatory_predicates` на месте, доступность ребра
вычисляется из прав на колонки соединения (ADR-005). `interpret_result` — раскрывает
допущение из `usage_notes`: «посчитано по любому заказу из кампании; при first-touch
цифра другая».

Главный инвариант сохраняется: **модель по-прежнему не может придумать связь — она
ходит только по активным рёбрам реестра.** Меняется то, что каждое ребро несёт
смысл и живёт под CI-гейтом. S31 (v1.4): инвариант — свойство СИСТЕМЫ, обоих
контуров исполнения: FSM — рёбра плана (скелет), тул-контур — сверка пары
операндов каждого JOIN с активным снимком (`SchemaGraphStore.join_edges` в
`validate_free_sql`); выдуманная связь — hallucination (ретрай оправдан).

S31 re-review (v1.5–v1.6) — честная граница инварианта. Сверяются: пары операндов
JOIN всех скоупов, пары корреляций подзапросов (внешняя таблица ↔ таблицы того же
сравнения), соединение ≥3 табличных источников, где присоединяемый источник не
связан равенством колонок с уже присоединёнными в конъюнктивном скелете ON —
функциональный критерий (fix-волна 4), а не перечень форм: comma, CROSS JOIN,
`ON TRUE`/`ON 1=1`, самосравнение, равенство «чужих» источников (`JOIN c ON
m.id = o.id` — c не тронут), равенство под `OR`/`NOT`/`CASE` (`OR TRUE` —
тавтология) — всё произведения, пары «соседей» произвольны (fail-closed);
несверяемые формы (производный источник CTE/подзапрос/LATERAL в операнде или в
корреляции) — fail-closed, обёртка связь не легализует. Вне
сверки BY DESIGN: semi-join и скалярный подзапрос БЕЗ корреляции (`WHERE c.id IN
(SELECT …)`, `= (SELECT …)`, `= ANY(…)`) — сравнение со значение-множеством:
строки одной таблицы не комбинируются со строками другой, «связь» в смысле
реестра не утверждается; включение в сверку давало бы ложные отказы на частом
законном SQL. Решение исполнителя fix-волны re-review S31 (консервативный вариант
«задокументировать, не расширять» из рекомендаций ревью); пересмотр — BL-045,
при первом кейсе злоупотребления этой формой.

## 5. Последствия

**Положительные:**
- Три разрыва закрыты явно: атрибуция — в `usage_notes`, тип джойна — бизнес-дефолт
  в ребре, бизнес-связи без FK — вносятся владельцем.
- Ответы бизнес-корректны и воспроизводимы: ребро + допущение фиксируются в трейсе;
  качество меряется (join-correctness по `edge_id`, §9 eval prd).
- Ребро живёт под CI-гейтом: активация — по измеренным фактам (колонки, типы,
  уникальность, сироты, fan-out против кардинальности), дрейф схемы ловится до
  попадания в мир агента.
- Знание домена живёт у владельца данных и меняется без разработчика; «нет пути»
  превращено в очередь заявок — у владельца есть ранжированный бэклог.

**Отрицательные / риски:**
- **Семантический слой — ручной труд**: сложность переносится из разработки в
  domain-настройку — осознанная цена; удешевляется bootstrap (FK + майнинг SQL/BI
  как кандидаты, строгий режим «предложить → подтвердил»).
- **Cold start (RISKS R-D3)**: пока реестр пуст, агент бесполезен; владелец —
  организационное узкое место. Метрики старта — доля вопросов с активным путём и
  time-to-edge.
- **Граф — производная структура (в отдельной СУБД, ADR-003):** дрейф настроек ↔
  рёбра возможен. Закрыто §4.3: истина в PG-строках (Neo4j — только топология),
  `graph_version` с пином на прогон, reconciliation-тест в CI.
- Конфликт ребра с грязными данными (campaign_id надёжен только с 2026-03)
  фиксируется в `usage_notes`, а не правкой данных — ловушка остаётся видимой.
- Пропуск владельцем нужного ребра → «путь не найден» + уточняющий вопрос + заявка:
  честный отказ предпочтительнее домысла.

**Критерии пересмотра решения (revisit triggers):**
- Наполнение связей становится бутылочным горлышком (много доменов, мало владельцев) →
  усилить автообнаружение: ранжирование `agent_edge_proposals` по частоте, батч-
  подтверждение владельцем.
- Появляется требование «время-зависимых» связей (курс на дату заказа с таблицей
  курсов) → расширение `temporal` условным джойном (temporal join) — правка
  ребра/планировщика, не принципа.
- Eval-сет покажет систематические ошибки выбора ребра → пересмотреть подсказку
  `meaning`/`intent_tags` в промпте `plan_joins` (подсказку — да, свободу — нет).

### Compliance, Security & Ethics

Реестр и заявки — таблицы настроек: агенту дана только read-only вьюха `active`,
запись — роль владельца реестра; каждое изменение — в append-only аудит (ADR-005 §2,
security.md). `mandatory_predicates` (MANDT, tenant, deleted=false) — часть контракта
корректности, не персональные данные; PII-редакция аудита — security.md §5.
