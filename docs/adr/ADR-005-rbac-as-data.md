## 1. Контекст

Глобальный whitelist таблиц закрывает «ограниченный доступ» как принцип, но не
бизнес-потребность: логист видит только логистику; аналитик с правами HR — логистику
и премии («кто из менеджеров выполнил план по отгрузкам и не был премирован» —
кросс-доменный джойн). Требования владельца: права меняем как настройки — таблица в
БД «такая-то роль, такая-то таблица, такие-то поля или `*`»; аутентификация — вне
агента. Цена этого выбора известна заранее: БД перестаёт различать пользователей —
промах валидатора вернёт чужие данные **молча**, поэтому архитектура границ должна
компенсировать это осознанно.

## 2. Сравнение по осям

| Ось | A: per-user GRANT PostgreSQL | B: права как данные в БД | C: внешний policy-движок (OPA/Casbin) | D: RLS сразу |
|---|---|---|---|---|
| Изменение права | DDL + flush пулов | **`UPDATE` строки, действует со следующего запроса** | правка политики вне БД | правка политики |
| Управление без разработчика | нет (DDL) | **да (SQL-настройка)** | да, но инфраструктура | нет |
| Пул соединений | на каждую роль | **один сервисный аккаунт** | один | один |
| Кто различает пользователей в БД | сама БД | никто → компенсируется рубежами | никто | БД (на уровне строк) |
| Соответствие практике BI (Metabase/Superset) | нет | **да — так работают BI-системы** | да | частично |
| Сложность v1 | средняя | **низкая** | высокая (ещё один сервис) | средняя |
| Региональная изоляция строк | нет | нет (следующая ступень) | возможна | **нативно** |

## 3. Рассмотренные варианты

### Вариант A — per-user GRANT
Отвергнут по трём причинам владельца: изменение прав — DDL; пул соединений на каждую
роль; рассинхрон между конфигом агента и состоянием БД. Плюс деградация аудита:
«кто спросил» живёт в БД-логах, не в trace агента.

### Вариант C — внешний policy-движок
Отвергнут на v1: ещё один сервис в учебном проекте ради того же результата, что даёт
таблица настроек; переносится позже за порт `AccessPolicy` без изменения рубежей.

### Вариант D — RLS сразу
Отвергнут как **замена** правам-данным: RLS закрывает изоляцию строк («менеджер
видит отгрузки только своего региона»), не таблично-колоночные права. Принят как
**составная часть рубежа БД** (v1.2, ревью-03 S4): политики читают
`SET LOCAL app.user_id` / `app.region`, которые выставляет приложение на
транзакцию; архитектура не меняется — scope в state остаётся источником.

### Вариант B — права как данные ✅ **ПРИНЯТО**

## 4. Решение

**Права — таблицы настроек в том же PostgreSQL:**

```sql
CREATE TABLE agent_permissions (          -- роль → таблица → колонки
    role        text NOT NULL,
    schema_name text NOT NULL DEFAULT 'public',
    table_name  text NOT NULL,
    columns     text NOT NULL DEFAULT '*',   -- '*' | 'employee_id,name,department'
    updated_by  text,
    updated_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (role, schema_name, table_name)
);

CREATE TABLE agent_user_roles (           -- пользователь → роли
    user_id text NOT NULL,
    role    text NOT NULL,
    PRIMARY KEY (user_id, role)
);
```

`'*'` — все колонки; список — только перечисленные. Права агент только читает,
никогда не меняет; редактируют владельцы данных. Ключевой принцип:

> **граница знаний агента = граница прав.** Недоступная таблица не существует в
> версии реальности агента: её нет в подграфе (планировщик не спланирует
> недоступный джойн), её DDL не попадает в RAG (модель не знает имени и не может
> «попытаться»), валидатор и БД — рубежи на случай бага.

**Версионирование настроек — триггерный счётчик, не `max(updated_at)`** (ревизия 02
§3.2). Проверка `max(updated_at)` покрывает только UPDATE: выдача/отзыв роли —
INSERT/DELETE в `agent_user_roles`, у которой версии нет вовсе; DELETE строки прав
`max()` не поднимает. Ровно для кейса revoke — самого чувствительного — контракт
NFR-5 («действует со следующего запроса») нарушался: отозванная роль жила бы в
per-user кэше до рестарта (TTL сознательно убран — staleness неограничен). Решение —
счётчик на группу настроек, который инкрементирует триггер на **любое** изменение:

```sql
CREATE TABLE settings_version (
    name    text PRIMARY KEY,   -- 'permissions' | 'user_roles' | 'relationships'
    version bigint NOT NULL DEFAULT 0
);
CREATE FUNCTION bump_settings_version() RETURNS trigger AS $$
BEGIN
  INSERT INTO settings_version(name, version) VALUES (TG_ARGV[0], 1)
  ON CONFLICT (name) DO UPDATE SET version = settings_version.version + 1;
  RETURN NULL;
END $$ LANGUAGE plpgsql;
-- три триггера AFTER INSERT OR UPDATE OR DELETE (FOR EACH STATEMENT):
-- agent_permissions → 'permissions'; agent_user_roles → 'user_roles';
-- agent_relationships → 'relationships' (ADR-006 §4)
```

`resolve_access` читает счётчики (один SELECT трёх строк — дешевле, чем `max()`) на
каждый запрос: версия изменилась → per-user кэш прав сбрасывается целиком
(пользователей ≤ 10). `plan_joins` — то же для топологии графа (ADR-006). Отвергнутая
альтернатива: soft-delete + `updated_at` на всех трёх таблицах — меняет UX владельцев,
DELETE всё равно приходится запрещать; триггер проще и полнее.

**Аутентификация — до агента, за портом `AuthProvider`** (агент — resource server):
MVP — `DevTokenAuth` (токен/выбор пользователя в Streamlit — живое демо RBAC),
production — `OIDCAuth` (JWKS-верификация JWT). Правило: голый `user_id` параметром —
не identity; аудит фиксирует проверенную личность, а не то, что прислал клиент.
S31: правило действует на весь CLI — сырой `--user` упразднён, токен обязателен
для любого контура, исполняющего SQL; `--token` имеет приоритет над `DEV_TOKEN`
из .env. (v1.4, BL-048/D-041: контур один — FSM; формулировка сохранена.)

**Рубежи** (граница знаний = граница прав — рубеж 1 по построению; 2–5 — на случай бага):

| Рубеж | Что проверяет | За счёт чего |
|---|---|---|
| 1. Фильтрация мира | подграф, retrieval, DDL, глоссарий — только разрешённое по scope | детерминированный код |
| 2. **AST-валидатор — главный рубеж** | таблицы и колонки ∈ правам; одна инструкция; запрет `SET/COPY/CALL/DO` и функций из deny-list; обход CTE/UNION/подзапросов/LATERAL; `LIMIT` к внешнему запросу; диалект postgres; скелет не изменён (`skeleton_hash`), `mandatory_predicates` на месте, джойны ⊆ `edge_id` плана; вложенные тела (CTE/подзапросы/LATERAL) — те же ACL-правила + «таблицы ⊆ план» (BL-051(a)); с v1.5 (S33, аудит A5): '*'-право не пропускает несуществующую колонку — именованная колонка под '*' сверяется с каталогом фактических колонок мира (`PermissionStore.columns_catalog` — `information_schema.columns` под `agent_planner`, только '*'-таблицы прав пользователя; «колонки нет» → hallucination с фактическим списком; отсутствующая запись каталога → дефект стыка R1 fail-closed) | sqlglot + **deny-by-default по типам узлов** + adversarial-тесты в CI (v1.4, BL-048/D-041: свободный вход тул-контура удалён вместе с контуром — «корпус прогнан через ОБОИХ входа» — история S31/B2; корпус — регресс FSM-входа) |
| 3. Deny-list схем | `pg_catalog`, `information_schema`, служебные схемы графа, `agent_*` — не существуют для агента | иначе один SELECT утаскивает топологию БД и структуру ролей |
| 4. ACL колонок соединения | ключи джойна (например `email`) доступны? нет — ребро недоступно целиком | вычисляется из `agent_permissions`, без PII-флага на ребре |
| 5. БД — второй настоящий рубеж | read-only транзакция (`default_transaction_read_only`), `statement_timeout` на сессию, RLS + `SET LOCAL app.user_id`; раздельные коннекты: планировщик и исполнитель `agent_ro` | агент не может ослабить рубеж ни промптом, ни SQL |

**Требования к валидатору** (компенсация «БД не различает пользователей»):

1. **Deny-by-default по типам узлов AST — ключевое правило.** Валидатор работает по
   whitelist'у типов узлов, которые умеет проверять; узел вне whitelist'а → **отказ**,
   а не «не проверили → пропустили». Перечисление конструкций (ниже) не может быть
   полным — sqlglot богаче любого списка; fail-closed превращает неполноту из
   молчаливой утечки в явный отказ.
2. Полный обход AST (SELECT/WHERE/JOIN ON/GROUP BY/ORDER BY/подзапросы/EXISTS/CTE —
   каждая пара «таблица, колонка»); `SELECT *` разворачивается в разрешённые колонки
   (не отклоняется — иначе либо лазейка, либо тупые отказы); все relation-ссылки
   включая тела CTE.
3. **Одна инструкция** на запрос; инструкции `SET/COPY/CALL/DO` и вызовы функций из
   deny-list — отказ независимо от прав (форма, не содержание); **`LIMIT` — к внешнему
   запросу** (`LIMIT 1000`); диалект парсинга — postgres (иначе диалектный зазор
   превращается в дыру).
4. **Deny-list схем:** `pg_catalog`, `information_schema`, служебные схемы графа,
   `agent_*` (настройки и аудит) — табличная проверка отсекает до AST-углубления.
5. **Скелет не изменён моделью:** `skeleton_hash` совпадает, все `mandatory_predicates`
   рёбер плана на месте (`MANDT`, `lang`, `deleted=false`, tenant), джойны ⊆
   `edge_id` плана (ADR-006), тип джойна совпадает с планом.
6. **ACL колонок соединения (рубеж 4):** ключевые колонки каждого джойна ∈ правам;
   нет доступа к ключу — ребро недоступно целиком. Вычисляется из `agent_permissions`;
   PII-флаг на ребре сознательно не заводится — одна истина о правах.
7. One-time hardening `agent_ro` (запрет `dblink`/`pg_read_file` — иначе `FROM
   dblink(...)` обходит табличный whitelist).
8. **Adversarial-тесты в CI обязательны**, и корпус покрывает не меньше поверхности,
   чем умел парсер: UNION с чужой таблицей, подзапросы, `t.*`, каталоги, **window-функции
   (`OVER (PARTITION BY ...)`), `LATERAL`, `DISTINCT ON`, `GROUPING SETS`**.
9. **Property-based сверка с парсером:** для корпуса SQL-ов множество колонок,
   извлечённое валидатором, обязано равняться множеству колонок из обхода sqlglot;
   расхождение = дыра в whitelist'е узлов, тест красный до продакшена.

**Рубеж 5 — БД как настоящий рубеж (v1.2, ревью-03 S4).** Приложение выставляет на
транзакцию `SET LOCAL app.user_id` (и `app.region` для RLS-политик); `agent_ro` —
`default_transaction_read_only = on` и `statement_timeout` на сессию — агент не может
ослабить ни промптом, ни SQL. **Раздельные коннекты планировщик/исполнитель:**
планировщику нужен `search_path` со служебными схемами графа, исполнителю `agent_ro` —
нет (меньше поверхности). Pooler в режиме transaction pooling совместим только с
`SET LOCAL` (сессионные `SET` протекают между клиентами пула) — правило для
конфигурации подключения. RLS-политики — поверх scope (вариант D), не замена ему.

**Различение исходов:** таблица не существует → галлюцинация → `diagnose_error`
(retry); существует, но вне прав → `degrade` без retry (сигнал безопасности).
**Деградация вместо отказа:** код фиксирует, чего не хватает; LLM формулирует:
«Данные о премиях доступны только роли HR. Могу показать, кто выполнил план по
отгрузкам — показать?» Схема скрывается, словарь бизнеса — нет: бизнес-понятия
публичны, недоступны данные. **Отказ не раскрывает существование данных (S9,
default по Q3):** формулировка бизнес-понятиями, без имён таблиц и без
подтверждения, что чужие данные есть — «Часть данных по этому вопросу вам
недоступна», а не «таблица bonuses вам не принадлежит».

**Инъекции второго порядка (S6):** инструкции могут прийти не только из вопроса, но
из данных БД, RAG-документов, `usage_notes` реестра, few-shot. Митигация: tool-output
и retrieval маркируются как **данные**, а не инструкции; действия по тексту из
результата запрещены; валидатор отсекает исполнение независимо от источника.

**Аудит (S8, append-only):** пользователь, вопрос, SQL, `edge_id` рёбер плана,
`graph_version` снапшота, число строк, отказы по правам, стоимость, уровни моделей.
Аудит — **вне state агента** (агент не может ни дописать, ни скрыть); PII в логах и
трейсах редактируется (security.md §5).

## 5. Последствия

**Положительные:**
- Изменение права мгновенно и без деплоя; RBAC демонстрируется живьём (сцены трёх
  персон: допуск, deny, деградация).
- Ни одного нового LLM-вызова: вся резолюция прав — детерминированный код.
- Заодно экономия токенов: в промпт попадает DDL только разрешённых таблиц.

**Отрицательные / риски:**
- **БД — не первичная per-user граница** (осознанный трейд): RLS на рубеже 5 —
  страховка и изоляция строк, первичная граница — валидатор (рубеж 2): бизнес-логика
  прав живёт в настройках, RLS-политики дублируют лишь грубое правило. Митигации:
  жёсткие требования к валидатору (§4), adversarial-тесты как условие приёмки PR,
  аудит с первого дня («кто спросил про непремированных менеджеров» —
  чувствительный запрос: личность, роли, `edge_id`, стоимость).
- Кэш и retrieval обязаны знать scope: ключ кэша = (scope, вопрос), namespace'ы
  few-shot/глоссария по ролям — иначе кэш отравляется между доменами (ADR-009).
- Residual risk: баг в ветке валидатора. Компенсация — deny-by-default по типам
  узлов (п. 1 §4) + adversarial-набор ≥ поверхности парсера + property-based сверка;
  приёмка сцены deny и этого набора — часть CI, а не ручная проверка (см. security.md).

**Compliance & Security:** аудит — append-only; идентичность из проверенного токена;
права агент не редактирует (управление — вне агента, у владельцев данных).

**Критерии пересмотра решения (revisit triggers):**
- Требование региональной изоляции строк → расширение RLS-политик на
  `app.region` (механизм рубежа 5 готов).
- Число ролей/таблиц прав растёт так, что SQL-настройки неудобны → внешний
  policy-движок за портом `AccessPolicy` (рубежи не меняются).
- Инцидент-класс «пропуск валидатора» → пересмотр рубежа 5 (per-user роли на уровне
  БД для чувствительных таблиц) — ценой отказа от «права как данные» для этих таблиц.
