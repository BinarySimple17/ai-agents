# ADR-007: каскад моделей — Intent-Based Routing с политикой ретраев M1

- **Статус:** Принято (v1.2, 2026-11-18 — отработка ревью-03 M1–M8/E1–E6 ([D-016](../../DECISIONS.md)/[D-017](../../DECISIONS.md)): политика попыток — попытка 2 та же модель + текст ошибки, попытка 3 — уровень вверх при достатке бюджета (supersedes правило v1.1 «каждый retry вверх»); глобальные капы ≤ 8 вызовов / ≤ 90 s / ≤ 2 ₽ с резервом 0,6 ₽; экономика зафиксирована по снимку каталога 18.11.2026 (0,61/0,62/0,67 ₽; базлайн 2,57 ₽; ≈76%); бенчмарки — Spider 2.0 / BIRD; circuit breaker завершается деградацией. v1.1 — эскалация — единое правило генерирующих узлов; v1.0 — статическая матрица)
- **Дата:** 2026-11-14
- **Контекст принятия:** закрытие требования ДЗ «логика выбора моделей + роутинг» и бюджета запроса; модели выбраны из реального каталога routerai.ru. Ревизия v1.2 — ревью-03: экономика сходится только при политике M1 (попытка 2 дешёвая), бенчмарки Text-to-SQL — Spider 2.0/BIRD вместо кодовых
- **Связанные документы:** prd.md (§4 FR-8, FR-10, FR-14, §5 NFR-1, NFR-2, NFR-7, §9 eval), ADR-002 (карта «кто что решает»: tier назначает код), ADR-004 (лимиты прогона), ADR-008 (принудительные форматы), model-card.md (снимок каталога и тарифов)

## 1. Контекст

Узлы агента требуют разных навыков: классификация и извлечение (clarify, diagnose),
генерация кода (generate_sql, шаги декомпозиции), структурное планирование (plan_query),
связный текст для пользователя (interpret_result). Профили нагрузки различаются
радикально: классификационные узлы вызываются на **каждый** запрос и промпт-тяжёлые,
генерация SQL — длинный контекст и короткий код, интерпретация — то, что пользователь
видит как «качество агента». «Одна модель на всё» проигрывает по бюджету и TTFT;
«одна дешёвая» — по качеству SQL и текста. Каталог провайдера routerai.ru
(OpenAI-совместимый шлюз; снимок от 18.11.2026 — 618 моделей, имена проверены) даёт
выбор в рублях.

## 2. Сравнение по осям

|---|---|---|---|---|
| Стоимость типового запроса (оба без retry — корректное сравнение) | ≈ 2,57 ₽ | ≈ 0,13 ₽ (оценочно) | **≈ 0,61 ₽** | зависит от доли эскалаций |
| Качество SQL | максимум | риск: код — слабое место дешёвых моделей | максимум на критичном узле (deepseek — код) | как C при обученном роутере |
| Качество текста пользователю | максимум | просадка (самая видная часть) | **флагман на interpret_result** | как C |
| TTFT дешёвых узлов | флагманский вход на каждый запрос («инфраструктурный налог») | минимальный | **дешёвый вход на частых узлах** | как C |
| Контроль инженера / предсказуемость | полный | полный | **полный: «узел → навык → модель» зашито в граф** | теряется (вероятностный исход) |
| Готовность к внедрению | сразу | сразу | **сразу** | нужен собственный eval-сет (дуэли/данные) |
| Стоимость 1000 запросов | ≈ 2 570 ₽ | — | **≈ 670 ₽** (с ретраями по политике §4) | — |

## 3. Рассмотренные варианты

### Вариант A — всё на флагмане (`z-ai/glm-5.3-prime`)
Отвергнут цифрами: 2,57 ₽ против 0,61 ₽ на типовом запросе (оба без retry);
классификационные узлы платят 299 ₽/1М за входные токены там, где достаточно
3,20 ₽/1М. Роутинг экономит **≈ 76%**; вклад в базлайн равный: `clarify + plan_joins`
≈ 0,98 ₽ и `generate_sql` ≈ 0,98 ₽.

### Вариант B — всё на дешёвой (`qwen/qwen3.7-flash`)
Отвергнут: генерация SQL — задача, где семейство qwen-flash проигрывает DeepSeek по
execution accuracy на многотабличных схемах (Spider 2.0 / BIRD); `interpret_result` —
единственный текст, который видит пользователь, — просадка недопустима. Дешёвая
модель остаётся на классификационных узлах, где ошибка дёшево исправима.

### Вариант D — вероятностный роутер (обученный на дуэлях LMArena / своих данных)
Отвергнут на v1 — нет eval-сета для обучения и оценки (§9 prd). Зафиксирован как
последующая ступень: подключаем, когда появится собственный eval-сет.

### Вариант C — статический Intent-Based Routing ✅ **ПРИНЯТО**

## 4. Решение

**Роутинг статический: классификатор определяет не «сложность», а какой навык нужен
узлу, и направляет к модели, сильной в этом навыке. Intent известен заранее — роль
узла, поэтому соответствие «узел → навык → модель» зашито в граф.**

Правило — три уровня: **классификация / извлечение / разбор ошибки → маленькая
(qwen); генерация кода → средняя (deepseek); рассуждение и финальный текст →
флагман (glm).**

Матрица (модели из каталога routerai.ru, снимок 18.11.2026; цены — зафиксированные
тарифы провайдера, ₽ за 1М токенов — model-card):

| Узел | Модель | Обоснование |
|---|---|---|
| `clarify`, `diagnose_error` | `qwen/qwen3.7-flash` (3,20/13; кэш-чтение 0,64; тариф ≤ 32K) | классификация/извлечение; вызываются на каждый запрос — скорость (TTFT) и минимальная цена входа; ошибки дёшево исправимы |
| `plan_joins` | код строит k взвешенных путей; `qwen/qwen3.7-flash` ранжирует топ-5 | сотни таблиц дешёвая модель не вывезет, ранжирование готовых кандидатов — вывезет; план проверяет код; неоднозначность ранжирования → `clarify` (A6), не эскалация |
| `generate_sql`, `generate_step_sql` | `deepseek/deepseek-v4.1-flash-1017` (8/12; кэш-чтение 0,82) | **критичный узел**: модель наполняет готовый скелет — средней достаточно; выход в ~78 раз дешевле флагманского — профиль «длинный контекст, короткий код»; «галлюцинация связи» исчезает как класс (скелет от кода), остаются ошибки фильтра/агрегации |
| `plan_query` | deepseek (reasoning адресно) | DAG строится редко; валидация инвариантов — код |
| `interpret_result` | `z-ai/glm-5.3-prime` (299/939) | единственный текст, который видит пользователь: язык и связность — флагман оправдан; вход — компакция (`compact_result`), не сырые строки |
| `resolve_access`, `build_skeleton`, `validate_sql`, `check_cost`, `execute_sql`, `merge_results`, `compact_result`, `degrade` | **код, без LLM** | граница прав и корректность — не место для модели (валидация JoinPlan и скелета — здесь же) |

### 4.1 Политика ретраев M1 (D-016; supersedes правило v1.1 «каждый retry вверх»)

«Не получилось» решает код, а не модель: для SQL — валидатор (ADR-005), для плана —
механическая проверка JoinPlan. Политика попыток — **три попытки на узел**:

1. **Попытка 1** — базовая модель узла (матрица выше);
2. **Попытка 2** — **та же модель + текст ошибки**: большинство сбоев — формат и
   невнимательность, дешёвый повтор без оплаты дорогой модели (на этом сходится
   экономика §4.3);
3. **Попытка 3** — **модель на уровень вверх** (эскалация), только если остатка
   бюджета хватает.

Счётчики — **на узел** (≤ 3 попыток) плюс **глобальные капы на прогон**: ≤ 8
LLM-вызовов, ≤ 90 s, ≤ 2 ₽. Перед каждой эскалацией — проверка оценки стоимости
против остатка **с резервом 0,6 ₽ под `interpret_result`**: не хватает — честный
отказ или incomplete, а не «потратили всё и не смогли объяснить». Не справил и
флагман — отказ с уточняющим вопросом. В контекст при retry идёт только последний
SQL/план + текст ошибки, не цепочка попыток.

Эскалацию назначает код по `retry_count` — модель маршрут не выбирает (ADR-002);
только вверх (попытка 2 — не откат вниз, а повтор той же модели с контекстом
ошибки; «флагман → дешёвая» fallback отсутствует — если флагман не справился,
откат не поможет). Эскалации расходуют наузловый лимит попыток и глобальные капы.

### 4.2 Бенчмарки и structured output

**Обоснование моделей — бенчмарки** (источники: HuggingFace, LMArena; пресс-релизы
вендоров — с осторожностью). Релевантные для Text-to-SQL — **Spider 2.0 / BIRD**
(execution accuracy на многотабличных схемах) и **LMArena** для языка. Правила
чтения:

1. **Низкий результат — дисквалификатор, высокий почти ничего не говорит**
   (насыщение; 98% ≠ «идеально» — риск **загрязнения данных**).
2. **Никакого синдрома одной метрики** — отбор по совокупности, включая «что не плохое».
3. **Инфраструктурный налог** — флагман на дешёвом узле поднимает TTFT и жжёт бюджет.

Для открытых моделей — класс и публичные результаты семейства как proxy; финальная
калибровка — собственным eval-сетом (§9 prd).

**Structured output (M5):** `JoinPlan` / `QueryPlan` / `ResultCompact` —
pydantic-модели, ответ LLM валидируется схемой при **temperature 0** — механическая
проверка дешёвая и надёжная (ADR-008). Reasoning-режим включается адресно
(`plan_query`, попытка 3) и не включается на классификационных узлах.

### 4.3 Экономика (зафиксирована по снимку каталога 18.11.2026 — D-017)

Тарифы плавают — расчёт зафиксирован по значениям ниже (методика важнее цифр;
пересчёт — только решением владельца с фиксацией новой даты, sync с model-card):

| Узел | Модель | Токены in/out | Стоимость |
|---|---|---|---|
| `clarify` | qwen | 800 / 120 | 0,0041 ₽ |
| `plan_joins` | qwen | 1500 / 200 | 0,0074 ₽ |
| `generate_sql` | deepseek | 2250 / 350 | 0,0222 ₽ |
| `diagnose_error` (retry, та же модель) | qwen | 2000 / 150 | 0,0084 ₽ |
| `interpret_result` | glm | 1150 / 250 | 0,5786 ₽ |
| код-узлы (`resolve_access` … `compact_result`, `degrade`) | — | — | 0 |

Вход `interpret_result` в 1150 токенов обоснован компакцией: `compact_result` отдаёт
схему + `row_count` + ≤ 20 строк + агрегаты, а не сырые 1000 строк.

Итоги (политика ретраев §4.1):

- типовой запрос без retry ≈ **0,61 ₽**; +25% запросов с дешёвым retry (попытка 2 —
  та же модель) ≈ **0,62 ₽**; +5% с эскалацией SQL на glm (≈ 1,00 ₽ за вызов) ≈
  **0,67 ₽**;
- эффект роутинга, сравнение корректное (оба без retry): «всё на glm» = 0,352 +
  0,636 + 1,001 + 0,579 ≈ **2,57 ₽** — экономия **≈ 76%**;
- распределение: `interpret_result` ≈ **95%** стоимости;
- **кап с резервом:** худший случай (план на glm 0,90 + SQL на glm 1,00 + объяснение
  0,58 ₽) превышает 2 ₽ → `cap = 2 ₽`, `reserve(interpret) = 0,6 ₽`, генерация
  ≤ 1,4 ₽; перед эскалацией — проверка против остатка, не хватает — честный
  отказ/incomplete (§4.1);
- масштаб: 1 000 запросов ≈ **670 ₽** — час работы аналитика;
- **рычаг оптимизации — `interpret_result` (M8):** шаблон + средняя модель для
  простых результатов, гейт по eval (§9 prd) — **в базовую версию не входит**.

Типовой прогон ≈ **6,6К токенов суммарно** (920 + 1700 + 2600 + 1400) при 0,9–2,6К
на отдельный вызов — двухуровневый тариф qwen (≤ 32K / > 32K) всегда дешёвый уровень.

## 5. Последствия

**Положительные:**
- ≈ 76% экономии против «всё на флагмане»; предсказуемая цена запроса и честная
  методика её пересчёта при смене тарифов.
- Дешёвый retry (попытка 2 — та же модель) делает политику ретраев массовой без
  удорожания: +25% ретраев стоят +0,01 ₽.
- Смена модели — параметр вызова через единый шлюз (NFR-7); провайдер возвращает
  три роли `cheap / mid / strong` — замена конкретных моделей не трогает узлы.
- TTFT-контроль на частых узлах (NFR-1) — правила роутинга зашиты, а не угадываются.

**Отрицательные / риски:**
- Статическая матрица не адаптируется к «неожиданно сложному» вопросу — принятые
  динамические механизмы (политика ретраев M1 с эскалацией на попытке 3,
  декомпозиция) покрывают рискованные узлы (план, генерация SQL), остальное —
  revisit после eval-сета.
- Цены и состав каталога плавают (на 18.11.2026 `glm-5.3-prime` уже 180/565 против
  299/939 в расчёте) — расчёт зафиксирован по снимку (D-017), иначе канон
  расползается; методика важнее цифр. reasoning-режим включается адресно.
- RPM/TPM шлюза: типовой прогон ≈ 6,6К токенов, 0,9–2,6К на вызов; всплески →
  backoff 1→2→4с **с jitter** (без него синхронные ретраи разных сессий бьют шлюзом
  волнами), circuit breaker (5 сбоев → 60с).
- **Circuit breaker завершается деградацией, а не пустой ошибкой (M6):** валидный SQL
  без объяснения или отложенная задача — пользователь получает результат, пусть и
  неполный (флаг в ответе).
- **Таймаут на каждый LLM-вызов (~15s):** зависший вызов шлюза — не «сбой» для
  breaker'а (тот считает ошибки, не медлительность); таймаут конвертирует
  медлительность в отказ узла → штатный путь (`diagnose_error` / деградация).
- **Back-of-envelope конкурентности — озвученное допущение v1:** воркеры за очередью
  (развёртывание — c4-l2 v1.8: agent-api + agent-worker), профиль v1 — ≤ 10
  одновременных пользователей, p95 20s → до ~10 параллельных LLM-вызовов и до 10
  занятых соединений PG (дефолт пула 100 — с запасом); ощущение скорости — TTFT ≤ 3s
  на частых узлах. Per-user token bucket — в коде агента (security.md §3). Рост
  нагрузки → реплики воркеров и пересчёт профиля, не переделка архитектуры.

**Критерии пересмотра решения (revisit triggers):**
- Собственный eval-сет готов → обучить вероятностный роутер (вариант D) и сравнить
  с матрицей на тех же вопросах; поглощение возможно частями.
- Смена тарифов/состава каталога routerai.ru → пересчёт §4.3 и матрицы **решением
  владельца с фиксацией новой даты снимка** (D-017); правило то же: навык →
  бенчмарк → модель.
- Появление дешёвого reasoning-класса с гарантированным structured output (ADR-008)
  → пересмотр `plan_query` без эскалаций на флагман.
- Устойчивая очередь / деградация p95 при > 10 одновременных пользователях →
  реплики воркеров + пул-сайзинг (пересчёт back-of-envelope §5).
- Устойчиво частые эскалации `plan_joins` (> 10% вопросов) → поднять стартовый
  tier план-узла (mid сразу) с перерасчётом экономики §4.3.
