# ADR-007: каскад моделей — Intent-Based Routing с эскалацией при retry

- **Статус:** Принято (v1.1, 2026-11-16 — эскалация — единое правило генерирующих узлов: plan_joins получает валидацию JoinPlan и эскалацию cheap→mid→strong; generate_sql — эскалация проговорена в матрице)
- **Дата:** 2026-11-14
- **Контекст принятия:** закрытие требования ДЗ «логика выбора моделей + роутинг» и бюджета запроса; модели выбраны из реального каталога routerai.ru
- **Связанные документы:** prd.md (§4 FR-8, FR-14, §5 NFR-1, NFR-2, NFR-7), ADR-002 (карта «кто что решает»), ADR-004 (эскалация при retry шага), ADR-008 (принудительные форматы ограничивают выбор моделей)

---

## 1. Контекст

Узлы агента требуют разных навыков: классификация и извлечение (clarify, diagnose),
генерация кода (generate_sql, шаги декомпозиции), структурное планирование (plan_query),
связный текст для пользователя (interpret_result). Профили нагрузки различаются
радикально: классификационные узлы вызываются на **каждый** запрос и промпт-тяжёлые,
генерация SQL — длинный контекст и короткий код, интерпретация — то, что пользователь
видит как «качество агента». «Одна модель на всё» проигрывает по бюджету и TTFT;
«одна дешёвая» — по качеству SQL и текста. Каталог провайдера routerai.ru
(OpenAI-совместимый шлюз, 608 моделей) даёт выбор в рублях.

## 2. Сравнение по осям

| Ось | A: всё на флагмане | B: всё на дешёвой | C: статический Intent-Based Routing | D: вероятностный роутер на дуэлях |
|---|---|---|---|---|
| Стоимость типового запроса | ≈ 3,31 ₽ | ≈ 0,13 ₽ (оценочно) | **≈ 0,61 ₽** | зависит от доли эскалаций |
| Качество SQL | максимум | риск: код — слабое место дешёвых моделей | максимум на критичном узле (deepseek — код) | как C при обученном роутере |
| Качество текста пользователю | максимум | просадка (самая видная часть) | **флагман на interpret_result** | как C |
| TTFT дешёвых узлов | флагманский вход на каждый запрос («инфраструктурный налог») | минимальный | **дешёвый вход на частых узлах** | как C |
| Контроль инженера / предсказуемость | полный | полный | **полный: «узел → навык → модель» зашито в граф** | теряется (вероятностный исход) |
| Готовность к внедрению | сразу | сразу | **сразу** | нужен собственный eval-сет (дуэли/данные) |
| Стоимость 1000 запросов | ≈ 3 310 ₽ | — | **≈ 610–620 ₽** | — |

## 3. Рассмотренные варианты

### Вариант A — всё на флагмане (`z-ai/glm-5.3-prime`)
Отвергнут цифрами: 3,31 ₽ против 0,61 ₽ на типовом запросе; классификационные узлы
платят 299 ₽/1М за входные токены там, где достаточно 3,20 ₽/1М. Роутинг экономит
**~81%**; главный вклад — именно классификационные узлы.

### Вариант B — всё на дешёвой (`qwen/qwen3.7-flash`)
Отвергнут: генерация SQL — задача кода, где семейство qwen-flash не тягается с
DeepSeek (SWE-bench-класс); `interpret_result` — единственный текст, который видит
пользователь, — просадка недопустима. Дешёвая модель остаётся на классификационных
узлах, где ошибка дёшево исправима.

### Вариант D — вероятностный роутер (обученный на дуэлях LMArena / своих данных)
Отвергнут на v1 — нет eval-сета для обучения и оценки (open #2). Зафиксирован как
последующая ступень: подключаем, когда появится собственный eval-сет.

### Вариант C — статический Intent-Based Routing ✅ **ПРИНЯТО**

## 4. Решение

**Роутинг статический: классификатор определяет не «сложность», а какой навык нужен
узлу, и направляет к модели, сильной в этом навыке. Intent известен заранее — роль
узла, поэтому соответствие «узел → навык → модель» зашито в граф.**

Правило — три уровня: **классификация / извлечение / разбор ошибки → маленькая
(qwen); генерация кода → средняя (deepseek); рассуждение и финальный текст →
флагман (glm).**

Матрица (модели из каталога routerai.ru; цены — тариф провайдера, ₽ за 1М токенов):

| Узел | Модель | Обоснование |
|---|---|---|
| `clarify`, `diagnose_error` | `qwen/qwen3.7-flash` (3,20/13; кэш-чтение 0,64; тариф ≤ 32K) | классификация/извлечение; вызываются на каждый запрос — скорость (TTFT) и минимальная цена входа; ошибки дёшево исправимы |
| `plan_joins` | `qwen/qwen3.7-flash` (3,20/13), **эскалация при провале валидации JoinPlan: deepseek (reasoning) → glm-5.3-prime** | частый узел — старт дёшев; валидацию плана делает код, эскалация — только по факту провала (v1.1); исчерпание → `fail` (уточняющий вопрос) |
| `generate_sql` | `deepseek/deepseek-v4.1-flash-1017` (8/12; кэш-чтение 0,82), **эскалация на glm-5.3-prime при retry** (через `diagnose_error`) | **критичный узел**: код — сильная сторона семейства DeepSeek; выход в ~78 раз дешевле флагманского — профиль «длинный контекст, короткий код» точно ложится на SQL |
| `plan_query`, `generate_step_sql` | deepseek (reasoning адресно), **эскалация на glm-5.3-prime** при retry | DAG строится редко; эскалация платит за фактический провал |
| `interpret_result` | `z-ai/glm-5.3-prime` (299/939) | единственный текст, который видит пользователь: язык и связность — флагман оправдан |
| `resolve_access`, `validate_sql`, `check_cost`, `execute_sql`, `merge_results` | **код, без LLM** | граница прав и корректность — не место для модели (валидация JoinPlan — здесь же: код, не модель) |

**Два динамических механизма без отдельного классификатора** — его роль до появления
eval-сета: (1) **триггер декомпозиции** T1/T2 — детерминированные пороги, без LLM;
(2) **эскалация** — v1.1 (решение владельца): единое правило всех генерирующих узлов
(`plan_joins`, `plan_query`, `generate_sql`, `generate_step_sql`) — повторная попытка
после провала идёт **на уровень вверх** (cheap→mid→strong; выше strong некуда —
дальше `diagnose_error`/отказ): платим только за фактический провал — data-driven
в миниатюре. Провал фиксирует код: для SQL — валидатор и `diagnose_error`; для
`plan_joins` — структурная валидация JoinPlan при парсинге (все таблицы ∈ scope,
каждый джойн — ребро графа, ≤ 4 таблиц, связность — как инварианты `plan_query`
в ADR-004): невалидный план → retry с эскалацией, исчерпание → `fail`
(уточняющий вопрос). Эскалацию назначает код по `retry_count` — модель маршрут
не выбирает (ADR-002); эскалации расходуют общий retry-бюджет ≤ 3. Только вверх:
нет fallback «флагман → дешёвая» — если модель не справилась, откат вниз не поможет;
правильный путь — `diagnose_error`.

**Обоснование моделей — бенчмарки** (источники: HuggingFace, LMArena; пресс-релизы
вендоров — с осторожностью). Карта «навык → бенчмарк»: генерация кода — SWE-bench /
HumanEval; рассуждение — MATH; язык — LMArena L-rating; tool use — BFCL. Правила
чтения:

1. **Низкий результат — дисквалификатор, высокий почти ничего не говорит** (HumanEval
   насыщен; < 85% — коду не доверяем; 98% ≠ «идеально» — риск **загрязнения данных**).
2. **Никакого синдрома одной метрики** — отбор по совокупности, включая «что не плохое».
3. **Инфраструктурный налог** — флагман на дешёвом узле поднимает TTFT и жжёт бюджет.
4. Устаревшие бенчмарки (MMLU, GSM8K) — только негативный сигнал.

Для открытых моделей — класс и публичные результаты семейства как proxy;
финальная калибровка — собственным eval-сетом.

**Экономика** (полный расчёт — hw-01/README.md §7): типовой запрос ≈ **0,61 ₽**
(без retry), среднее с ретраями ≈ 0,62 ₽; с кэшем (hit rate 30%) ≈ 0,61 ₽;
декомпозированный ≈ 0,65 ₽ (+6% — окупается); `interpret_result` ≈ 95% стоимости —
главный рычаг дальнейшей оптимизации; **бюджет-кап 2 ₽** на запрос (FR-14) — при
исчерпании остановка с частичным ответом (валидный исход, ADR-002). Эскалации в
типовую цену не входят (редки); худший сценарий `plan_joins` (cheap→mid→strong;
контекст графа ~3К токенов) добавляет ≈ 0,9 ₽ (вход флагмана 299 ₽/1М) — запрос
с двумя провалами может подойти к капу → `budget_stop` (честная остановка).

## 5. Последствия

**Положительные:**
- ~81% экономии против «всё на флагмане»; предсказуемая цена запроса и честная
  методика её пересчёта при смене тарифов.
- Смена модели — параметр вызова через единый шлюз (NFR-7); провайдер возвращает
  три роли `cheap / mid / strong` — замена конкретных моделей не трогает узлы.
- TTFT-контроль на частых узлах (NFR-1) — правила роутинга зашиты, а не угадываются.

**Отрицательные / риски:**
- Статическая матрица не адаптируется к «неожиданно сложному» вопросу — принятые
  динамические механизмы (эскалация на всех генерирующих узлах — v1.1, декомпозиция)
  покрывают рискованные узлы (план, генерация SQL), остальное — revisit после
  eval-сета.
- Цены и состав каталога плавают — расчёт «плюс-минус километр»; методика важнее
  цифр. reasoning-режим включается адресно (plan_query, эскалация) и не включается
  на классификационных узлах — латентность там важнее.
- RPM/TPM шлюза: типовой запрос = 2 дешёвых + 1 средний + 1 флагманский вызов,
  ~3К токенов; всплески → backoff 1→2→4с **с jitter** (без него синхронные ретраи
  разных сессий бьют шлюзом волнами), circuit breaker (5 сбоев → 60с).
- **Таймаут на каждый LLM-вызов (~15s):** зависший вызов шлюза — не «сбой» для
  breaker'а (тот считает ошибки, не медлительность); таймаут конвертирует
  медлительность в отказ узла → штатный путь (`diagnose_error` / `degraded`).
- **Back-of-envelope конкурентности — озвученное допущение v1:** один sync-процесс,
  ≤ 10 одновременных пользователей по одному запросу, p95 20s → до ~10 параллельных
  LLM-вызовов и до 10 занятых соединений PG (дефолт пула 100 — с запасом); ощущение
  скорости — TTFT ≤ 3s на частых узлах. Per-user token bucket — в коде агента
  (security.md §3; портала в v1 нет). Рост нагрузки → реплики процесса за LB и
  пересчёт профиля, не переделка архитектуры.

**Критерии пересмотра решения (revisit triggers):**
- Собственный eval-сет готов → обучить вероятностный роутер (вариант D) и сравнить
  с матрицей на тех же вопросах; поглощение возможно частями.
- Смена тарифов/состава каталога routerai.ru → пересчёт §7 и матрицы; правило то же:
  навык → бенчмарк → модель.
- Появление дешёвого reasoning-класса с гарантированным structured output (ADR-008)
  → пересмотр `plan_query` без эскалаций на флагман.
- Устойчивая очередь / деградация p95 при > 10 одновременных пользователях →
  реплики процесса + пул-сайзинг (пересчёт back-of-envelope §5).
- Устойчиво частые эскалации `plan_joins` (> 10% вопросов) → поднять стартовый
  tier план-узла (mid сразу) с перерасчётом экономики §4.
