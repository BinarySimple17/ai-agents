# ADR-008: принудительные форматы — constrained decoding где доступно, тул-based enforcement где нет

- **Статус:** Принято (v1.0)
- **Дата:** 2026-11-14
- **Контекст принятия:** все структурированные выходы агента должны быть валидным JSON по схеме; наблюдение на реальном провайдере показало, что «structured output» через шлюз не гарантирован
- **Связанные документы:** prd.md (§4 FR-9), ADR-002 (невалидный план ломает оркестратор), ADR-004 (QueryPlan — структурированный выход), ADR-007 (выбор моделей частично зависит от этого решения)

---

## 1. Контекст

Структурированные выходы агента — `Clarification`, `JoinPlan`, `QueryPlan` (DAG шагов
декомпозиции), диагностические подсказки `diagnose_error` — парсятся кодом
оркестратора и валидатором инвариантов. Невалидный JSON валит парсер: узел получает
мусор, retry расходует бюджет, декомпозиция откатывается. Класс отказов «невалидный
структурированный выход → retry» нужно закрыть по построению, а не надеждой на
послушание модели.

Проверка реального провайдера (`routerai.ru/api/v1/chat/completions`, deepseek-flash):
режим structured outputs на интерфейсе возвращает валидный JSON, но в теле ответа
рядом присутствует свободный reasoning-текст — гарантии «строго JSON и ничего кроме»
облачные шлюзы **не дают**.

## 2. Сравнение по осям

| Ось | A: доверять structured outputs провайдера | B: prompt-only + парсинг с retry | C: constrained decoding где доступно + тул-based enforcement где нет |
|---|---|---|---|
| Гарантия валидного JSON | декларируется, фактически не гарантирована через шлюз (reasoning-тело рядом с JSON) | нет — вероятность ошибки пропорциональна длине | **by design**: xgrammar зануляет вероятности токенов, нарушающих схему; тул — схема enforced протоколом function calling |
| Зависимость от провайдера | полная | нет | частичная: слой A работает там, где есть; тул — универсален |
| Латентность/цена | базовая | retry-штрафы | базовая (тул не дороже обычного вызова) |
| Свобода смены модели | полная | полная | слегка ограничена: тул требует function calling у модели — почти все поддерживают; xgrammar-слой — только у self-hosted/локальных |
| Применимость к reasoning-моделям | сомнительна (тело reasoning) | сомнительна | **тул работает** — проверено на практике |

## 3. Рассмотренные варианты

### Вариант A — полагаться на structured outputs провайдера
Отвергнут как единственный слой: наблюдение на routerai.ru (§1) показывает, что
гарантия — декларативная. Остаётся как первый слой там, где инфраструктура его
поддерживает (self-hosted/локальные модели: xgrammar компилирует JSON-схему в
конечный автомат, logit masking физически зануляет запрещённые токены — валидный
JSON становится свойством среды исполнения).

### Вариант B — промпт + парсинг с retry
Отвергнут как основной: превращает гарантию в вероятность; на reasoning-моделях
(план декомпозиции) промпт-дисциплина ещё слабее. Остаточное применение — как
диагностический контекст в `diagnose_error` при невалидном выходе, не как защита.

### Вариант C ✅ **ПРИНЯТО** — двухслойная схема

## 4. Решение

**Класс отказов «невалидный структурированный выход» закрывается двумя слоями:
гарантированно — там, где есть constrained decoding; надёжно тулом — там, где нет.**

- **Слой 1 — constrained decoding (если инфраструктура поддерживает):** xgrammar
  компилирует JSON-схему в конечный автомат; logit masking зануляет вероятности
  токенов, нарушающих схему. Валидный JSON — свойство среды исполнения, а не
  поведения модели.
- **Слой 2 — тул-based enforcement (универсальный фолбэк):** там, где нужен стройный
  чёткий JSON без лишнего, а xgrammar недоступен (облачные шлюзы), структурированный
  выход оформляется **вызовом тулa** с JSON-схемой аргументов — протокол function
  calling принуждает форму. Подход проверен на практике:
  https://github.com/BinarySimple17/teeth_game (тулы поверх reasoning-моделей через
  OpenAI-совместимый шлюз).

Осознанная цена: тул слегка ломает идею «смена модели — правка ручки API» — тул
живёт в оркестраторе и должен регистрироваться для каждой модели, требующей его
(практически все поддерживают function calling; реестр тулов — в composition-слое).
Пока решение такое; revisit — по мере гарантий провайдеров.

**Инвариант, который не отменяет ни один слой: текст от LLM — не доверенный.**
Валидация по существу обязательна независимо от формата: `QueryPlan` — проверка
инвариантов кодом (топология, ≤ 4 шагов, whitelist key-колонок — ADR-004); SQL —
AST-валидатор + ACL (ADR-005) + проверка джойнов по графу (ADR-006). Принудительный
формат снимает класс «сломанный JSON», но не «валидный JSON с вредоносным/неверным
содержимым».

## 5. Последствия

**Положительные:**
- Отказ «невалидный JSON → retry» исключён по построению на обоих слоях; бюджет
  retry расходуется на содержательные ошибки (галлюцинация, права), а не на парсинг.
- Схема работает одинаково для обычных и reasoning-моделей (проверено на
  teeth_game) — reasoning включается адресно (plan_query, эскалация) без риска
  для структурированных выходов.
- Валидатор инвариантов остаётся единым: одинаковый для слоя 1 и слоя 2.

**Отрицательные / риски:**
- Реестр тулов и регистраций per-model — дополнительный код в composition-слое;
  дрейф «модель добавили, тул не зарегистрировали» ловится тестом конфигурации.
- xgrammar-слой доступен не через все шлюзы — на routerai.ru реально работает слой 2;
  слой 1 — стратегия для self-hosted/локального fallback (ADR-007, NFR-7).
- Провайдеры могут начать гарантировать structured outputs честно — тогда слой 2
  для конкретной модели отключается флагом конфигурации (без правки узлов).

**Критерии пересмотра решения (revisit triggers):**
- routerai.ru (или иной шлюз) даёт документированную гарантию строгого JSON без
  reasoning-тела у целевых моделей → отключить слой 2 для этих моделей флагом,
  пересчитать TTFT/цену.
- Появление constrained decoding у облачных провайдеров через OpenAI-совместимый
  API → слой 1 становится основным, тул — только для reasoning-моделей без поддержки.
- Смена состава моделей (ADR-007) → перерегистрация тулов; тест-конфигурация
  входит в CI.
