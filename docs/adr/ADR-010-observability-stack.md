# ADR-010 — Live-наблюдаемость: OTel → Prometheus/Jaeger → Grafana

- **Статус:** Принято (v1.2, 2026-11-15 — источник `/metrics`: долгоживущий Streamlit-демо; CLI-прогоны — OTLP-спаны + query_trace; решение владельца, FIX-005. v1.1, 2026-11-14 — Jaeger вместо Tempo; без коллектора: Prometheus скрейбит `/metrics` напрямую)
- **Требования prd.md:** FR-11 (наблюдаемость), NFR-1/2/6/8 (пороги — они же SLO)
- **Связанные документы:** observability.md (операционный уровень: сигналы, пороги,
  корреляция), er-data-model.md (`query_trace` — system of record), c4-l2-container.md
  (Observability Plane), security.md §5 (сегментация плоскости телеметрии),
  RISKS.md (R-C2, R-C4, R-P1 — потребители сигналов)
- **Триггер решения:** решение владельца (2026-11-14) — live-стек обязателен. Дополнительные
  мотивы: диагностика R-C4/R-C2 в реальном времени, а не по отчёту на вехе; демо для
  ДЗ-06 и выпускной работы (дашборды и waterfall трейса — сильная демонстрация);
  компетенция LGTM-семейства — часть целей курса.

---

## 1. Контекст

observability.md v1.0 закрепил отчётный минимум: трейс в `query_trace`, логи в stdout,
метрики SQL-представлениями, «страница» заменена отчётом по вехам. Это честный минимум
для ≤ 10 одновременных, но у него есть цена, которая растёт по мере движения к выпускной
работе: сигнал о деградации запаздывает до вехи; «где зависло / где деньги» — только
последующий разбор `node_timings`; для калибровки T1/T2 и динамического роутера
(revisit ADR-007) нужен живой срез, а не ретроспектива. Вопрос: строить ли live-контур
наблюдаемости, и если да — свой или managed.

## 2. Сравнение по осям

| Ось | C0 Отчёт из query_trace (v1.2) | C1 Self-hosted OTel | C2 Managed (Grafana Cloud) |
|---|---|---|---|
| Время до сигнала о деградации | часы–дни (отчёт на вехе) | минуты (дашборд/алерт) | минуты |
| Диагностика «где зависло / где деньги» | последующий разбор `node_timings` | live spans + p95 по узлам | то же + долгая история |
| Усилия внедрения | ноль (уже сделано) | средние: SDK + 3–4 контейнера + дашборды | минимальные (без контейнеров) |
| Данные и ₽ | всё локально, бесплатно | всё локально, бесплатно | телеметрия уходит вовне (R-S4), free-tier лимиты |
| Надёжность самой телеметрии | ломаться нечему | коллектор/стек могут ломаться — митируется async-экспортом | SLA вендора |
| Демо / защита | скриншоты SQL-отчётов | живые дашборды + waterfall трейса | то же, но на чужой инфраструктуре |

## 3. Варианты

- **C0 — отчёт из `query_trace`** (статус quo v1.2). Дёшево и достаточно для eval-сета
  и экономики по горизонту, но сигнал запаздывает до вехи, спанов нет. **Не выброшен:**
  остаётся постоянным аналитическим слоем (eval-сет, отчёты) — live-стек его не заменяет.
- **C1 — self-hosted OTel-стек, без коллектора.** SDK в приложении: трейсы — OTLP
  напрямую в Jaeger all-in-one; метрики — Prometheus-экспортёр SDK на `/metrics`
  приложения, Prometheus скрейбит напрямую; Grafana (дашборды, поиск трейсов) +
  Alertmanager (уведомления). Полный контроль данных, ноль внешних зависимостей,
  единственная стоимость — сопровождение контейнеров.
- **C2 — Grafana Cloud / managed OTLP.** Ноль инфраструктуры, но телеметрия покидает
  контур (усугубляет R-S4 — и без того осознанный допуск «данные у LLM-провайдера»),
  free-tier ограничения по спанам. Отклонён; OTLP-экспорт делает миграцию тривиальной —
  revisit-вариант при появлении корпоративного контура.

## 4. Решение

**C1 — self-hosted OTel-стек** (состав Observability Plane в c4-l2):

1. **SDK opentelemetry-python в приложении.** Спаны: корневой на прогон (run), по
   одному на узел FSM, LLM-вызов (атрибуты: node, role, model, attempt, tokens,
   cost_rub, timeout — числа, не payload) и выполнение SQL (datasource, row_count).
   Трейсы — OTLP напрямую в Jaeger (BatchSpanProcessor: батчинг, best-effort —
   телеметрия не блокирует запрос); метрики — Prometheus-экспортёр SDK на `/metrics`
   (тот же крошечный HTTP-сервер, что `/livez`/`/readyz`). HTTP-сервер поднимает
   **долгоживущий процесс — Streamlit-демо** (v1.2): CLI-прогон живёт секунды и
   скрейбиться не может; его телеметрия — OTLP-спаны (async-batch, отправка при
   завершении) и `query_trace`.
2. **Jaeger all-in-one** — хранилище трейсов: OTLP-native (4317/4318), Badger на
   локальном volume (переживает рестарт), встроенный UI; Grafana подключает его
   как data source. OTLP-эндпоинт — переменная окружения: Jaeger, Tempo или другой
   OTLP-бэкенд меняются env-ом, не кодом.
3. **Prometheus** — метрики: скрейп `/metrics` напрямую (без коллектора); источник —
   Streamlit-демо (из compose — `host.docker.internal:<port>`); CLI-прогоны в
   live-сериях не участвуют — их вклад виден аналитическим слоем `query_trace`
   (`v_metrics_*`); алерт-правила по симптомным сигналам observability.md §4. Названия и лейблы
   метрик — observability.md §2.3 (низкая кардинальность: node/role/model/status;
   `user_id` и текст вопроса в спаны и метрики не идут — PII и кардинальность).
4. **Grafana** — дашборды (золотые сигналы в терминах FSM: rate по терминальным
   статусам, доля fail/degrade/rejected, p95 латентности узлов и TTFT, сатурация —
   пул соединений и состояние breaker), поиск трейса по `trace_id` (data source
   Jaeger); Alertmanager — webhook-уведомления (email/Telegram). **Не пейджинг:**
   дежурства нет — уведомление, разбор по таблице §4 observability.md.
5. **`query_trace` остаётся system of record:** бизнес-payload (вопрос, SQL, допущения,
   стоимость) — навсегда, на нём eval-сет и экономика; спаны/метрики — операционный
   слой с коротким retention. `trace_id` прогона = OTel trace_id — ключ связи миров
   (§3 observability.md). Семплирование 100% (объёмы §1 observability.md).

## 5. Последствия

**+**
- сигнал о деградации — минуты, а не веха; алерты по симптомам реальные (§4 observability.md);
- waterfall трейса — точный ответ «где зависло / где деньги» для R-C2/R-C4 без ручного разбора;
- живые дашборды — демонстрация ДЗ-06 и выпускной работы;
- экономика по узлам живым счётчиком (cost-контур ADR-007) — материал для пересчёта §7;
- компетенция стека наблюдаемости (OTel/Prometheus/Grafana/Jaeger) — курсовая ценность.

**−**
- compose растёт с 3 до 6–7 контейнеров (jaeger, prometheus, grafana, alertmanager
  опционально) — self-hosted сопровождение (обновления, диски, «watch the watcher»:
  self-metrics Prometheus и up-таргеты, включая `/metrics` приложения, — в той же Grafana);
- без коллектора: нет единой точки фильтрации/обогащения телеметрии и мульти-sink —
  экспорт идёт из приложения напрямую; потеря некритична (батчинг/retry в SDK,
  best-effort), но возврат коллектора — триггер ниже;
- дашборды и алерт-правила нужно поддерживать; риск «телеметрия ради телеметрии» —
  митируется правилом: каждый алерт/панель отвечает на строку таблицы §4 observability.md;
- SDK в горячем пути — барьер снимается асинхронным экспортом (решено архитектурно).

**Триггеры пересмотра:** сопровождение стека начинает съедать время → откат к C0
(отчётный слой не выброшен, он в коде); корпоративный контур → C2/managed; рост объёмов
спанов → семплирование 10–25%; появились multi-sink, фильтрация/обогащение телеметрии
на пути или второй эмиттер → вернуть OTel Collector (SDK меняет endpoint — env);
появляется Loki → trace-to-logs корреляция; Grafana Alerting заменит Alertmanager
(−1 контейнер) — конфигурационное решение, не архитектурное.
