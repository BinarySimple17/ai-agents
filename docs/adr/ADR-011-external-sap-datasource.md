# ADR-011 — Внешний источник данных SAP (OAuth, исполнение под правами токена)

- **Статус:** Принято (v1.2, 2026-11-18 — RunContext +`user_id`: канал PG выставляет `SET LOCAL app.user_id` (рубеж 5, ADR-005 §4; ruling ARCH-GATE S13). v1.1 — QuerySpec вместо SQL-текста: ручка на ABAP строит Open SQL и проверяет права)
- **Требования prd.md:** §8 (допущения — прод-сцена SAP: подключение с минимальными усилиями), FR-6 (AuthProvider), FR-12 (декомпозиция как механизм федерации)
- **Связанные документы:** ADR-004 (key-set exchange — единственный кросс-базовый джойн), ADR-005 (AuthProvider, RBAC как данные, три рубежа), **ADR-008** (structured output — генерация спеки), ADR-010 (спаны на выполнение SQL, trace_id), security.md §3–4 (PII на границе, токены как секреты), RISKS.md (R-S1, R-D4, R-S5), code-architecture-draft (§4 порт, §5.2 мульти-БД)
- **Контекст принятия:** прод-сцена владельца: пользователь аутентифицируется через SAP (OAuth — страница входа отдаёт токен пользователя); обращения к SAP с этим токеном выполняются под его правами. Агент строит SQL и выполняет его через HTTPS-ручку SAP, получая результат в нормализованном виде. Требование: архитектура и код допускают подключение **с минимальными усилиями**. Реализация — после v1 (hw-plan §7, расширения владельца); решение фиксируется сейчас, чтобы ядро не пришлось переделывать.

---

## 1. Контекст

В v1 единственный канал исполнения — локальный PostgreSQL под сервисной ролью `agent_ro`; права — настройки в БД (ADR-005); валидатор — единственная per-user граница (БД пользователей не различает). Прод-сцена меняет три вещи сразу: (а) identity приходит из SAP по OAuth; (б) исполнение уходит из нашей БД в SAP по HTTPS; (в) права на данные арбитрит SAP, а не наш каталог. Вопрос: где в архитектуре проходят эти границы — аутентификация, права, исполнение, федерация — чтобы подключение SAP было адаптером, а не переделкой ядра.

## 2. Сравнение по осям

| Ось | A: SAP сбоку, вне контура | B: SAP отдельным контуром | C: SAP как datasource за портами |
|---|---|---|---|
| Изменения ядра FSM/валидатора | нет, но валидация/трейс/семантика не работают вовсе | дублируются целиком | **ядро не меняется: адаптер + узел генерации спеки** |
| Валидация запроса | отсутствует | дублируется | **структурная по IR — deny-by-default по схеме спеки, без парсера** |
| Права/безопасность | вне нашего контроля и аудита | второй комплект прав — рассинхрон | **SAP — арбитр; наши настройки — фильтр мира** |
| Федерация PG ↔ SAP | невозможна | два несоединяемых мира | **ADR-004 key-set exchange штатно** |
| Трейс/наблюдаемость | отсутствует | дублируется | **тот же trace_id и спаны (ADR-010)** |
| Усилия | минимальные — ценой отказа от агента | максимальные | **адаптер + RunContext + метаданные** |

## 3. Варианты

### Вариант A — SAP сбоку
Отвергнут: запросы к SAP минуют валидатор, трейс, семантику рёбер и бюджет — это не
агент, а отдельный запросник; данные вне контура прав и аудита.

### Вариант B — второй контур (свой планировщик/права/валидатор для SAP)
Отвергнут: полное дублирование ядра ради другого канала исполнения; рассинхрон двух
комплектов прав — новый класс рисков без выгоды.

### Вариант C — внешний datasource за существующими портами ✅ **ПРИНЯТО**
Агент и сегодня не знает, «где» физически лежат таблицы; канал исполнения — деталь
адаптера. Это и есть смысл порта `SQLExecutor` (c4-l2 «точки роста за портами»).

## 4. Решение

**SAP — внешний datasource за теми же портами; права арбитрит SAP; единственная
правка кода ядра — контекст исполнения в порту.**

1. **Аутентификация:** OAuth-флоу (страница входа SAP → redirect → code → токен) —
   у фронта/портала, не в FSM: браузерная интеракция не встраивается в state machine.
   Агент — resource server: адаптер `SapAuthProvider` за портом `AuthProvider`
   (верификация токена — introspection или JWKS). Контракт «identity из проверенного
   токена» (ADR-005) не меняется.
2. **Контекст исполнения (главная правка кода):** порт `SQLExecutor.execute(request,
   *, ctx: RunContext)` (v1.1: запрос — дискриминированный `QueryRequest`), где
   `RunContext` несёт `trace_id` (= OTel trace_id, ADR-010), `user_id` (v1.2,
   ruling ARCH-GATE S13 — владелец scope; fail-closed непустое), `scope` и
   `token_ref`; RunContext — VO в `domain/` (без внешних зависимостей).
   `PostgresSqlExecutor` игнорирует токен (ходит под `agent_ro`; trace_id и
   user_id — в `SET LOCAL`/`set_config(…, is_local=true)`, рубеж 5 — ADR-005 §4);
   `SapHttpExecutor` кладёт токен в `Authorization: Bearer`, trace_id —
   в заголовок запроса (аудит на стороне SAP).
3. **Исполнение — формализованная спека, не SQL-текст** (решение владельца, v1.1).
   `SapHttpExecutor` принимает `QueryRequest(kind="spec")` и отправляет HTTPS POST с
   **`QuerySpec`** — формализованным IR запроса: таблицы и путь джойна (из JoinPlan —
   LLM их не придумывает), фильтры (колонка / оператор из whitelist / значение-bind),
   проекции, группировка, сортировка, лимит; `key_column` — явное поле (шаги
   декомпозиции без парсинга SQL). **Ручка на стороне ABAP строит по спеке
   динамический Open SQL и проверяет права** (CDS/DCL, AUTHORITY-CHECK) — только так
   «исполнение под правами токена» покрывает авторизации приложения, а не только
   HANA; нативный ADBC отклонён — он эти проверки обходит. Контракт ручки:
   `{spec} → {columns, rows, row_count, truncated}` → нормализация в `QueryResult`.
   Валидация спеки — структурная: таблицы/колонки ∈ scope, джойны ∈ рёбрам графа,
   операторы ∈ whitelist, неизвестное поле спеки → отказ (deny-by-default по схеме
   IR — без парсера). PG-путь не меняется: `QueryRequest(kind="sql")` — текст +
   sqlglot + adversarial-корпус. 401/403 → `degrade`-исход, не retry (refresh —
   один раз, иначе «войдите заново»).
4. **Права per datasource — инверсия рубежа 3:** для SAP-источника арбитр — SAP
   (исполнение под правами токена = максимум того, что пользователь видит и так;
   промах валидатора возвращает 403, а не молчаливую утечку — R-S1 для этого
   источника закрыт по построению). Наши настройки прав **не дублируют** SAP:
   фильтр мира (подграф/RAG/DDL до генерации — модель не видит чужих таблиц) и
   UX-деградация бизнес-понятиями (дешевле HTTP 403 после генерации). Видимость
   метаданных — импорт из SAP-каталога, не ручной ввод.
5. **Каталог источников:** `agent_data_sources` (таблица → `ds_id`, протокол
   `sql` | `spec`; код вычисляет datasource и форму запроса, LLM не знает) —
   draft §5.2; SAP = `ds_id='sap'`, `protocol='spec'`. Ребро графа, пересекающее
   границу источников, форсирует шаг на своём источнике; handoff —
   материализованный key-set (ADR-004: определение распределённого запроса без 2PC).
6. **Диалект/валидатор:** диалектная проблема снимается самим IR — Open SQL нигде
   не представлено текстом: sqlglot остаётся валидатором только PG-пути (текст +
   adversarial-корпус); спека SAP проверяется структурно (п. 3). Генерация для
   SAP — отдельный сервис StructuredSpec за ADR-008 (structured output): LLM
   заполняет только фильтры и проекции; таблицы, путь и тип джойна приходят из
   `plan_joins`. T2 (`EXPLAIN`) — флаг per datasource: недоступен → декомпозиция
   SAP-источника триггерится только T1.
7. **Семантика/память:** SAP-таблицы — узлы графа Neo4j (FK — из импортированных
   метаданных, где доступны; бизнес-рёбра — владелец, ADR-006, `usage_notes` — те
   же); метаданные/DDL — в pgvector с фильтром scope (рубеж 1 не ослабляется).
8. **Наблюдаемость:** спан на SAP-вызов уже предусмотрен ADR-010 (спан на выполнение
   SQL: datasource, row_count, latency); токен в спаны/трейс/логи не попадает никогда
   (security §4).

## 5. Последствия

**+**
- ядро не меняется: FSM, валидатор, память, кэш, экономика, budget — как для PG;
  подключение = адаптер + `RunContext` + импорт метаданных + контракт ручки;
- per-user исполнение сильнее coarse-рубежа: для SAP-источника исчезает класс
  «молчаливой утечки» (R-S1) — SAP сам различает пользователей;
- федерация PG ↔ SAP — штатный механизм ADR-004, а не новое решение;
- trace_id доезжает до SAP — сквозной аудит по одному ключу.

**−**
- новая граница контура: спека запроса и результаты уходят в SAP-ручку — допуск по
  образцу R-S4, фиксируется для прод-контура (PII-правила §3 действуют и здесь);
- выразительность: спека покрывает аналитическое ядро (фильтры/проекции/агрегация/
  сортировка), но не произвольный SQL — window-функции, CASE в SELECT, подзапросы
  в WHERE — v1 нет; расширение спеки, не возврат к тексту;
- ручка — новый сервис в периметре SAP (по сути SQL-шлюз): обязательна авторизация
  вызывающего (сервисная идентичность агента + per-user токен внутри) — иначе
  прямой вызов в обход budget/rate-limit/аудита агента (RISKS R-S5);
- генерация для SAP — отдельный узел со своими промптами/few-shot (ядро FSM,
  лимиты и кэш не меняются);
- T2 может быть недоступен (ручка без EXPLAIN) → SAP-декомпозиция только по T1;
- зависимость от контракта ручки: если SQL-эндпоинта нет — ручку нужно создать на
  стороне SAP (динамический Open SQL в ABAP — стандарт) или трансляция спеки →
  OData/CDS в адаптере — порт не меняется.

**Критерии пересмотра решения (revisit triggers):**
- нужна выразительность за пределами спеки (window-функции, выражения) →
  расширение IR, не возврат к SQL-тексту; OData/CDS-источник → третий протокол
  того же порта (spec → OData-параметры);
- SAP требует сервис-аккаунт вместо per-user токена → возврат к модели `agent_ro`
  для SAP: валидатор снова единственная граница — усилить adversarial-CI (как для
  primary);
- вторая внешняя СУБД → вынести routing/адреса источников из кода в конфиг;
- OAuth refresh не покрывает длинные декомпозиции → pre-refresh токена перед планом
  (по времени жизни).
