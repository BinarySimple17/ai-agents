# ADR-001: готовые Text-to-SQL решения vs собственный агент на LangGraph

- **Статус:** Принято (v1.0)
- **Дата:** 2026-11-14
- **Контекст принятия:** старт архитектурного пакета; проверка гипотезы «изобретаем ли мы велосипед» до фиксации остальных решений
- **Связанные документы:** prd.md (§1–3 проблема/цели), ADR-002 (оркестрация), ADR-005 (RBAC), ADR-006 (семантика связей)

---

## 1. Контекст

Text-to-SQL — популярная ниша с готовыми инструментами. Прежде чем проектировать свой
агент, проверяем, закрывает ли существующее решение обязательные требования кейса и
расширения владельца: RBAC как настройки, декомпозиция тяжёлых запросов, семантика
связей от владельцев данных, каскад моделей с контролем стоимости.

Кандидаты:

- **Vanna.ai** (open-source, MIT) — RAG text-to-SQL: «обучается» на DDL, документации и
  парах «вопрос → SQL» (векторное хранилище), генерирует SQL по похожим примерам;
  есть коннекторы к БД и Streamlit-фронт.
- **LangChain SQLDatabaseChain / create_sql_agent** — цепочка «схема в промпт → SQL →
  (опц.) выполнение»; валидация минимальная, связи таблиц модель угадывает по схеме.
- **LlamaIndex NLSQLTableQueryEngine / SQLAgent** — то же в терминах LlamaIndex:
  контекст схемы + few-shot, генерация одним вызовом.

## 2. Сравнение по осям требований

| Ось | Vanna.ai | LangChain / LlamaIndex | Наше ТЗ | Пересечение? |
|---|---|---|---|---|
| Планирование джойнов | схема + похожие примеры в промпт; связи решает модель | схема в промпт; связи решает модель | граф связей + `shortestPath`; модель ходит **только по реальным рёбрам** | идея общая (схема в контекст), механика разная |
| RBAC per-user | нет (права = права подключения к БД) | нет | права как данные (`agent_permissions`), три рубежа, различение галлюцинация/права | нет |
| Семантика связей (kind/meaning/join_type/usage_notes) | нет — только то, что в DDL | нет | владелец данных вносит бизнес-рёбра поверх FK | нет |
| Декомпозиция тяжёлых запросов | нет — один SQL за прогон | нет | триггеры T1/T2, QueryPlan DAG, key-set exchange | нет |
| Каскад моделей по узлам | одна модель на всё | одна модель на всё | Intent-Based Routing: cheap/mid/strong + эскалация | нет |
| Валидация до выполнения | опционально, без ACL-семантики | SQLDatabaseChain «try run» | AST + граф + ACL **до** выполнения; текст LLM не доверенный | частично (идея) |
| Кэш со скоупом прав | нет | нет | ключ (scope, вопрос), namespace'ы по ролям | нет |
| few-shot по примерам | есть (ядро подхода) | есть | есть у нас — как приём, не как основа | **да, прямое пересечение** |

**Итог сверки:** пересечение по приёму «схема + примеры в контекст» — существенное,
подход проверен. Пересечение по архитектурным требованиям — нулевое: ни один кандидат
не планирует джойны по графу с семантикой рёбер, не держит права как данные и не
декомпозирует тяжёлые SQL. Критичные требования (RBAC-сцены трёх персон, бизнес-рёбра
владельцев, T1/T2, каскад с бюджетом 2 ₽) готовые решения **не закрывают и в roadmap
не содержат** — их прирост идёт в сторону генерации дашбордов и авто-обучения, не в
сторону контроля.

## 3. Рассмотренные варианты

### Вариант A — взять Vanna.ai как основу
Отвергнут. Закрывает FR-1/FR-3 частично (вопрос → SQL), но не закрывает FR-4…FR-7
вообще: валидации до выполнения с ACL нет, прав как настроек нет, семантики рёбер нет.
Чтобы довести до ТЗ, пришлось бы встраиваться внутрь его генератора — поддерживать
чужой код, который архитектурно решает не нашу задачу.

### Вариант B — форкнуть и расширить готовое
Отвергнут. Расширения составляют **всю** нашу архитектуру (граф связей, RBAC,
декомпозиция, каскад): форк даёт нам чужой retrieval-слой, который у нас и так есть
(pgvector + глоссарий + few-shot), плюс обязательство следить за upstream.

### Вариант C — готовое как зависимость для части конвейера
Отвергнут на v1. Единственная заимствуемая часть — подбор few-shot примеров; она —
полтора запроса к pgvector, изолирована за портом `VectorStore`. Если когда-нибудь
понадобится более хитрый выбор примеров — заменим адаптер, а не архитектуру.

### Вариант D — собственный агент на LangGraph ✅ **ПРИНЯТО**
Основание: совпадает с ТЗ и не дублирует готовое по существу. См. §4.

## 4. Решение

**Строим собственный агент на LangGraph (workflow-скелет с агентным ядром — ADR-002);
готовые Text-to-SQL решения фиксируем как prior art и источник приёмов.**

Заимствуем проверенное:

1. **Индексация «обучения» как данных:** Vanna держит DDL/доки/примеры в векторном
   хранилище — у нас то же (pgvector: DDL с комментариями, глоссарий, few-shot),
   подтверждаем форму, меняем содержание (добавляются связи с семантикой).
2. **Примеры как главный рычаг качества SQL** — few-shot остаётся в контексте каждого
   вызова `generate_sql`.
3. **Опыт их отказов:** в issues Vanna/LangChain типовые провалы — галлюцинация таблиц
   и связей, потеря контроля над повторными выполнениям; у нас это закрыто
   архитектурно (граф + валидатор до выполнения) — и это подтверждает выбор.

## 5. Последствия

**Положительные:**
- Каждое нетривиальное требование (RBAC, семантика, декомпозиция, каскад) живёт в
  нашей архитектуре, а не в патчах поверх чужой.
- Все решения трассируются в ADR-пакет — защита и ревизии не зависят от внутренностей
  сторонней библиотеки.
- Стек минимальный: LangGraph + драйвер PostgreSQL + Valkey — без «мета-фреймворка»
  поверх фреймворка.

**Отрицательные / риски:**
- Собственная инженерия всех контуров — осознанно. Митигируется слоением
  (code-architecture-draft: порты/адаптеры) и тем, что retrieval-часть — стандартные
  компоненты, а не своя наука.
- Риск переизобретать плохо то, что готовое делает хорошо (подбор примеров, кэш).
  Митигируется: приемы заимствованы сознательно (п. 1–3 §4), компоненты за портами.

**Критерии пересмотра решения (revisit triggers):**
- У Vanna (или аналога) появляется планируемый джойн-контур по графу схемы + per-user
  ACL как данные → пересмотреть Вариант B/C.
- Собственный eval-сет покажет, что наш `generate_sql` систематически хуже
  «обученной» Vanna на тех же вопросах → пересмотреть few-shot-стратегию (не основу).
