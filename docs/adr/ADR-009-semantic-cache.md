# ADR-009: кэш вопросов Valkey со scope в ключе (точное совпадение)

- **Статус:** Принято (v1.2 — 2026-11-15, решение владельца: без семантической близости — точное совпадение вопроса + TTL-справочные шаги; у запиненного Valkey нет KNN-поиска, FIX-005; v1.1 — позиция lookup, put-оркестратор, реплей декомпозиции; ревизия 02)
- **Дата:** 2026-11-14
- **Контекст принятия:** повторные и перефразированные вопросы — норма аналитики; кэш желателен, но при per-user правах наивный кэш опасен (отравление между доменами); после перевода `generate_sql` на deepseek экономика кэша пересматривалась
- **Связанные документы:** prd.md (§4 FR-13, §5 NFR-4), ADR-003 (Valkey — не хранилище истины), ADR-005 (scope в ключе — следствие RBAC), ADR-007 (кэш перестал быть рычагом стоимости)

---

## 1. Контекст

Аналитические вопросы повторяются: тот же вопрос днём и вечером, перефразировка
(«выручка по Германии в октябре» / «сколько заработали на клиентах из Германии за
октябрь»), справочные запросы (список активных кампаний, сегменты) — сотни раз в
день. Без кэша каждый повтор — полный цикл агента: LLM-вызовы, latency, деньги.

Требование безопасности делает кэш нетривиальным: **SQL, построенный для
пользователя с правами HR, нельзя отдавать пользователю-логисту** — наивный кэш
«вопрос → SQL» отравляется между доменами. Плюс after-the-fact пересмотр: когда
`generate_sql` переехал с флагмана на deepseek (ADR-007), стоимость среднего вызова
стала копейками, и кэш перестал быть главным рычагом экономики — его роль нужно
переопределить честно.

## 2. Сравнение по осям

| Ось | A: без кэша | B: кэш по точному совпадению вопроса | C: семантический кэш, ключ (scope, вопрос) | D: полагаться на KV-кэш провайдера |
|---|---|---|---|---|
| Повторы дословно | полный цикл | попадание | попадание | частичное (кэш-чтение токенов) |
| Перефразировки | полный цикл | **мимо** | **попадание** (векторная близость) | мимо |
| Изоляция доменов | н/д | **нет — отравление между доменами** | **да: scope — часть ключа** | н/д (кэширует токены, не ответы) |
| Экономия денег | — | есть | ограничена после ADR-007 (0,62 → 0,61 ₽ при hit rate 30%) | есть на входных токенах |
| Экономия latency (TTFT) | — | есть | **есть — главный эффект** | есть |
| Кэш справочных шагов декомпозиции | нет | нет | **да, с TTL** (самые частые попадания — шаг не выполняется вовсе) | нет |

## 3. Рассмотренные варианты

### Вариант B — кэш по точному совпадению
Отвергнут как основной: перефразировки мимо, а точные повторы покрываются семантическим
кэшем superset'ом. Остаточное применение — нет (сравнение на равенство — частный
слой семантического поиска).

### Вариант D — только KV-кэш провайдера
Отвергнут как альтернатива, принят как **сопутствующий эффект**: qwen-тариф имеет
кэш-чтение 0,64 ₽ (против 3,20 ₽ входа) — повторные вызовы классификационных узлов
уже дешевле без нашей инфраструктуры. Это снижает денежную ценность нашего кэша и
подтверждает его переориентацию на latency и справочные шаги.

### Вариант A — без кэша
Отвергнут: TTFT-эффект на повторах и кэш справочных шагов декомпозиции остаются
ценными, даже когда деньги перестали быть главным аргументом.

### Вариант C ✅ **ПРИНЯТО**

## 4. Решение

**Кэш вопросов на Valkey по точному совпадению: «тот же (нормализованный) вопрос →
готовый SQL». Ключ кэша = (scope, вопрос); few-shot и глоссарий живут в namespace'ах
по ролям. Семантическая близость («похожий вопрос») исключена решением владельца
(v1.2): у запинанного Valkey нет KNN-поиска, а ссылка на него делала решение
нереализуемым; перефразировки идут полным циклом — осознанный трейд в пользу
простоты и нулевого класса ложных hit'ов (риск R-Q5 снят по построению).**

Правила:

1. **Scope — часть ключа, не метадата.** Записи разных прав физически не пересекаются:
   SQL, построенный под правами HR, не найдётся запросом логиста — изоляция доменов
   структурная, а не дисциплиной кода (NFR-4: 0 утечек через кэш).
2. **Namespace'ы по ролям для RAG-словаря:** глоссарий и few-shot выдаются из
   namespace'а scope — модель не видит даже существования чужих таблиц.
3. **Кэш справочных шагов декомпозиции с TTL** (ADR-004): список активных кампаний,
   сегменты — результаты промежуточных шагов кэшируются; это самые частые попадания,
   шаг вообще не выполняется.
4. **`interpret_result` кэшированию не подлежит** — зависит от фактических строк
   результата, а не от вопроса.
5. **Инвалидация:** права изменились (счётчик `settings_version` вырос — ADR-005 §4)
   → старые записи scope считаются недействительными по версии; справочные шаги —
   TTL; статистика hit/miss — в трейс (FR-11).
6. **Допущения `clarify` — в значении кэша, сверка на hit (обязательное правило).**
   Ключ (scope, embedding) не покрывает **вопросные** допущения: фильтры
   (`status='paid'`), границы периода, выбор варианта метрики. Перефразировка
   «выручка за октябрь по оплаченным» семантически близка к кэшу «выручка за октябрь» —
   наивный hit выполнил бы кэшированный SQL **без фильтра**, и валидация этого не
   увидит (SQL структурно валиден). Поэтому: при `put` в значение пишутся допущения
   `clarify`; при `get` сверяются с допущениями текущего вопроса (LLM-сверка на
   cheap-модели или точная нормализация); не совпали → hit считается miss, вопрос
   идёт полным циклом. Кэшированный SQL выполняется только при совпадении
   допущений — иначе класс «уверенно неверная цифра» воскрешается через P1-компонент.
   **Позиция lookup — после `clarify`, до `plan_joins`** (ревизия 02 §3.3): сверять
   допущения можно только когда они уже зафиксированы текущим вопросом; бонус
   позиции — на хите экономятся retrieval и shortestPath.

**Реплей декомпозиции из кэша.** Кэшируются не только одиночные SQL: в значении
рядом с допущениями лежат `query_plan` + `sql_steps` шаблонов шагов. Хит
декомпозированного вопроса входит прямо в цикл шагов (`validate_step →
execute_step`), минуя `plan_query` и `generate_step`; валидация каждого шага не
пропускается. `put` делает **оркестратор** — по факту успешного прогона, когда
есть и результат, и допущения (не `resolve_access`; ревизия 02 §3.3).

**Честная переоценка роли** (следствие ADR-007): денежная экономия кэша SQL
минимальна — 0,62 ₽ → 0,61 ₽ при hit rate 30% (`generate_sql` на deepseek стоит
копейки; до перевода это был главный рычаг). Оставшиеся ценности кэша: **TTFT на
повторах**, **справочные шаги** (шаг не выполняется вовсе), **разгрузка RPM/TPM**
лимитов шлюза. Кэш остаётся в архитектуре как P1-компонент с ясной, но уже не
денежной мотивацией.

## 5. Последствия

**Положительные:**
- Отравление между доменами исключено структурно (scope в ключе, namespace'ы
  словаря) — отказ #12 из реестра README §6 закрыт по построению.
- Точные повторы обходят полный цикл: выигрывает latency и лимиты провайдера
  (§4.4 README); перефразировки — полным циклом (v1.2, осознанно).
- Справочные шаги декомпозиции получают «бесплатное» ускорение с TTL.

**Отрицательные / риски:**
- Денежный эффект теперь пренебрежим (0,61–0,62 ₽) — ценность кэша в latency:
  если TTFT дешёвых моделей упадёт ниже порога восприятия, компонент может быть
  упрощён до кэша справочных шагов.
- **Ложноположительный hit.** С v1.2 класс «близкая перефразировка» исключён по
  построению (близости нет). Остаточный случай — вопросные допущения при точном
  повторе (`clarify` недетерминирован; валидацией не ловится, SQL структурно
  валиден) — закрыт правилом 6: сверка допущений в значении кэша. Ранний сигнал —
  `agent_cache_hits_total{result="assumption_miss"}` > 1% hit'ов, жалобы
  «цифра не сходится».
- Valkey — ещё один компонент стека; единственный с правом быть вне PostgreSQL
  (ADR-003): он кэш, потеря содержимого — деградация скорости, не потеря данных.

**Критерии пересмотра решения (revisit triggers):**
- Логи показывают устойчивую потребность в перефразировках (точные повторы редки) →
  вернуться к близости механизмом pgvector (не Valkey — KNN там нет; правила 1–6
  и scope-изоляция не меняются) — точка будущего ADR, не правка этого.
- Hit rate < 10% на реальных логах → сократить кэш до справочных шагов (п. 3).
- Появление истории диалога (open #1 prd) → ключ расширяется сессией/липким scope,
  инвалидация по правам сохраняется.
- Переход на другой тариф/провайдер (ADR-007 revisit) → пересчёт роли KV-кэша
  провайдера vs наш слой.
