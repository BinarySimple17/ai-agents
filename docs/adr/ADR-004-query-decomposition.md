# ADR-004: декомпозиция тяжёлых запросов (аналог FOR ALL ENTRIES)

- **Статус:** Принято (v1.1 — ограничение кольца T2, ревизия 02)
- **Дата:** 2026-11-14
- **Контекст принятия:** расширение владельца к кейсу; решено реализовывать в учебном проекте сразу, с планом Б (заглушка) при нехватке времени
- **Связанные документы:** prd.md (§4 FR-12), ADR-002 (цикл шагов в state machine), ADR-003 (один снапшот), ADR-007 (эскалация при retry), ADR-008 (QueryPlan — структурированный выход)

---

## 1. Контекст

Одиночный SQL на 5+ таблиц с громоздкими джойнами рискует таймаутом, дорогим планом
и длинным неинформативным retry: ошибка перегенерирует весь запрос. В ABAP-мире эта
проблема решается паттерном `FOR ALL ENTRIES`: первый SELECT кладёт внутреннюю
таблицу ключей, следующий выбирает `... FOR ALL ENTRIES itab` — разбиение одного
тяжёлого statement на цепочку простых. Вопрос: переносим ли паттерн в агент, и если
да — кто решает, когда декомпозировать?

Ограничения, без которых переносить нельзя: ключи подставляются **только**
bind-параметрами; пустой набор ключей в ABAP — известная ловушка (FAE без защиты
выбирает **всё**); длинный FAE бьётся на пакеты; всё должно выполняться в одном
снапшоте, иначе шаги увидят разные данные.

## 2. Сравнение по осям

| Ось | A: всегда одиночный SQL | B: CTE / temp-таблица | C: key-set декомпозиция (FAE-аналог) |
|---|---|---|---|
| План для БД | один сложный план | план оптимизируется внутри одной инструкции | каждый шаг — план на ≤ 3 таблиц, простой и предсказуемый |
| Retry-гранулярность | весь запрос | весь запрос | **только упавший шаг** |
| Валидация | один большой SQL | один большой SQL | короткий SQL на шаг — валидатору легче, adversarial-покрытие надёжнее |
| Control flow | нет | нет | **управляемый кодом**: short-circuit, капы, честные остановки |
| Мульти-БД | невозможен | невозможен | **единственный механизм** джойна между инстансами (key-set exchange) |
| Стоимость/латентность | базовая | лучше A | +6% стоимости, N последовательных шагов (медленнее при слабом триггере) |
| Сложность | — | низкая (SQL) | высокая (DAG, guardrails, merge) — природа решения |

## 3. Рассмотренные варианты

### Вариант A — всегда одиночный SQL
Отвергнут как единственный режим: у тяжёлых запросов нет ни гранулярности retry,
ни контроля переполнения. Остаётся как режим по умолчанию для лёгких запросов.

### Вариант B — CTE (`WITH ... AS MATERIALIZED`) / temp-таблицы
Отвергнут как основной режим, признан сильным на одном PostgreSQL: та же работа
внутри одной инструкции обычно быстрее client-side слияния. Осознанный компромисс:
на одном PG CTE часто оптимальнее нашей декомпозиции — поэтому декомпозиция
**триггерная**, а не режим по умолчанию. В учебном проекте механизм реализуется
полностью: лучший полигон для циклов state machine, per-step guardrails и
динамического роутинга (эскалации).

### Вариант D — LLM сам решает, декомпозировать ли
Отвергнут: порог должен быть детерминированным, иначе дешёвые запросы деградируют
в декомпозицию (дороже и медленнее), а тяжёлые проскакивают. Решение принимает код.

### Вариант C — key-set декомпозиция с детерминированными триггерами ✅ **ПРИНЯТО**

## 4. Решение

**Тяжёлый запрос разбивается на DAG простых шагов с передачей key-set через
bind-параметры; слияние делает детерминированный код. Триггер — код, не LLM.**

**Триггеры (два, оба детерминированные):**
- **T1 — структурный** (после `plan_joins`, бесплатно): ≥ 4 таблиц или путь ≥ 3 хопов
  → декомпозиция сразу, не тратя вызов на заведомо тяжёлый SQL;
- **T2 — по стоимости плана** (узел `check_cost`): `EXPLAIN` (никогда `EXPLAIN
  ANALYZE` — он выполняет запрос) над валидированным SQL; cost выше порога или
  оценка строк промежуточного джойна > 1M → декомпозиция; уже сгенерированный SQL
  передаётся планировщику как контекст.
- **Ограничение кольца T2** (ревизия 02 §3.4): повторное срабатывание T2 на
  откатившемся к одиночному SQL запросе расходует **общий retry-бюджет**; второе
  T2 → терминал overflow-класса («сузьте период/сегмент»), а не новый круг
  декомпозиции — кольцо `check_cost → plan_query → откат → generate_sql →
  check_cost` ограничено счётчиком, а не только денежным капом (иначе ~3 круга
  по 2 LLM-вызова до `budget_stop` на заведомо тупиковом пути).

**QueryPlan** — DAG из ≤ 4 шагов, каждый шаг соединяет ≤ 3 таблиц; `key_column` —
реальная PK/FK-колонка графа; инварианты проверяет код при парсинге (топологический
порядок, ацикличность, whitelist key-колонок). Невалидный план → один retry
`plan_query`, затем откат к одиночному SQL.

**Правила выполнения шагов (guardrails, все — в коде):**

| Правило | Что защищает |
|---|---|
| Только bind: `WHERE x = ANY(%s)`, конкатенация ключей запрещена | инъекции + разгром кэша планов |
| Пустой key-set → short-circuit: зависимые шаги не выполняются, честное «данных нет» | ловушка пустой itab ABAP: без защиты шаг выбрал бы всё |
| Кап key-set: `LIMIT max_keys + 1`, переполнение → остановка + уточняющий вопрос | молча обрезать нельзя — все downstream-цифры станут неверными |
| Чанки по 1000 ключей: дедуп, сортировка, последовательные запросы, merge в коде | аналог разбиения длинного FAE |
| `LIMIT max_keys+1` на промежуточных шагах; `LIMIT 1000` — только финал | политика лимитов по типам шагов |
| Все шаги в одной транзакции `REPEATABLE READ` | N SELECT'ов видят один снапшот (ADR-003); **осознанный трейд**: LLM-вызовы между шагами держат транзакцию открытой 20+ с — pin `xmin` (bloat/vacuum) и занятое соединение пула; в v1 (7 таблиц, мало пользователей) норма, при параллелизме — пересборка снапшотной модели (`pg_export_snapshot` + `SET TRANSACTION SNAPSHOT` на каждый execute, транзакция не живёт поверх LLM-времени) |
| Каждый шаг валидируется как полноценный SQL (AST + ACL + граф) | шаг — не «доверенный внутренний» SQL |
| Retry-бюджет **общий на план** (≤ 3) | иначе 4 шага × 3 попытки размывают защиту от dead loop |

Retry упавшего шага уходит в `diagnose_error` с контекстом шага (SQL, ошибка,
`purpose`, статистика key-set); регенерируется только шаг. Роутинг при retry —
эскалация вверх (ADR-007).

## 5. Последствия

**Положительные:**
- Retry-гранулярность: перегенерируется упавший шаг, не весь запрос; на тяжёлых
  запросах декомпозиция окупается (0,65 ₽ против 0,67 ₽ у одиночного SQL с двумя
  полными ретраями — и он чаще упирается в таймаут).
- Валидатор получает короткие SQL — adversarial-покрытие надёжнее.
- Готовый фундамент федерации: между двумя инстансами JOIN физически невозможен,
  key-set exchange — единственный механизм соединения (open #3).

**Отрицательные / риски:**
- +6% стоимости (`plan_query` + 3 шага на deepseek) и латентность N последовательных
  шагов — p95 декомпозированных меряется отдельно (< 25s).
- На одном PostgreSQL CTE обычно оптимальнее — поэтому триггер, а не режим по
  умолчанию; target: decomposition rate < 20%.
- Сложность состояния: `query_plan`, `step_results`, `current_step`, `decomposed` —
  компенсируется тем, что каждый шаг — отдельный проход графа (гранулярность trace).
- **Долгая RR-транзакция поверх LLM-времени** — зафиксированный трейд (правило 6 §4):
  один прогон держит соединение пула 20+ с и пинует `xmin`. Триггер пересмотра —
  pool wait time / возраст `xmin` на мониторинге; путь перехода —
  `pg_export_snapshot` + `SET TRANSACTION SNAPSHOT` (тот же снапшот без удержания
  соединения между шагами).

**План Б (зафиксирован заранее):** декомпозиция — оптимизация, а не критический путь.
При нехватке времени узел `plan_query` заменяется заглушкой «всегда не декомпозировать»
— базовый цикл с T1/T2 и одиночным SQL работает, заглушка прозрачна для архитектуры.

**Критерии пересмотра решения (revisit triggers):**
- Eval-сет покажет, что T2 срабатывает на запросах, где CTE быстрее, — уточнить
  пороги/единицы cost (open #3), возможно добавить проверку «CTE vs декомпозиция»
  на план.
- Рост overflow rate (> 5%) — сигнал проблем фильтров/схемы, не повод поднимать кап.
- Появление второй БД — декомпозиция из оптимизации становится обязательной.
- Ожидание пула соединений / рост возраста `xmin` (первый параллелизм) —
  пересборка снапшотной модели на `pg_export_snapshot` (см. правило 6 §4).
