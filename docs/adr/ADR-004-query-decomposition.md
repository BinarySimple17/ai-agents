# ADR-004: декомпозиция тяжёлых запросов (key-set exchange)

- **Статус:** Принято (v1.3 — 2026-11-18, пост-приёмочный патч по отзыву (D-019): T2-исходы уточнены — approximate/matview идут через `compact_result → interpret_result` с флагом `approximate` (пользователь получает полноценное объяснение), async/отказ — терминальные исходы; ретрай шага декомпозиции проговорён явнее. v1.2 — A2/A8/A9/A10/A3 (T2 → async/matview/approximate/отказ, key-set 50 000, T1 — основной путь); v1.1 — ограничение кольца T2)
- **Дата:** 2026-11-14
- **Контекст принятия:** расширение владельца к кейсу; решено реализовывать в учебном проекте сразу
- **Связанные документы:** prd.md (§4 FR-12), ADR-002 (цикл шагов в state machine), ADR-003 (один снапшот), ADR-007 (эскалация при retry), ADR-008 (QueryPlan — структурированный выход)

---

## 1. Контекст

Одиночный SQL на 5+ таблиц с громоздкими джойнами рискует таймаутом, дорогим планом
и длинным неинформативным retry: ошибка перегенерирует весь запрос. Решение —
key-set декомпозиция (semi-join по массиву ключей, batch-fetch): первый SELECT
достаёт ключи, следующий выбирает `WHERE key = ANY(...)`, разбиение одного тяжёлого
statement на цепочку простых. Вопрос: когда декомпозировать, и кто решает?

Ограничения, без которых переносить нельзя: ключи подставляются **только**
bind-параметрами; пустой набор ключей — известная ловушка (без защиты шаг выбирает
**всё**); длинный batch-fetch бьётся на чанки; всё должно выполняться в одном
снапшоте, иначе шаги увидят разные данные.

## 2. Сравнение по осям

| Ось | A: всегда одиночный SQL | B: CTE / temp-таблица | C: key-set декомпозиция (semi-join по массиву ключей) |
|---|---|---|---|
| План для БД | один сложный план | план оптимизируется внутри одной инструкции | каждый шаг — план на ≤ 3 таблиц, простой и предсказуемый |
| Retry-гранулярность | весь запрос | весь запрос | **только упавший шаг** |
| Валидация | один большой SQL | один большой SQL | короткий SQL на шаг — валидатору легче, adversarial-покрытие надёжнее |
| Control flow | нет | нет | **управляемый кодом**: short-circuit, капы, честные остановки |
| Мульти-БД | невозможен | невозможен | **единственный механизм** джойна между инстансами (key-set exchange) |
| Стоимость/латентность | базовая | лучше A | +6% стоимости, N последовательных шагов (медленнее при слабом триггере) |
| Сложность | — | низкая (SQL) | высокая (DAG, guardrails, merge) — природа решения |

## 3. Рассмотренные варианты

### Вариант A — всегда одиночный SQL
Отвергнут как единственный режим: у тяжёлых запросов нет ни гранулярности retry,
ни контроля переполнения. Остаётся как режим по умолчанию для лёгких запросов.

### Вариант B — CTE (`WITH ... AS MATERIALIZED`) / temp-таблицы
Отвергнут как основной режим, признан сильным на одном PostgreSQL: та же работа
внутри одной инструкции обычно быстрее client-side слияния. Осознанный компромисс:
на одном PG CTE часто оптимальнее нашей декомпозиции — поэтому декомпозиция
**триггерная**, а не режим по умолчанию. В учебном проекте механизм реализуется
полностью: лучший полигон для циклов state machine, per-step guardrails и
динамического роутинга (эскалации).

### Вариант D — LLM сам решает, декомпозировать ли
Отвергнут: порог должен быть детерминированным, иначе дешёвые запросы деградируют
в декомпозицию (дороже и медленнее), а тяжёлые проскакивают. Решение принимает код.

### Вариант C — key-set декомпозиция с детерминированными триггерами ✅ **ПРИНЯТО**

## 4. Решение

**Тяжёлый запрос разбивается на DAG простых шагов с передачей key-set через
bind-параметры; слияние шагов — детерминированный код (`merge_results`). Триггер —
код, не LLM. Декомпозиция — ради корректности структурно сложного запроса, не ради
цены: разбиение одиночного плана на «ключи → `= ANY(array)`» (semi-join по массиву
ключей, batch-fetch) обычно медленнее одиночного — теряется оптимизация плана,
растут round-trips.**

**Триггеры (два, оба детерминированные, решают разные проблемы):**
- **T1 — структурный** (после `plan_joins`, бесплатно): ≥ 4 таблиц или путь ≥ 3 хопов
  → декомпозиция. **T1 — основной путь на боевом масштабе** (сотни таблиц): структурно
  сложный запрос корректнее считать шагами. На отладочном стенде из 7 таблиц T1 не
  срабатывает, `plan_query` — заглушка «не декомпозировать» — оговорка стенда, не
  дизайна.
- **T2 — по стоимости плана** (узел `check_cost`): `EXPLAIN` (никогда `EXPLAIN
  ANALYZE` — он выполняет запрос) над валидированным SQL; cost выше порога или
  оценка строк промежуточного джойна > 1M → тяжёлый **одиночный** план ведёт
  **не в декомпозицию**, а в: async-задачу / matview / приблизительный расчёт /
  отказ с рекомендацией («сузьте период/сегмент»). **approximate/matview — через
  `compact_result → interpret_result` с флагом `approximate`**: пользователь
  получает полноценное объяснение результата; async/отказ — терминальные исходы
  без объяснения. Порог T2 — advisory; реальный
  страж — `statement_timeout`. Повторного кольца «T2 → декомпозиция → откат» нет по
  построению (правило кольца v1.1 снято вместе с самим кольцом).

**QueryPlan** — DAG из ≤ 4 шагов, каждый шаг соединяет ≤ 3 таблиц; `key_column` —
реальная PK/FK-колонка графа; инварианты проверяет код при парсинге (топологический
порядок, ацикличность, whitelist key-колонок). Невалидный план → retry по политике
M1 (ADR-007 §4.1), исчерпание → откат к одиночному SQL.

**Лимиты прогона (A10):** `deadline = 90 s`, `statement_timeout = 30 s`,
`max_sql_executions = 4`; остаток времени проверяется **перед каждым выполнением**
SQL и **перед каждой эскалацией** модели; не хватает — честный отказ / incomplete.

**Правила выполнения шагов (guardrails, все — в коде):**

| Правило | Что защищает |
|---|---|
| Только bind: `WHERE x = ANY(%s)`, конкатенация ключей запрещена | инъекции + разгром кэша планов |
| Пустой key-set → short-circuit: зависимые шаги не выполняются, честное «данных нет» | ловушка пустого набора: без защиты шаг выбрал бы всё |
| Промежуточный key-set — **полный, без `LIMIT`**; кап кардинальности **50 000 ключей**, превышение → async / отказ / флаг `approximate` (A2) | усечение промежуточного шага тихо занижает финальную сумму; молча обрезать нельзя — все downstream-цифры станут неверными; неполное не выдаётся за полное (`approximate`) |
| Чанки по 1000 ключей: дедуп, сортировка, последовательные запросы, merge в коде | разбиение длинного batch-fetch |
| `LIMIT 1000` — только финальный пользовательский результат, с флагом усечения в ответе | политика лимитов по типам шагов |
| Агрегация поверх fan-out ребра (`cardinality`/`fanout_guard`, ADR-006) — только с предагрегацией в CTE (A3) | двойной счёт — самый частый класс тихих ошибок Text-to-SQL |
| Все шаги в одной транзакции `REPEATABLE READ` | N SELECT'ов видят один снапшот (ADR-003); **осознанный трейд**: LLM-вызовы между шагами держат транзакцию открытой 20+ с — pin `xmin` (bloat/vacuum) и занятое соединение пула; в v1 (7 таблиц, мало пользователей) норма, при параллелизме — пересборка снапшотной модели (`pg_export_snapshot` + `SET TRANSACTION SNAPSHOT` на каждый execute, транзакция не живёт поверх LLM-времени) |
| Каждый шаг валидируется как полноценный SQL (AST + ACL + граф) | шаг — не «доверенный внутренний» SQL |
| Попытки по политике M1: ≤ 3 на узел + глобальные капы прогона (≤ 8 LLM-вызовов / ≤ 90 s / ≤ 2 ₽) | иначе 4 шага × 3 попытки размывают защиту от dead loop |

Retry упавшего шага уходит в `diagnose_error` с контекстом шага (SQL, ошибка,
`purpose`, статистика key-set); регенерируется **только упавший шаг, не весь план** —
`diagnose_error → generate_step_sql`; перегенерация целого плана дороже и шире по
поверхности ошибки. Роутинг при retry —
политика M1 (ADR-007 §4.1): попытка 2 — та же модель + текст ошибки, попытка 3 —
уровень вверх при достатке бюджета.

## 5. Последствия

**Положительные:**
- Retry-гранулярность: перегенерируется упавший шаг, не весь запрос; структурно
  сложный запрос (T1) корректнее считать шагами, чем одним планом на 5+ таблиц.
- Валидатор получает короткие SQL — adversarial-покрытие надёжнее.
- Готовый фундамент федерации: между двумя инстансами JOIN физически невозможен,
  key-set exchange — единственный механизм соединения (open #3).
- Тяжёлые одиночные планы (T2) имеют штатные исходы (async/matview/approximate/
  отказ с рекомендацией), а не разбиение «для цены»; approximate/matview —
  с полноценным объяснением через `interpret_result` (флаг `approximate`).

**Отрицательные / риски:**
- Стоимость `plan_query` + N шагов и латентность N последовательных шагов —
  p95 декомпозированных меряется отдельно (< 25s); декомпозиция — ради корректности,
  не ради цены (§4).
- На одном PostgreSQL CTE обычно оптимальнее — поэтому триггер, а не режим по
  умолчанию; target: decomposition rate < 20%.
- Сложность состояния: `query_plan`, `step_results`, `current_step`, `decomposed` —
  компенсируется тем, что каждый шаг — отдельный проход графа (гранулярность trace).
- **Долгая RR-транзакция поверх LLM-времени** — зафиксированный трейд (правило 6 §4):
  один прогон держит соединение пула 20+ с и пинует `xmin`. Триггер пересмотра —
  pool wait time / возраст `xmin` на мониторинге; путь перехода —
  `pg_export_snapshot` + `SET TRANSACTION SNAPSHOT` (тот же снапшот без удержания
  соединения между шагами).

**Критерии пересмотра решения (revisit triggers):**
- Eval-сет покажет, что T1 срабатывает на запросах, где CTE быстрее, — уточнить
  пороги/единицы cost (open #3), возможно добавить проверку «CTE vs декомпозиция»
  на план.
- Рост overflow rate (> 5%) — сигнал проблем фильтров/схемы, не повод поднимать кап.
- Появление второй БД — декомпозиция из оптимизации становится обязательной.
- Ожидание пула соединений / рост возраста `xmin` (первый параллелизм) —
  пересборка снапшотной модели на `pg_export_snapshot` (см. правило 6 §4).
