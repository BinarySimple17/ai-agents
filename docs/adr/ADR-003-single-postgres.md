# ADR-003: хранилища — PostgreSQL (pgvector) + Neo4j (граф связей)

- **Статус:** Принято (v2.0 — 2026-11-15, решение владельца после red-team аудита: граф вынесен в Neo4j (вариант C); PG — данные + pgvector + настройки + трейс; официальный образ pgvector вместо кастомной сборки AGE+pgvector; FIX-005. v1.1 — механика path-поиска в AGE; v1.0 — один PG с pgvector + AGE)
- **Дата:** 2026-11-14
- **Контекст принятия:** выбор хранилищ до проектирования retrieval-контура и RBAC; решение закреплено в architecture-draft §3.2 как «ключевое архитектурное решение»
- **Связанные документы:** prd.md (§4 FR-2, FR-3, FR-6), ADR-005 (права живут в той же БД), ADR-006 (граф связей), ADR-004 (декомпозиция требует one snapshot)

---

## 1. Контекст

Агенту нужны три вида данных в одном контуре:

1. **бизнес-данные** — 7 таблиц, по которым строятся запросы;
2. **векторная память** — DDL с комментариями, бизнес-глоссарий, few-shot примеры (RAG для `plan_joins`/`generate_sql`);
3. **граф связей** — FK- и бизнес-рёбра с семантикой, по которому `plan_joins` находит путь джойна (`shortestPath`).

Плюс служебные таблицы прав и связей (`agent_permissions`, `agent_user_roles`,
`agent_relationships`) — тоже данные, и для них важна транзакционность вместе с
бизнес-данными. Требование декомпозиции (ADR-004): все шаги тяжёлого запроса видят
**один снапшот** (`REPEATABLE READ`).

## 2. Сравнение по осям

| Ось | A: три системы (PG + Qdrant + Neo4j) | B: один PG (pgvector + AGE) | C: PG + Neo4j (без отдельного векторного) | C0: один PG + pgvector, граф — BFS в коде |
|---|---|---|---|---|
| Транзакционность прав и данных | разнесены по системам | **один ACID-контур** | один контур, но векторная память — в PG (т.е. это гибрид B) | **один ACID-контур** |
| Один снапшот для шагов декомпозиции | только в PG; граф/вектора вне | **нативно** (`REPEATABLE READ`) | нативно | нативно для SQL-шагов |
| Синхронизация схем между системами | постоянная задача (DDL в двух местах: таблицы и граф) | не нужна — FK-рёбра вычитываются из каталога той же БД | не нужна для FK | **не нужна вовсе** — граф собирается в памяти из каталога |
| Бэкап/восстановление | три технологии, три процедуры | **pg_dump один** | один | **один** |
| DSL для команды | SQL + Cypher + векторные API | **один SQL** (векторные запросы и Cypher внутри PG) | SQL + Cypher | **один SQL** (BFS — свой код) |
| Зрелость графовой части | Neo4j — эталон | AGE — моложе; для графа из 7 таблиц достаточно | Neo4j | **нет зависимости** — но path-логика ручная |
| Ops-нагрузка учебного проекта | 3 контейнера-СУБД, 3 версии, 3 пина | **1 контейнер** | 2 контейнера | **1 контейнер** |
| Перекрёстные запросы («найди разрешённые таблицы → их DDL → их рёбра») | руками склеивать | **джойн между таблицами прав, данными и рёбрами** | частично | **джойны** |

## 3. Рассмотренные варианты

### Вариант A — Postgres + Qdrant + Neo4j
Отвергнут. Для 7 таблиц и графа в десятки рёбер это ops-перебор: три технологии
бэкапа, синхронизация DDL-строк и графовых узлов, рассинхрон прав и данных при
сбоях. Единственный реальный довод «за» — зрелость Neo4j и Qdrant — ниже (§4).

### Вариант B — один PostgreSQL с pgvector + Apache AGE
Отвергнут (v2.0, решение владельца 2026-11-15): в openCypher/AGE нет функции
`shortestPath` (v1.1 обходился var-length-паттерном), движок менее зрел, а
совмещённый образ AGE+pgvector требовал кастомной сборки. На v1.0–v1.1 был принят
(один ACID-контур, один контейнер, один DSL) — история ниже.

### Вариант C — гибрид: PG (данные + права + pgvector) + Neo4j (граф) ✅ **ПРИНЯТО (v2.0)**
Основание: нативный Cypher с `shortestPath`; официальные запиненные образы вместо
кастомной сборки; контракт синхронизации топологии уже существовал (ADR-006 §4);
права, данные и декомпозиция целиком остаются в PG — ACID-контур данных не
разрезается (граф — производная структура, в транзакции шагов не участвует).

### Вариант C0 — вообще без графового движка (BFS в коде)
Честно самый дешёвый вариант по осям: для 7 таблиц и десятков рёбер `shortestPath`
— BFS в памяти за микросекунды; AGE несёт зрелостный риск (признаваемый самим ADR)
при нулевой выгоде на этом масштабе; синхронизация исчезает вовсе — граф собирается
в памяти из каталога при каждом старте запроса. Порт `GraphStore` изолирует замену.
**Отвергнут** по двум причинам: (1) компетенция ДЗ-04 курса — «гибридный поиск через
векторную **и графовую память**»: BFS-в-коде графовую память не демонстрирует;
(2) path-запросы с семантикой (несколько рёбер между таблицами, фильтр по `kind`,
вес ребра) на Cypher декларативны, рукописный BFS растёт в сложности быстрее графа.
Остаётся **точкой отката**: если сопровождение Neo4j окажется тяжёлым для масштаба
проекта — C0 дешевле (одна замена адаптера за портом `SchemaGraphStore`, минус
вторая СУБД).

## 4. Решение

**PostgreSQL — хранилище истины (бизнес-данные, векторная память pgvector, настройки
прав/связей/источников, query_trace); Neo4j — граф связей (только топология рёбер).
Valkey — отдельно, но только как скоростной слой кэша, не как хранилище истины
(ADR-009).**

Ключевые следствия по контурам:

- **RBAC:** права и данные в одной БД — `resolve_access` читает настройки тем же
  контуром, что и исполнение; изменение права — `UPDATE` строки, действует со
  следующего запроса (ADR-005).
- **Retrieval:** pgvector-таблицы — обычные таблицы: метадата-фильтр по scope можно
  делать джойном с правами, а не отдельным индексом-реестром.
- **Граф (Neo4j):** нативный `shortestPath`; рёбра — производная структура: FK-рёбра
  из каталога PG + бизнес-рёбра из `agent_relationships`; синк по счётчику
  `settings_version` и reconciliation-тест — контракт ADR-006 §4 (существовал уже
  для AGE, при Neo4j не меняется). Семантика рёбер — только в PG-строках; Neo4j
  хранит пары узлов + `rel_id`. Граф не участвует в транзакции шагов декомпозиции —
  дрейф топологии не влияет на корректность данных (худший случай — «путь не
  найден», не неверная цифра). Адаптер — за портом `SchemaGraphStore`.
- **Декомпозиция:** все шаги тяжёлого плана — одна транзакция `REPEATABLE READ` на
  одном read-only соединении PG (ADR-004) — данные и ключи в одной СУБД, как и в v1.0.
- **Инфраструктура:** официальные запиненные образы `pgvector/pgvector:0.8.0-pg17` и
  `neo4j:5.26.0-community` — кастомная сборка AGE+pgvector упразднена вместе с её
  локальными рисками; цена — +1 контейнер СУБД; бэкап — только PG (граф
  перестраивается из каталога и настроек).
- **Few-shot — кураторство, не автонаполнение:** источник примеров — успешные прогоны
  из `query_trace` (`status = ok`), но в индекс пример попадает только после
  подтверждения владельцем (та же дисциплина, что рёбра ADR-006 «предложить →
  подтвердил»); дедуп по нормализованному вопросу, лимит на домен. **Защита от
  само-подкрепления ошибок:** авто-включение «успешного по трейсу» запрещено —
  технически валидный, но бизнес-неверный SQL (R-Q2) иначе закрепился бы в памяти
  как эталон.

## 5. Последствия

**Положительные:**
- Нативный Cypher и `shortestPath` — зрелый движок вместо openCypher-подмножества AGE.
- Инфраструктура из официальных запиненных образов (pgvector/pgvector, neo4j) —
  кастомная сборка и её локальные риски упразднены; бэкап — только PG (граф
  перестраивается из каталога и настроек).
- Дрейф «настройки PG ↔ граф» закрыт контрактом ADR-006 §4 (счётчик версий +
  reconciliation-тест в CI) — контракт существовал уже для AGE.
- Перекрёстные проверки (валидация джойна по рёбрам, ACL по правам) — в PG,
  SQL-джойнами, без межсистемного кода.

**Отрицательные / риски:**
- **Вторая СУБД в сопровождении** (+1 контейнер, версии, healthcheck); синк
  топологии стал межсистемным — осознанный трейд, закрытый контрактом ADR-006 §4.
  Граф — производная: потеря Neo4j = деградация планирования до «путь не найден»,
  а не потеря данных.
- Векторный поиск pgvector уступает специализированным движкам на миллионах точек;
  наш объём (DDL + глоссарий + few-shot) — тысячи.
- Один инстанс PG несёт и OLTP-данные, и агентную нагрузку; в production — реплика
  для агентных чтений (не для v1).

**Критерии пересмотра решения (revisit triggers):**
- Сопровождение двух СУБД тяжело для масштаба проекта → откат на C0: BFS в коде за
  портом `SchemaGraphStore`, минус контейнер (движок — деталь адаптера).
- Схема растёт, появляются графовые алгоритмы сложнее `shortestPath` — остаёмся в
  Neo4j (запас зрелости); enterprise-функции не требуются — community-редакции хватает.
- Векторная память выходит на миллионы точек / нужен гибридный поиск (dense+sparse)
  → pgvector заменяется за портом `VectorStore`, остальные контуры не меняются.
- Появляется федерация второй БД (open #3): key-set exchange ADR-004 уже не
  предполагает «всё в одной БД» — декомпозиция остаётся.
