# Model Card — Text-to-SQL Agent

- **Статус:** v1.0 (2026-11-14)
- **Связанные документы:** ADR-007 (каскад и роутинг — владеющее решение), ADR-008 (принудительные форматы), prd.md (§5 NFR-1/2, §6 приёмка), hw-01/README.md §4, §7
- **Формат:** по структуре Model Card (Hugging Face / Google, 2018–2019), адаптирован под систему на **только pre-trained моделях** — собственного обучения нет и не планируется

## 1. Model Details

| Роль в системе | Модель | Тариф (₽/1М ток.: вход / выход / кэш-чтение) | Контекст | Версионирование |
|---|---|---|---|---|
| `clarify`, `plan_joins`, `diagnose_error` (cheap) | `qwen/qwen3.7-flash` | 3,20 / 13 / 0,64 (кэш-запись 4,06; тариф ≤ 32K — запросы агента всегда ~3К токенов) | 1M | параметр вызова через шлюз |
| `generate_sql`, `plan_query`, `generate_step_sql` (mid) | `deepseek/deepseek-v4.1-flash-1017` | 8 / 12 / 0,82 (кэш-запись не поддерживается) | 1M | параметр вызова; reasoning — адресно |
| `interpret_result`, цель эскалации (strong) | `z-ai/glm-5.3-prime` | 299 / 939 / 59 (кэш-запись не поддерживается) | 1M | параметр вызова |
| Эмбеддер (индексация DDL/глоссария/few-shot) | `qwen/qwen3-embedding-8b` | ~1 ₽/1М — не считаем в экономике: объём мизерный | — | `model_version` в метаданных коллекций |

Все три модели — за одним OpenAI-совместимым шлюзом (routerai.ru); узлы знают только
роли `cheap / mid / strong`, конкретные модели — конфиг (ADR-007, NFR-7). Смена
модели = правка конфига + пересчёт экономики §7; смена эмбеддера = переиндексация.

Владелец карточки: архитектор проекта. Лицензии моделей — условия каталога
провайдера; для открытых моделей — open-weight (Qwen, DeepSeek, GLM).

## 2. Intended Use

- **Назначение:** аналитические вопросы к демо-схеме (7 таблиц) с ответом «текст +
  SQL + допущения + стоимость»; roles пользователей — аналитик, кросс-доменный
  аналитик, владелец данных (настройки), администратор (prd §2).
- **Контекст/юрисдикция:** учебный проект (OTUS «AI Agents», HW-01) и пет-проект;
  данные — синтетическая демо-схема, реальное прод — при переходе в пет-проект.
- **Out-of-scope:**
  - ❌ генерация DDL/DML — только `SELECT`; read-only роль — единственный канал исполнения;
  - ❌ единственный источник решений: каждый ответ несёт SQL и допущения — проверяемо человеком;
  - ❌ оценка/ранжирование людей (вопросы типа «кто не был премирован» — аналитика
    по процессам, не кадровое решение); юридические заключения;
  - ❌ свободное исследование данных (exploratory) — одиночный «вопрос → ответ» (v1).

## 3. Training Data

Собственного обучения нет. Данные системы:

- **Корпус знаний:** DDL демо-схемы с комментариями колонок, бизнес-глоссарий
  («выручка» = `SUM(orders.total)`, «новый клиент» = критерий по дате), few-shot
  примеры «вопрос → успешный SQL», связи с семантикой (`meaning`, `usage_notes` —
  ADR-006). Всё — из pgvector с фильтром по scope (ADR-005).
- **LLM-веса — чужие pre-trained** (Qwen/DeepSeek/GLM); bias-профили наследуются.
  Митигация: генерация заземлена (SQL только по плану и графу связей — модель не
  может придумать связь, ADR-006), результат валидируется до исполнения (ADR-005).
- ПДн в индекс не попадают: демо-схема синтетическая; `employees.salary` — PII-колонка,
  закрытая правами по умолчанию.

## 4. Evaluation Results

Пороги приёмки (prd §5 NFR-6, §6):

| Метрика | Порог | Как меряется |
|---|---|---|
| Success rate | ≥ 80% | eval-сет «вопрос → эталонный SQL» |
| Точность пути джойна | ≥ 85% | сверка JoinPlan с эталоном |
| Join semantics accuracy (правильное бизнес-ребро) | ≥ 85% | eval-сет атрибуции (first-touch vs any-touch) |
| Доля уточняющих вопросов | 10–25% | трейс (больше — раздражает, меньше — рискуем допущениями) |
| Retry rate | ≤ 30% | трейс |
| Decomposition rate | < 20% | триггер должен срабатывать редко (ADR-004) |
| Overflow rate | < 5% | рост = проблемы фильтров/схемы |
| p95 latency / TTFT | < 20s / ≤ 3s | трейс (TTFT — контроль инфраструктурного налога) |
| Стоимость запроса | ≤ 0,7 ₽ | трейс, расчёт ADR-007 |

Статус: целевые — до построения eval-сета (open #2 prd); методология отбора моделей —
бенчмарки навыков (SWE-bench/HumanEval — код, MATH — рассуждение, LMArena — язык,
BFCL — tool use) с правилами чтения (низкий = дисквалификатор; риск загрязнения
данных; синдром одной метрики; инфраструктурный налог) — ADR-007 §4.

## 5. Ethical Considerations

- **Прозрачность:** каждый ответ содержит SQL, список допущений и стоимость; допущения
  из `usage_notes` (first-touch) раскрываются в тексте ответа — цифра без допущения
  не считается готовой (SOP п. 7).
- **Честный отказ:** при отсутствии пути между таблицами — уточняющий вопрос, а не
  «придуманный» джойн; при правах — деградация с формулировкой бизнес-понятиями,
  без раскрытия чужой схемы (ADR-005).
- **Подотчётность:** `query_trace` — кто, когда, что спросил, какие допущения, какой
  SQL, сколько стоило; чувствительные запросы («непремированные менеджеры»)
  фиксируются с проверенной личностью (audit — security.md).
- **Справедливость:** система отвечает на аналитические вопросы, не принимает
  кадровые/групповые решения; fairness-метрики неприменимы — зафиксировано сознательно.

## 6. Limitations

- **«Structured output» через шлюз не гарантирован** (наблюдение: reasoning-тело
  рядом с JSON у deepseek-flash) — закрыто двумя слоями ADR-008, но качество слоя
  1 зависит от инфраструктуры.
- **Reasoning-режим включается адресно** (plan_query, эскалация) — на
  классификационных узлах латентность важнее (TTFT).
- **Цены и состав каталога routerai.ru плавают** — расчёт «плюс-минус километр»,
  методика важнее цифр; смена модели — конфиг.
- **Бенчмарки устаревают и могут быть загрязнены** — публичные результаты служат
  proxy; финальная калибровка — собственным eval-сетом (open #2).
- **Одиночный скоуп v1:** без истории диалога, без RLS, без федерации — все три
  заходят поверх готовой архитектуры (revisit-триггеры ADR-002/003/004).
- **Degrade ≠ пустота:** отказ по правам — нормальное поведение, не метрика качества;
  рост degradation rate отслеживается отдельно (README §8).
- Известные риски и митигации — RISKS.md; операционная безопасность — security.md.
