# RISKS.md — риски Text-to-SQL Agent

- **Дата:** 2026-11-14 (living document, пересмотр по триггерам и на вехах)
- **Принцип ранжирования:** внутри каждой группы — по убыванию совокупной оценки
  (вероятность × влияние × стоимость митигации); группы — от наиболее критичной доменно.
- **Шкалы:** Вероятность и Влияние — Н/С/В; Сложность митигации — Н/С/В.
- **Связь с ADR:** значительная часть митигаций уже заложена в ADR-001…009 — это указано
  явно; RISKS.md не дублирует ADR, а сводит риски в один регистр и добавляет то, что в
  ADR не вошло.
- **Ранние индикаторы рисков — потребители сигналов observability.md:** там определены
  источник и способ съёма каждого индикатора (live-метрики Prometheus, логи, query_trace, SQL-отчёт); здесь —
  само пороговое значение и реакция.

## Группа 1. Качество ответов (агентный контур)

### R-Q1. Галлюцинация SQL: несуществующие таблицы/колонки/связи
- **Вероятность:** В · **Влияние:** В · **Сложность:** С
- **Риск:** модель генерирует SELECT по несуществующей структуре или соединяет таблицы
  по домыслу; в лучшем случае — SQL-ошибка (расход retry), в худшем — корректный на вид
  SQL с «творческим» джойном.
- **Митигация:** SQL не строится без JoinPlan (порядок узлов — ADR-002); ход только по
  рёбрам графа, модель не может придумать связь (ADR-006); полный обход AST + сверка
  каждой пары «таблица, колонка» до выполнения (ADR-005); различение галлюцинация/права
  → retry через `diagnose_error` с контекстом ошибки; few-shot и глоссарий в контексте.
- **Ранний индикатор:** рост `validator_reject`-статистики; success rate < 80% на eval-сете.

### R-Q2. Неверное бизнес-ребро / атрибуция (any-touch вместо first-touch)
- **Вероятность:** С · **Влияние:** В (цифры «уверенно неверные») · **Сложность:** С
- **Риск:** технически валидный SQL, бизнес-некорректная цифра: `usage_notes` не попали
  в контекст или модель выбрала ребро из нескольких возможных.
- **Митигация:** `usage_notes` как обязательные допущения в контексте (ADR-006);
  неоднозначная атрибуция → уточнение через `clarify`; тип джойна — из плана, валидатор
  сверяет INNER/LEFT с ребром; `interpret_result` обязан раскрыть допущение;
  join semantics accuracy ≥ 85% на eval-сете атрибуции.
- **Ранний индикатор:** падение join semantics accuracy; жалобы «цифра не сходится с отчётом X».

### R-Q3. Структурированные выходы невалидны → оркестратор ломается
- **Вероятность:** Н (после ADR-008) · **Влияние:** С · **Сложность:** Н
- **Митигация:** два слоя (constrained decoding где доступно + тул-based enforcement —
  ADR-008); валидация инвариантов QueryPlan кодом; откат к одиночному SQL при
  невалидном плане после одного retry.
- **Ранний индикатор:** рост парсинг-ошибок в trace; retry «мусорный JSON».

### R-Q4. Уточняющих вопросов слишком много / слишком мало
- **Вероятность:** С · **Влияние:** Н–С · **Сложность:** Н
- **Митигация:** правило «один вопрос и остановка» (SOP); явная фиксация допущений
  вместо вопроса, когда возможна; целевое окно 10–25% в трейсе; глоссарий снимает
  «дежурные» уточнения метрик.
- **Ранний индикатор:** доля `clarification` вне окна 10–25%.

### R-Q5. Ложноположительный hit кэша — уверенно неверные цифры
- **Вероятность:** С · **Влияние:** В · **Сложность:** С
- **Риск:** ключ (scope, embedding) не покрывает вопросные допущения `clarify`
  (фильтры, период, вариант метрики): перефразировка «по оплаченным» близка к кэшу
  «без фильтра» — кэшированный SQL выполняется, валидация проходит (структурно
  валиден), рёберные допущения раскрыты, а вопросные — нет. Воскрешение R-Q2 через
  P1-компонент.
- **Митигация:** допущения `clarify` — в значении кэша, сверка на hit; не совпали →
  miss и полный цикл (ADR-009 п. 6 — обязательное правило, не опция).
- **Статус (2026-11-15):** класс «близкая перефразировка» исключён решением
  владельца — кэш на точном совпадении (ADR-009 v1.2, FIX-005); остаточный случай —
  вопросные допущения при точном повторе (правило 6), индикатор
  `agent_cache_hits_total{result="assumption_miss"}`.
- **Ранний индикатор:** расхождение paraphrase-hit'ов с эталоном; жалобы «цифра не
  сходится» при совпавших правах.

## Группа 2. Безопасность

### R-S1. Пропуск ACL-валидатора — утечка данных между доменами
- **Вероятность:** Н · **Влияние:** Критич. · **Сложность:** С
- **Риск:** ветка AST-обхода не покрывает конструкцию (подзапрос, CTE, UNION, `t.*`,
  window-функции, `LATERAL`, `DISTINCT ON`, `GROUPING SETS`); БД per-user не
  различает — данные уходят **молча** (цена выбора ADR-005). Валидатор — единственная
  per-user граница без дублирования: всё остальное деградирует честно, это ломается тихо.
  (Исключение — внешние источники с per-user исполнением: SAP, ADR-011 — их БД
  различает пользователей, риск для таких источников закрыт по построению.)
- **Митигация:** **deny-by-default по типам узлов AST** — узел вне whitelist'а
  валидатора → отказ, неполнота превращается в явный отказ, а не пропуск (ADR-005 §4
  п. 1); полный обход AST, разворот `SELECT *`, отсечение каталогов, hardening
  `agent_ro` (запрет `dblink`/`pg_read_file`); **adversarial-тесты в CI обязательны**
  — корпус ≥ поверхности парсера, включая window/LATERAL/DISTINCT ON/GROUPING SETS;
  **property-based сверка**: колонки валидатора = колонки sqlglot на всём корпусе;
  правило «новый путь к данным → тест чужой-тенант»; аудит `degrade` с разбором.
- **Ранний индикатор:** дифф adversarial-корпуса против матрицы конструкций sqlglot;
  рост `degrade`-статистики; любой инцидент-класс.

### R-S2. Отравление кэша между доменами
- **Вероятность:** Н · **Влияние:** В · **Сложность:** Н
- **Митигация:** scope — часть ключа, namespace'ы словаря по ролям (ADR-009);
  инвалидация по версии прав; регресс-тест «cross-scope hit невозможен».
- **Ранний индикатор:** cross-scope hit в логах кэша.

### R-S3. Prompt injection через вопрос или содержимое данных
- **Вероятность:** С · **Влияние:** Н–С (SQL всё равно валидируется) · **Сложность:** Н
- **Митигация:** Rules с приоритетом над инструкциями пользователя; «…; DROP TABLE»
  отвергается AST-whitelist независимо от поведения модели; defense in depth: read-only
  роль — последний рубеж; инъекция-категория — в аудит (security.md §3).
- **Ранний индикатор:** события `guardrail_block(injection)`.

### R-S4. Данные уходят к LLM-провайдеру
- **Вероятность:** — (факт архитектуры) · **Влияние:** С (регуляторно в корпоративном проде) · **Сложность:** С (переход на локальные модели)
- **Митигация:** осознанный допуск v1 на синтетической демо-схеме (C4 L1); промпт —
  только вопрос и DDL разрешённых таблиц, результаты — только агрегат на
  `interpret_result`; порт `LLMProvider` позволяет замену на локальные модели одной
  переменной (NFR-7); для пет-проекта в корпоративном контуре — revisit ADR-007.
- **Ранний индикатор:** требование локализации от заказчика пет-проекта.

### R-S5. Прямой вызов SAP-ручки в обход агента
- **Вероятность:** Н · **Влияние:** Н–С · **Сложность:** Н
- **Риск:** пользователь с SAP-доступом зовёт ручку напрямую (по сути SQL-шлюз):
  данные всё равно под его правами — утечки нет, но обходятся наши guardrails —
  бюджет, rate-limit, аудит прогона, PII-маскирование, трейс.
- **Митигация:** авторизация вызова ручки — сервисная идентичность агента
  (проверка в ABAP) + per-user токен внутри; вызовы не под агентной
  идентичностью — отказ.
- **Ранний индикатор:** доля вызовов ручки, не соответствующая прогонам в
  `query_trace` (сверка по trace_id).

## Группа 3. Модели и экономика

### R-C1. Дрейф цен/квот/состава каталога routerai.ru
- **Вероятность:** В (цены меняются) · **Влияние:** С · **Сложность:** Н
- **Митигация:** методика расчёта важнее цифр (пересчёт по §7 при смене тарифов);
  смена модели — конфиг, роли `cheap/mid/strong` стабильны; 40 провайдеров у deepseek —
  роутер подбирает по доступности; кап 2 ₽ ограничивает худший случай.
- **Ранний индикатор:** средняя стоимость запроса > 0,7 ₽; рост 429.

### R-C2. TTFT/латентность хуже целей на классификационных узлах
- **Вероятность:** С · **Влияние:** С (TTFT ≤ 3s) · **Сложность:** Н
- **Митигация:** дешёвые модели на частых узлах (инфраструктурный налог учтён в
  роутинге); reasoning только адресно; кэш снижает частоту mid/strong вызовов;
  p95 и TTFT — в трейсе каждого прогона.
- **Ранний индикатор:** TTFT p95 > 3s в трейсе.

### R-C3. Бенчмарки устарели / загрязнены → модель выбрана неверно
- **Вероятность:** С · **Влияние:** С · **Сложность:** Н (дисциплина)
- **Митигация:** правила чтения (низкий = дисквалификатор; 98% ≠ «идеально»);
  совокупность метрик, а не одна; финальная калибровка — собственным eval-сетом;
  смена модели — конфиг без правки узлов.
- **Ранний индикатор:** расхождение proxy-бенчмарков и eval-сета после его сборки.

### R-C4. Рантайм-конверт: зависший LLM-вызов, шторм ретраев, параллелизм
- **Вероятность:** С · **Влияние:** С · **Сложность:** Н
- **Риск:** (а) зависший вызов шлюза вешает узел FSM — breaker считает ошибки, не
  медлительность; (б) backoff без jitter — синхронные ретраи разных сессий бьют
  волнами; (в) «один sync-процесс» при параллелизме: пул соединений + долгая
  RR-транзакция декомпозиции (ADR-004, правило 6) — первые точки деградации.
- **Митигация:** таймаут ~15s на каждый LLM-вызов (медлительность → отказ узла →
  штатный путь); jitter в backoff; per-user token bucket в коде агента
  (security.md §3); озвученный профиль v1 — ≤ 10 одновременных (back-of-envelope,
  ADR-007 §5); триггер пересмотра снапшотной модели — pool wait time / возраст `xmin`.
- **Ранний индикатор:** таймауты LLM в трейсе; ожидание пула; p95 > 20s при росте
  одновременности.

## Группа 4. Данные и домен

### R-D1. Демо-схема нерепрезентативна для пет-проекта (объёмы, распределения)
- **Вероятность:** В · **Влияние:** С · **Сложность:** С
- **Митигация:** пороги T1/T2 — начальные, калибруются на целевой БД; декомпозиция —
  триггерная, не режим по умолчанию; федерация и RLS — архитектурно готовы (revisit).
- **Ранний индикатор:** overflow rate и decomposition rate вне целевых окон на реальных данных.

### R-D2. Грязные данные ломают семантику рёбер (campaign_id надёжен только с 2026-03)
- **Вероятность:** С · **Влияние:** С · **Сложность:** Н
- **Митигация:** ловушки фиксируются в `usage_notes`, а не правкой данных; допущения
  раскрываются в ответе; владелец данных отвечает за актуальность notes.
- **Ранний индикатор:** жалобы на несходимость цифр по периодам.

### R-D3. Наполнение `agent_relationships` владельцами буктует (нет владельцев/времени)
- **Вероятность:** С · **Влияние:** С (бизнес-рёбра — ядро ценности) · **Сложность:** С
- **Митигация:** FK-рёбра — автоматически из каталога (базовый граф работает без
  ручного труда); автообнаружение кандидатов из trace в режиме «предложить →
  подтвердил» (ADR-006); честный отказ «путь не найден» предпочтительнее домысла.
- **Ранний индикатор:** доля отказов «путь не найден» при существующей бизнес-связи.

### R-D4. Расхождение метаданных агента и фактических прав внешнего источника (SAP)
- **Вероятность:** С · **Влияние:** С · **Сложность:** Н
- **Риск:** подграф/каталог считают «таблица видна», SAP-ручка возвращает 403 (или
  наоборот: устаревший каталог скрывает таблицу, которую пользователь видит) —
  отказ после генерации или скрытие данных. Права SAP мы не дублируем (ADR-011 §4),
  значит метаданные могут плыть относительно реальных прав.
- **Митигация:** наши настройки — только фильтр мира и UX (арбитр — SAP); импорт
  метаданных из SAP-каталога (по расписанию/токену); reconciliation по образцу
  ADR-006 (видимость каталога агента = видимость SAP); 403 от SAP — штатный
  `degrade`-исход, не баг контура.
- **Ранний индикатор:** рост HTTP 403/«путь не найден» на SAP-источнике
  (live-метрика по `datasource` — observability §2.3).

## Группа 5. Процесс и сроки

### R-P1. Eval-сет не построен к моменту калибровки
- **Вероятность:** С · **Влияние:** В (блокирует калибровку, динамический роутер,
  join semantics accuracy) · **Сложность:** С (разметка — ручной труд)
- **Митигация:** eval-сет — приоритет №1 «что дальше» (README §9); собрать из trace
  реальных прогонов + эталонные пары «вопрос → SQL / путь / ребро»; начать с
  20–30 вопросов, покрывающих сцены приёмки; тяжёлые вопросы собирать заодно с
  калибровкой декомпозиции.
- **Ранний индикатор:** пороги NFR-6 не измерены к моменту ревизии ADR-пакета.

### R-P2. Дрейф документация ↔ код (реализация разойдётся с ADR-пакетом)
- **Вероятность:** С · **Влияние:** В · **Сложность:** Н (дисциплина)
- **Митигация:** ADR — единственный источник решений; матрица трассировки prd §9;
  изменение решения = правка ADR в том же PR, что и код; пересмотр пакета на вехах.
- **Ранний индикатор:** расхождения «как в README» vs «как в коде» на ревью.

### R-P3. Объём работ учебного проекта (декомпозиция + RBAC + семантика) не влезает в срок
- **Вероятность:** С · **Влияние:** С · **Сложность:** Н
- **Митигация:** приоритеты P0/P1 в prd §4; план Б декомпозиции зафиксирован заранее
  (заглушка `plan_query` прозрачна для архитектуры — ADR-004); кэш — P1 и после
  пересчёта не критичен для экономики (ADR-009).
- **Ранний индикатор:** к концу первой итерации нет сквозного «вопрос → SQL →
  выполнение → ответ».

| Триггер | Что пересмотреть |
|---|---|
| Инцидент-класс «пропуск валидатора» | R-S1 → ADR-005 revisit (per-user роли БД для чувствительных таблиц) |
| Eval-сет готов | R-P1, R-C3 → калибровка T1/T2, динамический роутер (ADR-007 revisit), пороги NFR-6 |
| Смена тарифов/состава routerai.ru | R-C1 → пересчёт §7, матрица ADR-007 |

| Ожидание пула / рост возраста xmin | R-C4 → снапшотная модель pg_export_snapshot (ADR-004), реплики процесса (ADR-007) |
| Пет-проект в корпоративном контуре | R-S4 → локальные модели (ADR-007 revisit) |
| Рост 403/«путь не найден» на внешнем источнике | R-D4 → импорт метаданных SAP, reconciliation (ADR-011 revisit) |
| Первая итерация реализации | R-P3, R-P2 → сверка сроков и консистентности док↔код |
| Рост overflow/decomposition rate вне окон | R-D1 → калибровка порогов на целевой БД |
