# BL-049 — План джойнов в FSM: направление LEFT, «звезда», выбор рёбер моделью

- **Статус:** открыт
- **Дата:** 2026-11-26
- **Сессия-источник:** — (обсуждение с владельцем 2026-11-26, вне сессии)
- **Приоритет:** P2
- **Назначение:** шаг 1 — по команде владельца (можно до ДЗ-04); шаг 2 — после сдачи ДЗ-04 (27.12.2026); ARCH-GATE canon-check (ADR-006, ADR-007)

## Что обнаружено

Чтение `plan_joins_service.py` / `domain/skeleton.py` и прогоны сборки скелета. План
строится как один путь между парой таблиц-кандидатов; направление пути задаётся порядком
выдачи retrieval.

**Подтверждено прогонами:**

1. **Направление LEFT.** При обходе пути против реестра ключи переставляются, `join_type`
   остаётся как в реестре. Одно ребро `employees LEFT JOIN bonuses`:
   - `employees` первой → `FROM employees LEFT JOIN bonuses` — все сотрудники;
   - `bonuses` первой → `FROM bonuses LEFT JOIN employees` — сотрудники без премии исчезают.
2. **LEFT, затем inner от правой стороны.** `FROM employees LEFT JOIN bonuses ON …
   INNER JOIN bonus_types ON …` вернул 2 строки из 3 — сотрудник без премии выпал.
   (SQLite через `assemble_sql`; на стенде PostgreSQL не гонялось.)
3. **Валидатор не ловит.** Тест развёрнутого пути — только `inner` и только на маппинг
   ключей (`test_plan_joins.py::test_columns_follow_reversed_direction`); `validate_sql`
   сверяет джойны с планом, а план и скелет собраны из одного пути — в любую сторону
   согласовано.

**По чтению кода (не гонялось):**

4. **«Звезда».** План — цепочка между одной парой. Если вопросу нужны три и более сущности
   вокруг одной таблицы, они попадут в план, только если путь между двумя кандидатами
   пройдёт через остальные; проверки «план покрывает всё, о чём спросили» нет.

На стенде одно left-ребро (`employees–bonuses`), задеты только вопросы про премии; в бою
left-рёбра — обычное дело, ошибка тихая.

## Что делать

Шаг 1 — страховка, независимо от остального:

- `validate_join_plan` отклоняет ребро `left`, развёрнутое против реестра, и ребро `left`,
  после которого цепочка идёт inner-джойном от правой таблицы. Честный отказ вместо
  неверной цифры. На inner-сценариях hw-04 ничего не меняет. ≈ 1 ч номинала.

Шаг 2 — предложение агента, ждёт решения владельца:

- Модель выбирает набор рёбер, а не ранжирует готовые цепочки: граф, как сейчас, находит
  пути; модели отдаётся список рёбер из них с семантикой; тул возвращает `rel_id`; код
  собирает план-дерево (ключи, тип, обязательные предикаты — из реестра) и выбирает
  направление цепочки. Закрывает п. 1–4. «Валидировать как в S31» здесь недостаточно —
  свободная сверка пропускает тип, направление и ключи (BL-048). ≈ 2–3 ч номинала.

Вариант «вместо детерминированного поиска по графу» агент не рекомендовал: граф —
артефакт ДЗ-04 (hw-plan §4: «RAG по смыслу + граф по связям → JoinPlan»). Владелец не
возражал; отдельного решения нет.

## Оценка (базис: 1 ч номинала ≈ 10% недельного лимита токенов)

Шаг 1 — ≈ 1 ч; шаг 2 — ≈ 2–3 ч; с калибровкой S31 (×2) на оба шага закладывать 40–60%
недельной квоты. Прикидка агента, не решение владельца.
