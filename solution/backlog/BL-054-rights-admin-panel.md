## Решение владельца (2026-11-26)

1. Права ведутся в таблицах (`agent_permissions`, `agent_user_roles`) **через админку**.
2. Задумка ADR-005 (вариант B, «права как данные»): добавить пользователя, назначить ему
   группу (роль), изменить права группы — **без изменения схемы**, только
   `INSERT`/`UPDATE`/`DELETE`. Per-user GRANT и RLS-политики с зашитыми правами этого не
   дают: там правка права — DDL (`docs/adr/ADR-005-rbac-as-data.md:25`; варианты A и D
   отвергнуты как замена — `:35-38`, `:44-49`).
3. Админка нужна после ДЗ — на итоговом треке: после сдачи ДЗ-06, со стартом работ над итоговым
   проектом (та же постановка, что в D-040 п. 4 — `DECISIONS.md:379`).

## Что уже работает без админки

- Группа (роль) и её права — строки `agent_permissions` по ключу `role`; пользователь → группа —
  строки `agent_user_roles` (`20261118_0001_schema_v15.py:81-95`).
- Любая запись в эти таблицы триггером поднимает счётчик `settings_version`
  (`0001:171-177`); агент сверяет счётчик на каждом запросе и перечитывает права — изменение
  действует со следующего запроса, без рестарта (ADR-005 §4, `:107-109`; NFR-5).
- RLS-рубеж S35 этому не мешает: в тексте политики нет ни пользователей, ни групп, ни прав —
  исполнитель передаёт БД список таблиц, посчитанный из прав
  (`solution/sessions/S35_session.md:34-45`).

## Чего для админки не хватает (все пункты — DECISION NEEDED при планировании итогового проекта)

1. **Канал записи.** Права меняются только рукописным SQL под владельцем БД (демо-набор — сид
   `20261118_0003_demo_data.py:131-146`). Гранта на запись в таблицы прав нет ни у одной роли:
   планировщику — чтение (`20261118_0002_roles_hardening.py:80-83`), `registry_writer` пишет
   только в реестр связей (`:95-98`). Нужна новая миграция с отдельной ролью для админки
   (`INSERT`/`UPDATE`/`DELETE` на две таблицы прав); `agent_ro`/`agent_planner` остаются read-only.
2. **Кто администратор.** В `agent_user_roles` сидируются только бизнес-роли (`0003:143-146`);
   действующее лицо «Администратор платформы» в c4-l1 — трейсы, метрики, стоимость, аудит
   (`docs/diagrams/c4-l1-context.md:17`), управлением прав не занимается. Признак администратора
   прав — решить (роль в `agent_user_roles`, отдельный флаг, запись в сервисе `auth`).
3. **Где интерфейс.** В BL-047 заявлены только страницы логина и агента (`BL-047:36`); прод-фронтенд
   после ДЗ-06 — BL-018. Страница админки прав и её API — выбрать при планировании.
4. **Граница с учётными записями.** «Добавить пользователя» — это учётная запись в `auth`
   (таблицы паролей пока нет — BL-047) плюс строки в `agent_user_roles`. Одна админка на обе части
   или две — решить.
5. **Модель данных — после BL-029.** У `agent_user_roles` нет `granted_by`/`granted_at` — кто выдал
   группу, следа не оставляет; `agent_permissions.columns` — CSV-текст (`BL-029:11-14`, миграции —
   `BL-029:26-27`; парсеры — BL-014). Админку писать после этих миграций, иначе интерфейс закрепит
   CSV-формат и останется без следа выдачи.
6. **Проверки на вводе.** `table_name` — из каталога мира агента `agent_data_sources`
   (`pg_permission_store.py:36`); `schema_name = 'public'` — адаптер читает только публичную схему
   (`:26-33`); список колонок — сверять с реальными колонками таблицы; `updated_by` — identity
   администратора (`0001:86-87`).
7. **Канон.** ADR-005 §4 («редактируют владельцы данных», `:75-76`; «Управление без
   разработчиком: SQL-настройка», `:26`), c4-l1 (действующее лицо), security.md (новая роль БД),
   ER-модель — синк сессией итогового проекта с canon-check; вне сессии канон не править.
