## Что обнаружено

Обсуждение с владельцем 2026-11-26: как должен выглядеть вход пользователя, когда агент
работает сервисом. Что решил владелец (в порядке разговора):

1. Агент — не консольное и не локальное приложение, а сервис за дверью (входом).
2. При входе пользователь видит страницу логина, после входа — страницу агента.
3. Схема должна быть **правильной и не слишком сложной** («не раздувать скоуп проекта»).
4. Три сервиса на Python: **frontend**, **agent-api**, **auth** (предложил владелец, агент согласился).
5. Без nginx и без Keycloak/oauth2-proxy; фронтенд — **свой сервер на Python**.
6. Идея подписанного токена и проверки его на стороне агента — владельца (обсуждали для
   гейтвея), здесь перенесена на свой `auth`.
7. UI-библиотека: **пока NiceGUI, с требованием уточнить** — владелец использовал другую
   Python-библиотеку в другом проекте и проверит её позже (название не вспомнил).
8. Гейтвей: «и всё-таки ещё нужен гейтвей», реализация — **Envoy**. Роль гейтвея (единый вход,
   маршрутизация, проверка токена) — трактовка агента; владелец назвал только инструмент.
9. **Сразу целевой контур (2026-11-26, D-040):** Streamlit-демо (feat-022, D-032) не делается —
   веб-интерфейс и хозяин `/metrics` строятся сразу по этой схеме, в вехе V5 (ДЗ-06).

## Схема (направление, согласованное в обсуждении)

```
браузер
  │
  ▼
Envoy (gateway) — единственная дверь наружу: TLS, маршрутизация по путям,
  проверка токена для /api/*, стирание подделанных клиентских заголовков
  ├──► /        frontend  (FastAPI + UI-библиотека: страницы логина и агента)
  ├──► /auth/*  auth      (FastAPI: пользователи, хэши паролей, выдаёт подписанный токен)
  └──► /api/*   agent-api (FastAPI: ещё раз проверяет подпись токена → пользователь → агент)
```

- `frontend`, `auth` и `agent-api` наружу не публикуются — только Envoy (как Data Plane,
  security §5). Admin-интерфейс Envoy — только внутри кластера.
- Всё живёт на одном адресе, поэтому cookie сессии работает без CORS.
- Токен — JWT в cookie. Envoy умеет читать JWT из cookie (`from_cookies`) и оставляет его
  в запросе — `agent-api` видит тот же токен и проверяет сам.
- `agent-api` проверяет подпись тем же публичным ключом через порт `AuthProvider`: Envoy —
  не единственная линия защиты, правило «голый `user_id` — не identity» сохраняется без оговорок.
- Потоковый показ ответа (SSE) и WebSocket UI-библиотеки проходят через Envoy — таймауты
  маршрутов настроить под них (не сверено, открытый вопрос 3).
- CLI с дев-токенами (`DevTokenAuth`) остаётся для ДЗ и локальной работы без изменений.

## Что обязательно сделать правильно

Пункты 1–2 схемы — решения владельца. Ниже — дополнения агента из обсуждения (рекомендации;
подтвердить на canon-check при старте работ):

1. Агент не прикасается к паролям (ADR-005 «аутентификация вне агента»): таблицу паролей не
   включать в гранты агентных ролей (`agent_ro`, `agent_planner`).
2. Порт `AuthProvider` используется по назначению — `verify(token) → user_id`: адаптер проверки
   подписи токена. Замена своего `auth` на Keycloak позже — только ключ проверки в конфиге.
3. Пароли — только хэш готовой библиотекой; при неверном входе одинаковый ответ («неверный
   логин или пароль»); ограничение числа попыток входа.
4. Токен — JWT с асимметричной подписью и сроком: у `auth` приватный ключ; Envoy (`jwt_authn`)
   и `agent-api` проверяют публичным — ни гейтвей, ни агент не могут выпускать токены сами.
   Проверяются подпись, срок, `iss` и `aud`; алгоритм фиксирован в конфигурации, не берётся
   из самого токена.
5. Токен живёт в cookie: HttpOnly, Secure, SameSite=Lax — во фронтенде токена нет.
6. Досрочный отзыв токена невозможен: при увольнении роль снимается в таблицах прав
   (`agent_user_roles`) — права пропадают со следующего запроса, как сейчас.
7. Результат и поток ответа отдаются только тому пользователю, который создал запрос. В c4-l2
   схема `POST /ask → job_id` + `GET …/stream` принадлежность запроса пользователю не оговаривает.
8. Envoy стирает заголовки, которые ставит сам (например, с именем пользователя), чтобы клиент
   не мог их подделать. Проверка на Envoy — ранний отсев (отказ 401 до сервиса), а не замена
   проверке в `agent-api`.

## Design-требования очереди и ретрая (BL-053; решения владельца 2026-11-26)

При реализации `agent-api`/`agent-worker` (доказательства — BL-053). Гигиена схемы c4-l2
(три неточности) — S36 Task 6, здесь не дублируется.

**Ограничение по библиотеке** (решено 2026-11-26: выбор — при реализации, формулировку
схемы не наследовать):

1. arq — **maintenance only mode** (README, issue #510); очередь — sorted set и строковые
   ключи, **не Streams**; Valkey в документации arq не упомянут. Факты — по master на
   26.11.2026, при выборе сверить по зафиксированной версии.
2. Дефолты arq противоречат контракту «≤ 1 повтора»: `max_tries=5`, `job_timeout=300`,
   `max_jobs=10` — задавать явно.

**Контракт ретрая/идемпотентности — DECISION NEEDED при старте работ** (решение
владельца 2026-11-26: решить при реализации).

Общие положения (черновик владельца, приняты):

- ключ корреляции — `job_id`; повторная попытка — attempt того же `job_id`, не новый
  прогон; в каждом событии трейса — номер попытки;
- ретрай очереди — только падение воркера, ≤ 1 (`max_tries=2`); ошибки модели/SQL —
  внутри FSM (M1), наружу не всплывают: на входе воркера catch-all в исход `fail`
  (сегодня в исход переводятся только LLM-ошибки — `answer_question.py:124-137`,
  ошибки чекпоинтера/recursion/прерывания — `runner.py:168-180`, типизированные ошибки
  узлов; прочие исключения в arq = упавшая джоба);
- дедлайн 90 s — в воркере/FSM-гварде (`deadline_at` — `runner.py:146-147`,
  `routing.py:136-138`; `settings.py:141`); `asyncio.timeout` на API-хендлере ограничивает
  HTTP-запрос, не прогон — так и писать в схеме (S36 Task 6); `job_timeout` arq — внешняя
  страховка (около 100 s);
- пользовательский SQL read-only (`agent_ro`, LIMIT 1000, timeout 30 s) — повторное
  исполнение не угрожает данным, только стоимости и наблюдаемости.

As-is по коду (чего нет на 2026-11-26):

- `run_id` не существует: `trace_id` ставит раннер (`runner.py:148-149`), `thread_id` —
  сессия чекпоинтера (`answer_question.py:95`); оба можно передать снаружи (`run(…,
  thread_id=…)` — `answer_question.py:81`);
- в state (чекпоинтятся) — счётчик LLM-вызовов и `retry_count`; учёт ₽ — **резидентный
  аккумулятор адаптера шлюза** (`openai_provider.py:134,:529`) со сбросом на старте
  каждого прогона (`answer_question.py:93`); `budget_used.rub` в state пишут только
  терминальные узлы (`degrade_node.py:103`, `interpret_result_node.py:92`);
- продолжения с чекпоинта нет: `run()` начинает с нулевого state (`answer_question.py:94`),
  `resume` требует активной паузы (`runner.py:248-259`); TTL чекпоинта 600 s
  (`settings.py:155`); `deadline_at` — monotonic-метка;
- аудита в коде нет (таблицы `0001:188`, `:212` — писателя нет); трейс — append-only
  JSONL (`jsonl_tracer.py:20-45`).

Варианты (решение — при старте работ):

- **A. Новая попытка под тем же `job_id`** (рекомендация агента): `trace_id = job_id`,
  `thread_id` — свой на попытку, attempt = `ctx["job_try"]`; капы (2 ₽ / 8 вызовов /
  90 s) — на попытку. Нового метода раннера не нужно. Параллелизм — реплики воркера с
  `max_jobs=1` (c4-l2: «N воркеров»): резидентный ₽-аккумулятор остаётся корректным без
  рефакторинга. Худший случай по стоимости — два капа на упавшую джобу.
- **B. Продолжать с чекпоинта** (как в черновике владельца): счётчики не сбрасываются,
  оплаченные LLM-вызовы не повторяются. Цена по коду: новый метод раннера (изменение
  порта `GraphRunner`), TTL чекпоинта выше 600 s под окно ретрая, перевзвод
  monotonic-дедлайна, перенос учёта ₽ в state.

Сверить при реализации: идемпотентность INSERT заявок `agent_edge_proposals` при
повторном прогоне (S09); переподключение потока SSE после падения и повтора.

## Отвергнутые или отложенные варианты (чтобы не пересматривать)

- **OIDC-проверка токена Keycloak внутри агента** (`OIDCAuth`, текущий канон): агенту нужен
  исходящий доступ к Keycloak, которого нет в NetworkPolicy (egress — только LLM-шлюз).
- **Envoy + сервис авторизации (oauth2-proxy)**: oauth2-proxy отвергнут — владелец выбрал
  свой `auth`; Envoy оставлен, но в роли гейтвея.
- **Вход внутри `agent-api`** (два сервиса): агент получает доступ к хэшам паролей — против
  ADR-005.
- **nginx как дверь**: владелец — «зачем чужой веб-сервер».
- **Envoy как замена веб-серверу страниц**: не годится — Envoy не отдаёт статические файлы.
- **frontend как дверь и прокси** (первая редакция этой записи): заменено Envoy по решению
  владельца.
- **Node-сервер в рантайме**: лишний язык (проект Python-native, D-017); Node нужен только
  если UI — React/Vue (этап сборки).
- **React/Vue SPA** (BL-018): отложено — владелец выбрал сервер на Python.
- **Админка прав в V5** — не входит: нужна после ДЗ, на итоговом треке (владелец,
  2026-11-26); запись — BL-054.

## Оценка (базис: 1 ч номинала ≈ 10% недельного лимита токенов, ставка без осложнений)

Прикидка агента, не решение владельца: `auth` ≈ 1,5 ч; `agent-api` ≈ 2 ч; `frontend` ≈ 1 ч
(NiceGUI); конфигурация Envoy с контейнером ≈ 1 ч → **≈ 6–7 ч ≈ 60–70% недельного лимита по
базовой ставке**. Риски — ревью по безопасности и незнакомая проекту настройка Envoy (запас
×1,5–2). При React/Vue фронтенд +1–2 ч. Редакция без гейтвея выходила ≈ 5–6 ч.
