# BL-050 — FSM: рёбра с `join_operator != '='` не поддерживаются сквозняком — IR-сверка ON принимает только равенства (решено (c): контракт v1 — только '=')

- **Дата:** 2026-11-26
- **Сессия-источник:** — (READ-ONLY аудит готовности к удалению тул-контура 2026-11-26 + решение владельца, вне сессии)
- **Приоритет:** P2
- **Назначение:** — (закрыт решением (c): рубеж — проверка в считывателе семантики рёбер сейчас + CHECK в ближайшей миграции; пометки ER/ADR-006 — отдельная маленькая задача после removal, в коммит удаления не мешать)

## Что обнаружено

Поле `join_operator` реестра — декоративное: читается скелетом, но сквозной сверки не имеет.

- Скелет рендерит оператор ребра: `domain/skeleton.py:228` — `{from_table}.{col}
  {edge.join_operator} {to_table}.{col}`; семантика доходит до плана
  (`plan_joins_service.py:544,:677`).
- IR-сверка ON принимает только EQ-конъюнкты: `validate_sql_service.py:926-942`
  (`_on_pairs`); любой не-EQ (включая `<`/`>` и равенства под OR/NOT/CASE) → сентинел
  `_COMPLEX_ON` (`:174`).
- Следствие: при активном ребре с оператором ≠ `'='` FSM отклоняет **СОБСТВЕННЫЙ** SQL как
  hallucination — `audit.joins != _expected_joins(plan)` (`sql_validation.py:516-520`;
  эталон пар без оператора — `:527-544`).
- **Проверено прогоном 2026-11-26** (валидатор без БД, в памяти): при ребре
  `join_operator='<'` (и `'>='`) скелет рендерит `INNER JOIN customers ON
  orders.customer_id < customers.id`, вердикт FSM — `hallucination` («структура джойнов
  не соответствует плану (тип/таблица/пары ON/порядок)»); свободный вход на том же SQL —
  `ok`. Контроль: при ребре `'='` модель, написавшая `>=` в ON, отклоняется — не-EQ-джойн
  по EQ-ребру FSM не исполнит. Расход — M1-петля в пределах капов прогона (≤ 8 вызовов /
  ≤ 2 ₽ — `routing.py:132-135`), на каждом вопросе по такому ребру: план заведомо
  непроходим, скелет модель менять не может.
- Свободный валидатор оператор тоже не сверяет — только пары таблиц
  (`sql_validation.py:301-307`): «fail-closed тул-контура по оператору» не существует
  никогда (поправка к ранней рамке аудита).
- Контракт поля задокументирован: `er-data-model.md:83` ("default '='"), ADR-006:84,
  VO `schema_graph_store.py:91`, миграция `0001:108` (default `'='`).
- Active-рёбер с оператором ≠ `'='` сегодня нет: сиды 0003 (`:91-118`) и 0008 (`:46`)
  колонку не переопределяют — все `'='`; `join_type` (4×inner + 1×left) — другое поле.
- **CI-гейта активации рёбер в репо нет**: BL-026 (открыт, V6) — «перевод ребра в
  `active` ничем не проверяется»; в коде только колонки `status`/`ci_report`. Формулировка
  черновика решения «CI-гейт активации (ADR-006 §4.2) отвергает ≠ '='» описывает
  непостроенный механизм.

## Почему вне скоупа (аудита и коммита удаления)

Зазор предсуществует в FSM (раньше маскировался тем, что и свободный вход оператор не
сверял). Коммит удаления тул-контура (BL-048) его не исправляет и не ухудшает.

## Решение владельца (2026-11-26) — (c)

**Контракт v1 — только `'='`.** Колонку `join_operator` сохранить (без миграции ради неё),
активация ребра с оператором ≠ `'='` **отклоняется рубежом**, а не дисциплиной;
расширение IR-сверки — не сейчас.

Почему рубеж, а не «не активируем»: активация non-EQ ребра сегодня — runtime-ловушка
(см. прогон выше): отказ уходит в M1-петлю прогона пользователя; рубеж переносит его в
жизненный цикл ребра. Пока гейта активации нет (BL-026), рубеж — два уровня:

1. **Сейчас** (отдельная маленькая задача после removal, в коммит удаления не мешать):
   fail-closed проверка в считывателе семантики рёбер — `neo4j_graph_store.py:372`
   (единственная точка, где `join_operator` входит в мир агента): оператор ≠ `'='` →
   `SchemaGraphError`; `plan_joins_service.py:321-322` уже переводит это в честный отказ
   до генерации SQL, остальные рёбра не задеты. Около 5 строк + юнит-тест. Вместе с ней —
   канон-пометки (волна ревизий, canon-check): ER `er-data-model.md:83` («v1: только `'='`,
   прочие отклоняются рубежом»), ADR-006 §4.1/§4.2 (в перечень проверок гейта — «оператор
   поддержан исполнителем»; пункт наследует BL-026 при постройке гейта).
2. **CHECK-ограничение** `status <> 'active' OR join_operator = '='` в ближайшей миграции
   (отдельной миграции ради этого не плодить; естественный носитель — миграция паролей
   V5, BL-047): закрывает и runtime-вставки владельца реестра, а не только сиды.

До постройки уровня 1 действует дисциплина «активация рёбер только `join_operator='='`».

**Revisit-триггер:** temporal/интервальные соединения — совпадает с триггером ADR-006
(`:266-268`: «время-зависимые» связи → расширение `temporal` условным джойном — правка
ребра/планировщика, не принципа). Поле `temporal jsonb` в контракте есть (`0001:116`,
ADR-006:89); пример «validity-интервалы SAP (`BETWEEN valid_from AND valid_to`)» —
доменный пример владельца, в репо не зафиксирован. Как появится первый реальный
потребитель — IR-сверка на операторы, новая запись.
