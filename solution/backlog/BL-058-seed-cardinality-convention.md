# BL-058 — сид-ребро e_campaigns_orders: cardinality 'n:1' при left=campaigns против конвенции left-is-«1»; гейта активации рёбер нет

- **Статус:** открыт <!-- открыт | закрыт (...) — легенда; archive.sh срезает комментарий до проверки -->
- **Дата:** 2026-11-27
- **Сессия-источник:** S32 (ARCH-GATE canon-check architect, finding 2 по `src/migrations/versions/20261118_0003_demo_data.py:92`)
- **Приоритет:** P2 (вне blast-radius feat-023: у ребра `fanout_guard=false` — вывод one_side не вызывается)

## Предмет (факт по сидам, canon-check S32)

Сид-ребро `e_campaigns_orders` записано `('campaigns', '{campaign_id}', 'orders', …, 'n:1')` —
`cardinality='n:1'` при **left=campaigns**. Остальные рёбра реестра с направленной
cardinality следуют конвенции **left-is-«1»** (`e_customers_orders` '1:n' при left=customers,
`e_orders_items`/`e_products_items` '1:n' при left=orders/products — сторона «1» слева).
Для feat-023 конвенция вывода стороны «1» закреплена в ADR-006 §4.6 (v1.10):
`plan_joins_service._fanout_one_side` — «1:n» → left, «n:1» → right (ruling R3 ARCH-GATE S32).

На этом сиде конвенция даёт сторону «1» = **orders** (n:1 → right), тогда как бизнес-смысл
кампаний→заказов — campaigns «1» / orders «n» (n:1 от orders к кампании — «много заказов
приходят из одной кампании», т.е. в записи реестра имелась в виду ориентация
«orders n : 1 campaigns» при порядке left=campaigns). Семантика ребра не расходится с
данными (join-ключи симметричны), но при будущем включении `fanout_guard` на этом ребре
выведенная сторона «1» была бы неверной — guard отклонял бы агрегаты не над той таблицей.

## Варианты (решение — за владельцем)

1. **Исправить сид** (следующая миграция, V5/BL-047): `'n:1'` → `'1:n'` для e_campaigns_orders —
   конвенция left-is-«1» соблюдается без оговорок; правка применённой миграции запрещена
   (0003 не трогается), нужна новая.
2. **Оговорка в конвенции** (если сид менять нельзя): cardinality читать «left : right», а не
   «one : many» — тогда one_side-вывод обязан учитывать знак: отказ от конвенции left-is-«1»,
   усложнение `_fanout_one_side` и валидации реестра.
3. **Как есть** + строка в ADR-006 §4.6 «ребро вне конвенции» — минимально, но оставляет
   ловушку для будущих guard-включений.

## Сет на будущее (отдельно от выбора варианта)

Гейта активации рёбер нет (BL-026): реестр наполняется рукописным SQL — конвенция
cardinality/fanout_guard ничем не проверяется при INSERT. CI-гейт активации (ADR-006 §4.2)
закрыл бы класс «ребро вне конвенции» до попадания в снапшот.
