# BL-046 — Групповое правило пар JOIN (вариант A, ruling архитектора) — готовое решение открытой находки ревью

- **Статус:** открыт
- **Дата:** 2026-11-25
- **Сессия-источник:** S31 (REVIEW-GATE-цикл: re-review-6 «With fixes», 0C/1I/3M; consult архитектора по команде владельца)
- **Приоритет:** P3
- **Назначение:** точка возврата при первом реальном ложно-отказе валидатора или при следующем касании парной сверки JOIN / BL-033

## Что обнаружено (открытая Important re-review-6, НЕ закрыта волной)

Волна 6 (45d606a) сделала пары JOIN детерминированными и порядконезависимыми через
prev-primary tie-break («первична пара с предшественником цепочки»). Ревью-6 нашло цену:
вердикт стал зависеть от ОРИЕНТАЦИИ цепочки источников. Живой пример (обе формы
семантически одинаковы, рёбра customers↔orders и campaigns↔orders на месте):

- hub-first + фильтр (prev=campaigns):
  `FROM orders o JOIN campaigns m ON m.id = o.campaign_id JOIN customers c ON (c.id = o.customer_id) AND (c.region = m.channel)` → **HALLUCINATION** «campaigns↔customers» (ложный отказ);
- dim-first (prev=orders): тот же SQL с переставленными JOIN → **ok**.

Класс находки — fail-closed сторона (ложный ОТКАЗ легального SQL, пропуска нет),
но рубёж обязан быть предсказуемым: ориентация записи — не семантика.

## Готовое решение — ruling архитектора (consult 2026-11-25, НЕ имплементировано)

Вариант (A) принять как **ADR-006 v1.9** — «групповое правило», с четырьмя уточнениями:

1. **Два поля IR вместо одного**: `join_table_pairs` → `join_pair_groups`
   (кортеж групп пар, группы в документном порядке JOIN, пары внутри группы
   отсортированы по итоговым именам таблиц); корреляции — ОТДЕЛЬНОЕ плоское поле
   (`correlation_pairs`), политика «каждая пара несущая» (∀, строгая сторона).
   НЕ собирать корреляции в группу — правило ∃ ослабило бы пин
   `test_correlation_pairs_only_predicate_tables`.
2. **Self-пара — якорь группы**, не «выбросить и требовать ребро»: группа с
   self-парой (таблица↔сама себя) проходит; смешанный self-join
   (`c2.id = c.referrer_id AND c2.region = m.channel`) остаётся ok в обеих
   ориентациях (как на 45d606a).
3. **Сортировка итоговых пар** (имена таблиц, не алиасы/порядок равенств) —
   детерминированный порядок issues для сигнала ретрая M1.
4. **Фикс остаточного недетерминизма**: `validate_sql_service.py:367` —
   `for local_name in predicate_locals or local_table_names:` итерирует set —
   порядок issues корреляционных пар зависел от PYTHONHASHSEED (вердикт тот же);
   обернуть в `sorted(...)`.

Семантика правила: для каждого JOIN сервис строит ГРУППУ кандидатов — пары всех
его связывающих равенств ON (присоединяемая таблица × контрагент конъюнктивного
скелета, `_join_tie_refs` остаётся). Группа проходит, если хотя бы одна её пара —
ребро активного снимка или self-пара; остальные равенства группы — фильтры
(AND только сужает уже соединённые строки). Группа без якоря — hallucination по
каждой своей паре. Правило — функция множества конъюнктов ON и снимка реестра:
порядок конъюнктов и ориентация цепочки FROM/JOIN вердикт не меняют. Сервис
группирует без реестра и без графа связности (BFS `_assert_pair`/
`_names_connected`/prev-primary из волн 5–6 удаляются) — решает домен.

Следствия (осознанные, записать в ADR-006 §4 v1.9):
- «выдуманный конъюнкт рядом с реальным ребром = фильтр» — продолжение канона
  волны 4 (пин `test_or_branches_across_pairs_not_a_tie`, OK-компаньон) —
  множество принимаемого SQL ШИРЕ v1.8, правило v1.8 «первична пара с
  предшественником» ОТЗЫВАЕТСЯ (OUTER JOIN с фильтром в ON не имеет легальной
  WHERE-записи);
- «маскировка» вакуумным равенством на паре-ребре (`c.id*0 = o.customer_id*0`)
  — принимается, существует с v1.4 (отдельная запись при первом кейсе);
- асимметрия JOIN (группа, ∃) / EXISTS-корреляции (∀) — строгая сторона,
  пересмотр при первом ложном отказе;
- угол K1: алиас уже присоединённой таблицы только с нерегистровыми равенствами
  → отказ (строже v1.8, осознанно);
- USING hub-first ложно отбраковывается УЖЕ на 45d606a (фолбэк по соседям
  цепочки) — (A) не меняет; для починки нужны колонки в IR — граница BL-033.

Альтернатива (B) «правило волны 6 как канон» отвергнута архитектором:
канонизирует дефект re-review-6; hub-first — самая частая форма LLM-SQL;
OUTER JOIN с фильтром в ON не переносится в WHERE.

## Обязательные регрессии при имплементации (все красные на 45d606a, кроме №7)

1. Hub-first + фильтр между измерениями: обе ориентации и зеркальный порядок
   конъюнктов → OK, issues пустые.
2. `LEFT JOIN` с фильтром в ON → OK.
3. Одиночное выдуманное равенство: 2 таблицы; 3 таблицы (предшественник на
   стороне ребра и на стороне выдумки) → HALLUCINATION; группа из двух выдуманных
   → обе пары в issues, порядок стабильный.
4. Выдуманный конъюнкт рядом с ребром → OK в обеих ориентациях (комментарий
   «осознанно, волна 4 + v1.9»).
5. Self-join: чистый (уже есть) + смешанный в обеих ориентациях → OK.
6. Угол K1 → HALLUCINATION (комментарий «строже v1.8, осознанно»; на 45d606a
   этот SQL проходит — тест красный на до-фиксе).
7. Асимметрия форм: EXISTS с двумя корреляциями → HALLUCINATION (так и на HEAD),
   форма JOIN → OK (пин-документатор).
8. Свод сидов PYTHONHASHSEED: добавить корреляцию с ≥2 локальными таблицами и
   зеркальную неуспешную группу — строка issues побайтово равна.
9. Контракт IR: группы в документном порядке, пары отсортированы, корреляции —
   отдельное поле; FSM-вход поля не читает (потребители — `_check_join_pairs`
   и ассерты формы; подтверждено grep при ruling'е).
