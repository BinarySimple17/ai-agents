## Предмет (факты проверены 2026-11-27)

- `SELECT … INTO` — запись/DDL (Postgres переписывает его в `CREATE TABLE AS`), но sqlglot
  парсит его как `exp.Select` с arg `into`: гейты «корень ∈ {Select, Union, Subquery}» +
  deny-поиск Insert/Update/Delete/Create/Alter/Command его НЕ видят. Доказано прогоном на
  sqlglot 30.31.0 (pyproject: `sqlglot>=27.0`): `SELECT id INTO new_t FROM orders` →
  «PASS select», args содержит `into`. Это же — доказанная дыра №1 внешнего сниппета
  (его гейты 1/2 INTO пропускают).
- В FSM-контуре класс сегодня закрыт на двух границах — гейтом в валидаторе закрыт НЕ
  является:
  1. генератор: поля заполнения скелета лексически запрещают SQL-структуры, включая
     `sql_exp.Into` («INTO — DDL-класс», re-review S10 I-r1) —
     `generate_sql_service.py:261-262,:281,:291,:296`; модель не пишет FROM,
     assemble_sql собирает запрос из скелета — INTO в собранный SQL не попадает;
  2. исполнение: `agent_ro` — `default_transaction_read_only = on`
     (`src/migrations/versions/20261118_0002_roles_hardening.py:65`), SELECT INTO
     отклоняется read-only сессией.
- В domain-валидаторе явной проверки нет: `validate_sql` (`sql_validation.py:192`) и
  хелперы `_check_*` аргумент `into` не инспектируют (grep по файлу — только
  docstrings `:25,:98,:279,:497`).

## Что сделать

- `domain/sql_validation.py`, `validate_sql`: явный fail-closed отказ при наличии `into` —
  проверка корня `ast.args.get("into")` + `ast.find(exp.Into)` (вложенные случаи);
  формулировка issue в стиле существующих («SELECT … INTO — запись/DDL-класс, вне контура
  чтения»); docstring гейтов дополнить.
- Регрессионный тест `src/tests/unit/test_validate_sql.py`: SELECT INTO → отказ; контроль —
  обычный SELECT проходит (тест обязан падать на до-правочном коде — проверка новая, это
  выполняется по построению).

## Почему P3 и почему всё равно делать

Defense in depth: сегодня класс недостижим «по построению» (граница генератора), но
валидатор — единственный гейт между assemble и execute; если появится путь к
`validate_sql` мимо сборки (новый узел, SQL из кэша, второй контур исполнения) — пояс уже
стоит. Цена — одна проверка + тест.

## Вне скоупа записи

Прочие находки ревью внешнего сниппета к FSM-валидатору не относятся или уже покрыты/решены:
allow-list функций — `_check_functions` (`sql_validation.py:310`); производные источники
CTE/sub/LATERAL — отдельная категория (`:98,:400`); неявные соединения в WHERE /
«таблицы ⊆ план» — BL-051(a) (исполнено S39 — ace5ea7); whitelist рёбер из FK —
противоречит ADR-006 (реестр — SoT, FK — генератор кандидатов); USING/NATURAL — qualify
sqlglot 30.x разворачивает сам; DuckDB/sqlfluff/pglast/EXPLAIN-зонд — не нужны FSM-контуру.
Здесь не повторять.
