### Task 5: Адаптер pgvector_store — поиск с фильтром прав

`src/text_to_sql_agent/infrastructure/memory/pgvector_store.py` (пакет `memory/` пуст и ждёт
именно этого): `PgVectorStore` — реализация порта. Поиск — гибрид (D-026): нога A — dense,
cosine distance `<=>`; нога B — ключевая, `content_tsv @@ websearch_to_tsquery('russian', :q)`
(терпим к синтаксису запроса; пустой tsquery на странном вводе → нога пуста, валидно). Глубина
каждой ноги (`MAX_LEG_DEPTH`), вес dense (`RRF_ALPHA_DENSE = 0.9`) и RRF_K = 60 — именованные
константы с комментарием «почему такое значение»; слияние — взвешенный RRF (D-026, дополнение):
`score = α_dense/(K+rank_dense) + (1−α_dense)/(K+rank_fts)` — невзвешенный RRF измеримо
проигрывает чистому dense (слабая нога диктует порядок слияния); 0.9 держит dense ведущим,
ключевой ноге оставляя победу на точных идентификаторах. Текст запроса перед tsquery и перед
эмбеддингом — та же нормализация, что при индексации (Task 6, один общий хелпер). Фильтр прав — ДЖОЙН с
`agent_user_roles`/`agent_permissions` в SQL ОБЕИХ ног (ADR-003 §4: «метадата-фильтр по scope
можно делать джойном с правами»), deny-by-default: нет прав на таблицу документа → документ не
участвует ни в ноге, ни в слиянии. Подключение — сервисный `POSTGRES_DSN` (retrieval —
операция планировщика, c4-l2 «пул agent_planner»; роль `agent_ro` тут не нужна — права
применяет SQL-фильтр). Unit-тесты на моках курсора: SQL обеих ног содержит джойн прав;
документы без прав не возвращаются; RRF-фьюжн на фиксированных рангах даёт ожидаемый порядок.

(5) шумовой корпус-дистрактор (D-026): ~300 документов генератором с фиксированным сидом

стиле, что реальные; дистрактор ДЕЛИТ общий признак с целью (домен, маскировка под имя

адаптером в запросе (Task 5): снятие комбинирующего акута U+0301 и ё→е (акут не буква —
резал термы пополам: «Кана́рские» → «кан»+«рские»; замер родственного проекта на RuBQ:
nDCG@10 0.3634 → 0.4306 после однострочного фикса). Регистр НЕ трогаем — `to_tsvector`
приводит сам. Чанк начинается префиксом-заголовком («[таблица: orders] …», «[термин:

## Ловушки

1. **id модели:** в LM Studio фактический id — `gpustack/bge-m3-GGUF` (publisher/name), а в
   `.env.example` — `EMBEDDING_MODEL=text-embedding-bge-m3`. Перед индексацией сверить с
   `GET /v1/models` живого шлюза и выставить фактический id в `.env` — иначе 404 или молча
   другая модель.
2. verify-feature требует state=active: активируй feat-006 в первый же день (Предусловия-5),
   не перед коммитом.
3. Strict-режим verify-feature отвергает причину N/A «сессия не начата» (guard-subagents
   GATE_STRICT) — к закрытию заменить обе строки гейтов на evidence/фактическую причину.
4. Гвард auto-pick (start-фаза make check) смотрит **S19** (sort -V), пока оба файла сессий
   в корне: ARCH-GATE S19 заполняется при старте S19, не «чинить» его из S06.
5. Хост 127.0.0.1, не localhost (Windows: `::1` резолвится первым и молча дропается —
   D-020, S02 DSN-правило).
6. БД-тесты скипаются без `make infra-up` — `make check` зелёный без Docker, но
   verify-feature feat-006 требует поднятую инфру (layer-2 команды фичи).
7. Правка применённой миграции запрещена — таблица знаний = новый файл миграции (S00
   правило 5).
8. Реранк top-k (Qwen3-Reranker-0.6B уже скачан в LM Studio) — НЕ в этой сессии; при
   нехватке качества retrieval — файл BL-NN в `solution/backlog/` (S00 правило 11).
9. **Нога FTS может быть пустой** (`websearch_to_tsquery` на странном вопросе) — это валидно:
   выдача = результат dense-ноги, не ошибка поиска. Честность терминов: в доках/README это
   «ключевая нога (Postgres FTS, ts_rank)», не «BM25» — канонический BM25 сознательно не
   строится (D-026: ParadeDB — смена запиненного образа несоразмерна корпусу; rank_bm25 —
   новая зависимость + русская морфология).
10. **Нормализация — договор между индексом и запросом:** `content` хранится нормализованным
    (без U+0301, ё→е) и запрос нормализуется тем же хелпером — если стороны разойдутся,
    FTS-нога молча опустеет. Хелпер один, живут обе стороны от него.
