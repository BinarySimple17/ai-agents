## ⚠️ Прочитай перед началом

Находка владельца (2026-11-20, milestone/v2): «сейчас две сессии оформлены — а ARCH-GATE
пропускается». S06+S19 из батч-планирования (D-024/D-026) лежат с «N/A — сессия не начата»;
гвард проверял только последнюю (S19), S06 не проверялся никем.

Первая трактовка исправления («гейт по всем сессиям в корне») была отклонена владельцем
по ходу сессии: «не так — архитектурный контроль должен проходить по одной сессии, только
по той, которую стартуют; у неё в пререквизитах, наверное, должен быть чекбокс». Принятая
модель: гейт кусает только СТАРТУЕМУЮ сессию — маркер старта в самом файле (статус шапки
«◐ в работе» + чекбокс в Предусловиях); запланированные («[ ] не начата») — легальные планы,
гейт их скипает; canon-check проводится при старте сессии, не при планировании.

Сознательно НЕ делается: canon-check S06/S19 в рамках S23 (они не стартовали — вердикты
появятся при их старте, по чекбоксу из Предусловий); статус-гейтинг в strict-пути
verify-feature (feature-id — вне классификации, S02 Important-5 сохранён); проверка
«коммит ↔ сессия» — BL-006.

### Правила для исполнителя

1. Старт-гейт классифицирует по статусу шапки (первые 20 строк, синхронно с archive.sh):
   «◐ в работе» — проверяется жёстко; «[ ] не начата» — [SKIP]; «✅» в корне — WARN make
   archive; нет строки «Статус:» — fail-closed (проверять).
2. End-фаза согласована: без явного файла/фичи — последняя стартованная (◐); строгий путь
   verify-feature по feature-id не меняется.
3. Слияние harness-ветки в milestone/v2 — напрямую (санкция D-024); PR в dev не создаётся.
4. Негативный контроль после merge обязателен: S06 → «◐» с «не начата» → make check красный
   с именем сессии; вернуть «[ ] не начата» → зелёный.

### Task 1: guard-subagents.sh — классификация по статусу шапки

- `classify_session`: «✅» → closed; «◐» → started; строка «Статус:» есть без ✅/◐ → planned;
  строки нет → started (fail-closed).
- Start без аргументов: перебрать все `*_session.md` корня (sort -V, без S00/TEMPLATE):
  closed → WARN «make archive» (skip); planned → собрать в `[SKIP]`-строку (skip);
  started → полный прогон (блок вывода, `[FIX]`-самовосстановление, ARCH-GATE жёстко с
  `no_not_started=1` — «не начата» у ◐ = FAIL как противоречие статусу, REVIEW-GATE мягко);
  FAIL копятся глобально, провальные — в итоговый список. Стартованных нет → OK/exit 0 с
  объяснением ритуала (шапка → ◐, ARCH-GATE до кода).
- Start + явный файл / start + feature → одна сессия, жёстко, минуя классификацию (S22
  поведение сохранено); пустой корень → WARN exit 0 (рестартуемость).
- End без явного файла/фичи: последняя стартованная (◐) сессия; стартованных нет → WARN
  exit 0 (запланированные не блокируют clean-check); пустой корень → archive-fallback
  (legacy) как раньше. End + файл/фича — жёстко, без изменений.
