# Solution — план-сессий и канон исполнения

Уровень планирования harness для многосессионной разработки. Разделение ролей:

- **`feature_list.json`** (корень) отвечает на вопрос «**ЧТО** делаем» — атомарные фичи с верификацией;
- **`solution/`** отвечает на вопрос «**КАК** работаем» — на какие сессии разбит проект, кто владелец, что является каноном и где фиксируются противоречия.

## Что здесь лежит

| Файл | Назначение |
|---|---|
| [sessions.md](sessions.md) | **Индекс**: план-сессий (таблица), владельцы треков, карта владения файлами, граф зависимостей, вехи; «Текущее состояние» — ТОЛЬКО статус последней закрытой сессии |
| [sessions/S00_session.md](sessions/S00_session.md) | **Канон проекта**: стек, порты, контракты стыков, архитектура кода, запреты, процесс. Источник истины при любом конфликте. Не архивируется |
| [sessions/TEMPLATE_session.md](sessions/TEMPLATE_session.md) | Шаблон рабочей сессии (копируется под новый ID) |
| [sessions/archive/](sessions/archive/) | Закрытые сессии (переносит `make archive`; строки в таблице `sessions.md` остаются как история) |
| [backlog/](backlog/README.md) | **Беклог**: записи вне скоупа сессий — по одному файлу `BL-NN-*.md`; закрытые переносятся в [backlog/archive/](backlog/archive/) тем же `make archive` |
| [FIXES.md](FIXES.md) | Журнал устранения противоречий канона (документ ↔ документ, документ ↔ код) |

## Жизненный цикл сессии

1. **Планирование:** скопировать [TEMPLATE_session.md](sessions/TEMPLATE_session.md) под ID (`<трек><NN>_session.md`) — механика: `make new-session S=<ID> TITLE="..." F=<feat-XXX> [ROLE=продолжает]` (копия шаблона + строка в таблице `sessions.md`; нарратив — предусловия/задачи с самопроверками — заполняет агент), добавить сессию в граф зависимостей. Зависимости сессии = закрытые сессии; в шапке — поле **«Фичи»** с ролью сессии: **«закрывает»** (финальная сессия фичи) или **«продолжает»** (промежуточная). Одна фича может занимать несколько сессий — закрывает ровно одну; фичи-зависимости к старту сессии должны быть в `passing`.
2. **Исполнение:** агент-исполнитель читает S00 (канон) → свою сессию → работает по правилам `AGENTS.md`. Задача закрывается только после ✅ Самопроверки.
3. **Закрытие (clock-out по `AGENTS.md`):** критерии приёмки отмечены, отчёт по сессии заполнен (Сделано / Отклонения от плана / Перенесено), `progress.md` обновлён; фичи: сессия-«закрывает» проводит `make verify-feature F=<id>` для каждой своей фичи, сессия-«продолжает» оставляет фичу `active` с allowlist (`bash scripts/clean-state-check.sh . <id>`). Механика — `make close-session S=<ID> MSG=<файл-сообщение>`: гейты/отчёт/фичи проверяются fail-closed, статус шапки → `✅ дата`, строка реестра обновляется, в «Текущем состоянии» — новая строка статуса (одна, старая удаляется сама), `make archive` переносит файл сессии в `sessions/archive/` (закрытые беклоги — в `backlog/archive/`), clean-state protocol, коммит из MSG-файла. Детали — [docs/AGENT-OPERATIONS.md](../docs/AGENT-OPERATIONS.md).

## Приоритет источников при конфликте

1. `AGENTS.md` — правила работы агента (harness);
2. **S00** (`sessions/S00_session.md`) — канон проекта: стек, порты, контракты, запреты;
3. `docs/adr/` — архитектурные решения;
4. `docs/` — свёртки (ARCHITECTURE.md, ER-модель, OpenAPI);
5. рабочие сессии `solution/sessions/` — история исполнения.

Противоречие между любыми источниками (или между документом и кодом) — не правится тихо: запись в [FIXES.md](FIXES.md), решение владельца, синхронная правка всех затронутых мест. Файлы закрытых сессий не переписываются — это исторические записи.

## Обнаруженное вне скоупа

Всё найденное по ходу сессии, что не входит в её скоуп, — отдельным файлом в [backlog/](backlog/README.md) (`BL-NN-краткое-имя.md`, шаблон и реестр — в [backlog/README.md](backlog/README.md)); закрытые записи `make archive` переносит в [backlog/archive/](backlog/archive/). То, что влияет на приёмку текущей сессии, остаётся в сессии, а не уходит в беклог.
