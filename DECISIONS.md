## D-001: Python-зависимости — только uv

- Date: 2026-11-15
- Status: accepted
- Decision: Все зависимости — через uv (`pyproject.toml` + `uv.lock`); pip/poetry/conda не используются.
- Context: uv 0.11 уже установлен в окружении (pip тоже, но uv быстрее и даёт lockfile для воспроизводимой сборки); `python3` в Windows отсутствует — команды через `uv run`.
- Alternatives considered: pip + venv (дольше, нет lockfile из коробки); poetry (не проверен в окружении).
- Consequences: `./init.sh` делает `uv sync --frozen`; seed-скрипты и тесты запускаются `uv run`; скрипт audit-harness.sh патчен для распознавания `uv.lock` (D-003).

## D-014: Эскалация модели — единое правило генерирующих узлов (ADR-007 → v1.1)

- Date: 2026-11-16
- Status: accepted
- Decision: Повторная попытка любого генерирующего узла после провала идёт на уровень вверх (cheap→mid→strong): `plan_joins` — структурная валидация JoinPlan кодом при парсинге + эскалация при провале (раньше у узла не было ни эскалации, ни ветки провала в FSM); `generate_sql` — эскалация mid → strong после `diagnose_error` (правило уже было в §4 ADR-007 и FSM — теперь проговорено в матрице). Эскалацию назначает код по факту провала валидации (`retry_count` + `route_flags`); эскалации расходуют общий retry-бюджет ≤ 3; выше strong — терминальные исходы (`fail`/уточняющий вопрос). Валидация JoinPlan: все таблицы ∈ scope, каждый джойн — ребро графа, ≤ 4 таблиц, связность — как инварианты `plan_query` (ADR-004).
- Context: решение владельца («оценивать результат: если не получилось — передавать модели поумнее», для plan_joins и generate_sql). Аудит состояния пакета показал: эскалация для generate_sql/шагов уже записана (ADR-007 §4, state-agent), но у plan_joins не было ни эскалации, ни ветки провала — валидация JoinPlan нигде не была названа (у plan_query инварианты были, у plan_joins нет).
- Alternatives considered: прыжок «cheap → strong» сразу при провале plan_joins (отвергнуто: reasoning-режим mid дёшев, ~0,02 ₽ попытка, и часто достаточен — платим за провал поэтапно, сильнейшая модель — за фактическую надобность); LLM-судья качества плана (отвергнуто: модель не управляет маршрутом — ADR-002; валидация детерминированная и бесплатная; семантическая оценка «те ли таблицы» — revisit после eval-сета, как и вероятностный роутер ADR-007).
- Consequences: FSM получает второй retry-цикл (plan_joins self-loop + `fail`); матрица ADR-007 проговаривает эскалацию plan_joins и generate_sql явно; эскалации ограничены капом 2 ₽ (худший сценарий plan_joins ≈ +0,9 ₽ — возможен `budget_stop`); в query_trace/спанах виден tier попытки; revisit-триггер: эскалации plan_joins > 10% → поднять стартовый tier. Провода: ADR-002 v1.1, state-agent v1.2, prd v1.7 (FR-8/FR-10), S00 (контракты 1/2), feat-004/009/010, S09/S10; **hw-01/README.md** — эскалация отражена отдельным пунктом §4.3 с диаграммой-лесенкой (прямое указание владельца 2026-11-17 — исключение из правила «не переписывать», касается только эскалации); лимиты провайдера стали §4.4 — ссылки ADR-007 §6 («лимиты провайдера — §4.4»), prd (NFR-8 «README §4.4») и ADR-008 (§4.3→§4.4) теперь сходятся с публичной версией.

## D-026: Retrieval вехи V2 — гибрид (dense + Postgres FTS, слияние RRF) + шумовой корпус-дистрактор для честного замера качества

- Date: 2026-11-20
- Status: accepted
- Decision: Поиск по векторной памяти — гибрид из двух ног внутри того же адаптера `PgVectorStore`: (A) dense — pgvector cosine; (B) ключевая — PostgreSQL FTS (`content_tsv` — generated-колонка `to_tsvector('russian', content)` STORED + GIN; формально ts_rank, не канонический BM25 — на корпусе в сотни документов разницы в выдаче нет). Слияние — RRF: `score = Σ 1/(RRF_K + rank)`, RRF_K = 60 и глубина ноги — именованные константы. Фильтр прав — джойном с `agent_user_roles`/`agent_permissions` в SQL ОБЕИХ ног ДО слияния (NFR-4: слияние с нелегальными документами + пост-фильтр = дыра). Для честного замера (точка владельца: «топ-5 среди 7 таблиц — тривиален, нужен корпус с шумом») индекс дополняется шумовым корпусом: ~300 дистракторов генератором с фиксированным сидом (детерминированно, без LLM), `doc_kind='noise'`, `table_name NULL`; участвуют в поиске, никогда не попадают в промпт (фильтр при сборке контекста). Смоук-метрика hit@5 на 10–20 русских вопросах — baseline в отчёте S06; с ней сравниваются будущие апгрейды.
- Context: решение владельца 2026-11-20: «я бы BM25 добавил» + «чтобы не искать топ-5 среди 7 таблиц и ~похоже замерять поиск — надо добавить корпус с шумом» + «упарываться в строительство RAG не хочется». Варианты BM25 взвешены по цене: ParadeDB pg_search (канонический BM25, Tantivy) — отвергнут: смена запиненного образа БД `pgvector/pgvector` (правка D-006) и новый инфра-риск несоразмерны корпусу; Python `rank_bm25` — отвергнут: новая зависимость + русская морфология без стеммера («клиентов» не найдёт «клиент»). Postgres FTS даёт русский стемминг бесплатно, латинские идентификаторы (имена таблиц/колонок) — точным совпадением — ровно то слабое место dense, из-за которого и добавлялась ключевая нога.
- Alternatives considered: dense-only без шума (отвергнуто владельцем: замер тривиален, точные имена — слабое место dense); ParadeDB (отвергнуто: см. Context — оверинжиниринг по собственной оценке владельца); rank_bm25 в Python (отвергнуто); шумовой корпус только в тест-фикстурах без попадания в индекс (отвергнуто: тогда замер снова тривиален — шум должен ранжироваться вместе с реальными документами).
- Consequences: миграция S06 — generated-колонка (immutable: конфиг литералом) + GIN; адаптер — две ноги с общим фильтром прав, RRF, константы; сборка промпта фильтрует `doc_kind='noise'`; terminology-дисциплина: в доках — «ключевая нога (Postgres FTS, ts_rank)», не «BM25»; hit@5 — baseline-метрика (сравнение апгрейдов: реранкер Qwen3-Reranker-0.6B — кандидат в backlog при недостаточном baseline); feature_list не меняется (behavior feat-006 описывает результат поиска, не способ); ADR-003 не ревизуется (pgvector не заменяется, порт не тронут — его revisit-триггер про замену хранилища, не про гибрид внутри адаптера).
- Дополнение (2026-11-20, перенос измеренного опыта родственного проекта `zvvvv-abab-vectors` — ADR-009 §6 + ACCURACY.md + bench-генератор): (1) **RRF — взвешенный**, не плоский: `score = α_dense/(K+rank_dense) + (1−α_dense)/(K+rank_fts)`, константа `RRF_ALPHA_DENSE = 0.9` — невзвешенный RRF измеримо проигрывает чистому dense (BEIR: ArguAna nDCG@10 0.560 против 0.642, FiQA 0.338 против 0.423; причина структурная: документ, найденный только слабой ногой на ранге 1, получает 1/61 и бьёт dense-ранг 2 с 1/62; их α*=0.90 сделал гибрид ≥ dense на обоих корпусах). Наши 0.9 — старт без тюнинга, перекалибровка по hit@5-базлайну при необходимости; + кап глубины ноги `MAX_LEG_DEPTH` (на ~350 документах не срабатывает, страхует рост: длинный запрос одним термом без капа затаскивает тысячи документов). (2) **Нормализация текста** при upsert и в запросе (один общий хелпер): снятие комбинирующего акута U+0301 и ё→е — акут не буква и резал термы пополам («Кана́рские» → «кан»+«рские»); их замер на RuBQ: nDCG@10 0.3634 → 0.4306 после однострочного фикса. Регистр не трогаем — `to_tsvector` приводит сам. (3) **Дизайн дистракторов**: дистрактор делит общий признак с целью (иначе задача вырождается и hit@5 обманчиво высок); генератор — фиксированный seed, stdlib, самопроверка двойной генерацией (побитово тот же результат). (4) **Префикс-заголовок в чанке** («[таблица: orders] …») перед эмбеддингом — сигнал странице/таблице и якорь точного имени для FTS-ноги (каталог рычагов ACCURACY.md §6.2). Что переносить НЕ нужно: квантизация/LSH/IVF machinery (их SAP без векторной БД; у нас pgvector), per-token политика `MIXED_RU_EN2` с Porter2-стеммингом латиницы (у нас латиница — имена таблиц/колонок и должна совпадать точно; английской прозы в корпусе нет).
- Дополнение 2 (2026-11-20, решение владельца — разгрузка вехи V2): веха V2 — **dense-only** («простой источник контекста — dense из 7 табличек»): behavior feat-006 полностью выполняется на dense, корпус ~30 курируемых документов. Вся механика качества — ключевая FTS-нога, взвешенный RRF α_dense=0.9, кап глубины ноги, шумовой корпус-дистрактор, нормализация U+0301, hit@5-базлайн — переносится во веху V3 «Гибридная память» (запись BL-007 в `solution/backlog/`); дополнение и числа-якоря родственного проекта остаются каноном гибрида на момент планирования V3. ## D-027: Старт-гейт кусает только сессию, которую стартуют; маркер — статус шапки «◐ в работе»

- Date: 2026-11-20
- Status: accepted
- Decision: старт-фаза `guard-subagents.sh` (D-023) уточнена решением владельца: архитектурный контроль проходит **по одной сессии — той, которую стартуют**, а не по всем запланированным. Маркер старта — статус в шапке файла сессии (первые 20 строк, синхронно с archive.sh): «◐ в работе» → сессия стартовала, её ARCH-GATE проверяется жёстко (плейсхолдер/незаполненная строка/причина «сессия не начата» = FAIL — make check красный до canon-check ✅ или обоснованного N/A); «[ ] не начата» → запланирована (батч-планирование допустимо) → скипается с пометкой `[SKIP]` (гейт применится при старте); «✅» в корне → WARN «make archive». End-фаза согласована: без явного файла/фичи проверяется последняя стартованная (◐) сессия (запланированные не блокируют clean-check); строгий путь verify-feature по feature-id не меняется (S02 Important-5 сохранён); стартованных нет → WARN exit 0.
- Context: находка владельца на milestone/v2 (2026-11-20): «сейчас две сессии оформлены — а ARCH-GATE пропускается» (S06+S19 из батч-планирования D-024/D-026, обе «не начата»; гвард проверял только последнюю — S19). Батч-планирование должно оставаться дешёвым: план без canon-check легален, гейт включается при старте.
- Alternatives considered: гейт по всем сессиям в корне (реализовано и отвергнуто владельцем в этом же коммите: красит make check на все запланированные сессии, canon-check требовался бы при планировании, а не при старте); гейтить по статусу, но без валидации «не начата» у ◐ (отвергнуто: ◐ с «не начата» — то же знание в противоречии, дыра осталась бы); красить запланированные WARN'ом до старта (отвергнуто: шум без неизбежности); не трогать end-фазу (отвергнуто частично: запланированные сессии в корне блокировали бы clean-check чужим плейсхолдером REVIEW-GATE — согласована с той же статус-моделью).
