## D-001: Python-зависимости — только uv

- Date: 2026-11-15
- Status: accepted
- Decision: Все зависимости — через uv (`pyproject.toml` + `uv.lock`); pip/poetry/conda не используются.
- Context: uv 0.11 уже установлен в окружении (pip тоже, но uv быстрее и даёт lockfile для воспроизводимой сборки); `python3` в Windows отсутствует — команды через `uv run`.
- Alternatives considered: pip + venv (дольше, нет lockfile из коробки); poetry (не проверен в окружении).
- Consequences: `./init.sh` делает `uv sync --frozen`; seed-скрипты и тесты запускаются `uv run`; скрипт audit-harness.sh патчен для распознавания `uv.lock` (D-003).

## D-014: Эскалация модели — единое правило генерирующих узлов (ADR-007 → v1.1)

- Date: 2026-11-16
- Status: accepted
- Decision: Повторная попытка любого генерирующего узла после провала идёт на уровень вверх (cheap→mid→strong): `plan_joins` — структурная валидация JoinPlan кодом при парсинге + эскалация при провале (раньше у узла не было ни эскалации, ни ветки провала в FSM); `generate_sql` — эскалация mid → strong после `diagnose_error` (правило уже было в §4 ADR-007 и FSM — теперь проговорено в матрице). Эскалацию назначает код по факту провала валидации (`retry_count` + `route_flags`); эскалации расходуют общий retry-бюджет ≤ 3; выше strong — терминальные исходы (`fail`/уточняющий вопрос). Валидация JoinPlan: все таблицы ∈ scope, каждый джойн — ребро графа, ≤ 4 таблиц, связность — как инварианты `plan_query` (ADR-004).
- Context: решение владельца («оценивать результат: если не получилось — передавать модели поумнее», для plan_joins и generate_sql). Аудит состояния пакета показал: эскалация для generate_sql/шагов уже записана (ADR-007 §4, state-agent), но у plan_joins не было ни эскалации, ни ветки провала — валидация JoinPlan нигде не была названа (у plan_query инварианты были, у plan_joins нет).
- Alternatives considered: прыжок «cheap → strong» сразу при провале plan_joins (отвергнуто: reasoning-режим mid дёшев, ~0,02 ₽ попытка, и часто достаточен — платим за провал поэтапно, сильнейшая модель — за фактическую надобность); LLM-судья качества плана (отвергнуто: модель не управляет маршрутом — ADR-002; валидация детерминированная и бесплатная; семантическая оценка «те ли таблицы» — revisit после eval-сета, как и вероятностный роутер ADR-007).
- Consequences: FSM получает второй retry-цикл (plan_joins self-loop + `fail`); матрица ADR-007 проговаривает эскалацию plan_joins и generate_sql явно; эскалации ограничены капом 2 ₽ (худший сценарий plan_joins ≈ +0,9 ₽ — возможен `budget_stop`); в query_trace/спанах виден tier попытки; revisit-триггер: эскалации plan_joins > 10% → поднять стартовый tier. Провода: ADR-002 v1.1, state-agent v1.2, prd v1.7 (FR-8/FR-10), S00 (контракты 1/2), feat-004/009/010, S09/S10; **hw-01/README.md** — эскалация отражена отдельным пунктом §4.3 с диаграммой-лесенкой (прямое указание владельца 2026-11-17 — исключение из правила «не переписывать», касается только эскалации); лимиты провайдера стали §4.4 — ссылки ADR-007 §6 («лимиты провайдера — §4.4»), prd (NFR-8 «README §4.4») и ADR-008 (§4.3→§4.4) теперь сходятся с публичной версией.

- Date: 2026-11-19
- Status: accepted
- Decision: `scripts/guard-subagents.sh` — двухфазный. **Start-фаза** (`--phase start`, вызывается из `init.sh` — т.е. из `make check` — и из `make session-start`): (1) самовосстановление файла сессии — нет раздела «Гейты субагентов» или строк ARCH-GATE/REVIEW-GATE → канонические плейсхолдеры дописываются автоматически (`[FIX]`, идемпотентно; раздел — перед «Отчёт по сессии», ARCH-строка перед REVIEW); (2) ARCH-GATE обязателен: плейсхолдер/незаполненная строка = exit 1 → make check нельзя пройти с незаполненным ARCH-GATE (заполнение «задним числом» технически возможно — временной порядок остаётся процессным; механически гейт гарантирует, что незаполненный ARCH блокирует make check); (3) REVIEW-GATE на старте — мягкий `[WARN]` (жёсткая проверка остаётся end-фазе); (4) активной сессии нет (свежий клон / всё в archive/) → WARN, exit 0 — рестартуемость репозитория (`./init.sh` — verification feat-001); (5) закрытая сессия, не уехавшая в archive/ → WARN «make archive». **End-фаза** (дефолт; `make clean-check` / `session-end` / `verify-feature.sh` в strict-режиме) — прежнее поведение, файл не мутируется. Все пути к сессиям — через `SESSIONS_DIR` (переопределение в self-test). Self-test `scripts/tests/test-guard-subagents.sh` (53 assert-а / 17 кейсов: обе фазы, все ветки самовосстановления, идемпотентность, strict, совместимость, дословное равенство плейсхолдеров TEMPLATE) включён в `init.sh` — гвард, стоящий в цепочке make check, верифицируется на каждом прогоне.
- Context: запрос владельца — «архитектурный контроль пред стартом и ревью в конце должны быть неизбежными; при старте проверять консистентность файла сессии и добавлять недостающие чекбоксы». До: гейты проверялись только на финале (clean-check/session-end/verify-feature); ARCH-GATE можно было заполнять «задним числом» в конце сессии; файл сессии мог существовать без раздела гейтов; работа вовсе без файла сессии проходила clean-check (guard брал последнюю архивную сессию с заполненными гейтами).
- Alternatives considered: WARN-only на старте (отвергнуто: предупреждение игнорируется — неизбежность даёт только красный make check); отдельная команда `make session-start` вне init.sh (отвергнуто: её можно не запустить; неизбежность = встроенность в единый критерий консистентности репозитория); красить REVIEW-GATE на старте (отвергнуто: ревью по определению делается в конце — красный baseline на всю сессию ломает «repair baseline first»); жёстко требовать файл сессии в start-фазе (отвергнуто: ломает рестартуемость свежего клона — init.sh обязан быть зелёным из чистого checkout, feat-001); проверка «каждый коммит ↔ сессия» (вне скоупа, сложность несоразмерна пользе на текущем масштабе — один исполнитель).
- Consequences: новый ритуал «создай файл сессии ДО make check»: создал — make check красный → canon-check (или N/A с причиной) → зелёный; init.sh в start-фазе мутирует файл сессии (осознанное самовосстановление, каждая вставка репортится); дыра «работа вовсе без файла сессии» закрыта лишь частично (WARN на старте + end-fallback на архив) — усиление отложено в BL-006; провода синхронно: AGENTS.md (Startup шаги 4/8), TEMPLATE_session.md (раздел гейтов + Ловушки-4), scripts/README.md; S22 dogfoods гейт (ARCH-GATE N/A до первого код-коммита). REVIEW-GATE — в файле сессии.
